# Open design questions

These are unresolved design questions, not hidden implementation status or executor-ready plans. When a question receives an accepted contract and concrete acceptance case, move the resulting work into the appropriate project index.

1. **Shared-tree recovery and endpoint movement.** How can a stable TreeID refresh endpoint hints durably and verifiably without recreating a central registry?
2. **Identity and recovery UX.** How should device replacement, profile recovery, and disputes prove control without turning local Arbor Sync into a multi-user account service?
3. **Merge semantics.** What backing-appropriate logical conflict semantics should structured collections and whole-database SQLite revisions use beyond text's three-way merge?
4. **Determinism discipline.** How should query and agent-tool runtimes isolate clock, randomness, I/O, and runtime upgrades from results claimed to be deterministic?
5. **Compiler correctness.** How should handle extraction, validator generation, realm separation, and access inference be independently verified as security boundaries?
6. **Schema evolution.** How should mounted consumers continue to work on older shapes while an Arbor tree or external database changes schema?
7. **Consent precision.** How should interfaces explain enforcement-true prefix declarations that are broader than the reads or writes a particular run performs, especially for computed paths?
8. **Cross-server executable data.** How should query discovery, delegated authorization, and server-to-server routing let an allowed document use remotely hosted data without treating network reachability as authority?
9. **Local object store as a hardlink tree.** Arbor Sync's job is to make part of the disk content-addressable and keep it equal to Canopy's accepted root. Today other processes reach that store over loopback HTTP (`/v1/objects`), backed by a private SQLite path-to-hash index with stat-tuple validity. The interface that follows from the frame is a directory, `objects/<tree>/<hash>`: a file object is a hardlink to the real inode, a directory object is a small file the daemon writes, reads are an open and a verify, and superseded objects stay readable after rename-style saves until retention unlinks them, which is what Canopy fetch-through compensates for now. Open points before it is worth building: a measured cold open showing the loopback hop matters; same-volume and cloud-folder limits; in-place writers (Vim preserves hardlinks by writing in place) so verify-on-read and the Canopy fallback stay; pending-body objects remain daemon-only. Space, speed, and upkeep: a hardlink costs a directory entry and shares the inode, so file objects are free and only retained old versions cost their size until GC; every option pays the same file read and hash on lookup, and the lookup itself (an open, a microsecond LMDB get, or a tens-of-microseconds SQLite query) is noise beside it, so the only overhead worth removing is the loopback HTTP hop of a few hundred microseconds plus one copy, and only when many small objects are fetched in a burst; the walk still needs path-to-hash and stat tuples to know which links are stale, so the SQLite index stays and a hardlink tree is a second structure to keep consistent, same-volume only, with cross-volume falling back to copying. A key-value store buys nothing over either SQLite for the daemon's own index or hardlinks for the shared surface, since it either dangles like a pointer or copies like git.
