# The browser
*Part of the [Arbor spec](../spec.md): the human surface — navigation, rendering, editing, and agent pages.*

The browser is a view *and editing surface* over arbord, never an independent storage authority. The broader browser remains **TreeHopper**, in two faces: **TreeHopper web**, using the TypeScript arbord client, and **TreeHopper native**, whose `WorkspaceProvider` uses the Swift arbord client on macOS and a direct Clamshell backend on iOS ([plan-native.md](../plan-native.md)). Both clients implement the same local [REST and event contract](arbord-rest.md). TreeHopper's built-in source-preserving Markdown editor is **ArborNote**. A human in either face and an agent using the local API see the same workspace and live changes.

## 1. Navigation and system state

The home view renders `system:mounts` as subpage-like rows without storing control records in the publishable home page. Cmd+P accepts workspace paths, durable document IDs, `arbor://` names/TreeIDs, invitations, and full-text search. Provenance indicates local, mounted rw/ro, overlay-active, visited, pinned, or stale.

The sidebar is contextual: on a page it lists that page's containing directory; on a directory page it lists that directory's children. It therefore remains useful while reading or editing a file instead of disappearing into a page-only state. It is visible by default on desktop, collapsible through the header or Cmd-\, remembers that desktop preference locally, and becomes an initially closed overlay drawer on narrow screens. A parent action moves the context up one directory and is shown only while still below the root passed to `arbor dev`; navigation can never escape that root. Markdown labels, breadcrumbs, search results, and routes use logical extensionless names, so sibling `x.md`, directory `x/`, and fallback `x/_index.md` all contribute to the single browser location `/x`.

Every page has a source view. Search runs locally over the materialized workspace. Sharing a folder and accepting an invitation are system operations that create shared trees, grants, credentials, and mounts; TreeHopper supplies their human UI.

TreeHopper native uses system windows/tabs over this same browser model. Each tab owns reference-based back/forward history, current location, sidebar context, and presentation state; duplicate tabs share the provider's per-document coordination rather than opening competing write queues. Its toolbar supplies back, forward, parent, breadcrumbs/Open Location, sidebar, search, create, and context-sensitive node actions. Menus distinguish browser commands (New Document/Folder, Open Location, Move/Copy/Trash, link forms) from focused editor commands and disable the latter on file or collection surfaces. Home is a preferred starting location, never the workspace boundary. Platform-native chrome and interaction may differ from TreeHopper web as long as these states and operations agree.

## 2. Rendering and editing

View resolution precedence is strict:

1. reader override on the mount;
2. node's declared `view:`;
3. nearest ancestor `_view.tsx`;
4. built-in defaults.

Built-ins must be genuinely good: article for Markdown, outline for directories, and schema-derived tables for collections. Board, gallery, and calendar views are not specified until one is selected as a concrete feature. Custom presentation belongs in a script. A paragraph containing only a `.tsx` link renders its component as an island backed by arbord's render route.

Rendering resolves every authored reference — links and asset embeds alike — through the shared logical resolver before it reaches the DOM, because displayed routes omit the directory-like base slash and the DOM's native relative-URL rule therefore cannot match Arbor's ([arbord-rest.md](arbord-rest.md), parity reads). Ordinary-file bytes, assets included, are served at their logical routes by kind dispatch.

Built-in views are editable wherever the underlying node is writable. The article view for Markdown is a block editor whose write-back target is the file itself: the file stays canonical, frontmatter is preserved unless edited, and untouched blocks round-trip without churn — every edit remains a clean diff for git and agents.

The directory outline is the same editor over a **complete projected document**. TreeHopper combines the stored directory body with the fully hydrated immediate-child listing; an authored standalone link to a child anchors its managed row, while every unmentioned child appears once in stable directory order after the authored body. This projection exists even when neither sibling `x.md` nor fallback `x/_index.md` exists. Browsing therefore never dirties the filesystem. The first prose/property edit materializes the body, ordering/grouping materializes only the structural Markdown needed to preserve that intent, and first use of durable document identity may materialize frontmatter alone.

Managed child identity lives below the editor as `(block ID, NodeRef, authored/synthetic, kind, materialization)`. ArborNote may render its internal `standaloneLink` block and TreeHopper native may render Hunch's existing subpage row, but both expose the same ordinary link appearance and interactions. Prose/property edits become a singleton Markdown write; reorder, move, rename, copy, trash, and restore become structural mutations with `directoryRevision` and an explicit `beforePath` or `beforeBlockID`. A document session separates those intentions before persistence. Deleting a synthetic presentation row cannot hide a physical child, and arbord is never asked to infer structural intent from a full projected Markdown write.

Rendered body links are interactive. `notes` addresses a child of the containing logical document, `../roadmap` a sibling, and `/people/alice` the enclosing tree root; these semantics do not change when the body moves between `x.md`, `x/_index.md`, and a virtual projection. Absolute `arbor://name/path` and `arbor://tree/<TreeID>/path` destinations open the reader's mounted/visited copy or resolve the shared tree. TreeHopper canonicalizes legacy `.md`, `/_index.md`, bare-domain, and `tree:` spellings, preserves normal back/forward history, and sends explicit non-Arbor schemes to the host browser. A document-ID fragment wins over a stale path, preserving the open session, history, backlinks, and link target through a move. Giving a leaf document its first child creates a sibling directory and leaves its physical `x.md` body untouched without reinterpreting existing relative links.

Source view shows the actual stored Markdown. When the visible editor includes synthetic managed rows or an implicit empty body, source view labels that projection separately rather than claiming those rows already exist as bytes.

“Linked from” uses arbord's backlink index and remains informational. Removing the final authored link never offers to trash its target: tree placement is physical/logical structure, not home-page reachability. Trash is an explicit node operation. Recover can filter to the current document or show the workspace-wide union of Trash plus lost/purged Markdown entries.

TreeHopper web uses BlockNote as its interaction layer, not its storage model. Arbor parses CommonMark/GFM into source-spanned blocks; unsupported constructs remain visible editable raw-Markdown blocks. Saving reuses the exact source for untouched blocks and rewrites only edited blocks. YAML properties are patched through a concrete-syntax tree so comments, order, quoting, and unrelated values survive.

Inline Markdown is converted through the active BlockNote editor for strong, emphasis, strikethrough, inline code, links, and hard breaks. Arbor compares BlockNote's inline structure with the originally parsed structure: an untouched block keeps its exact delimiter spelling and bytes, while an edited block is emitted in BlockNote's canonical Markdown form. Underline, colors, and alignment are absent from the authoring controls because they have no Markdown round trip. Copy exposes BlockNote's Markdown `text/plain` plus rich/internal HTML formats; paste accepts explicit or detected Markdown through BlockNote's default handler. The Arbor-specific `▸` toggle remains a storage notation: internal BlockNote copies preserve the toggle, while external Markdown represents it as an ordinary bullet.

ArborNote supports portable footnotes (`[^label]` references and `[^label]: definition` blocks) plus inline and display LaTeX (`$…$` and `$$…$$`). These are Arbor-owned Markdown mappings expressed through BlockNote custom inline content, custom blocks, input rules, and slash-menu items; KaTeX is only the local renderer and never becomes storage. Arbor tokenizes these extensions before passing the ordinary Markdown between them through BlockNote's CommonMark/GFM conversion, so syntax inside a formula cannot be reinterpreted as emphasis or another Markdown construct. Footnote numbers derive from first-reference order while labels remain stable in source. Untouched syntax round-trips byte-for-byte, and edited regions serialize back to those ordinary Markdown forms.

Footnote definitions remain actual editable BlockNote nodes at their source positions; the responsive presentation never copies or relocates their Markdown. On a wide layout, referenced definitions are projected into the available right margin, aligned with their first references and stacked downward when notes would collide. On a narrow layout, or when the margin is insufficient, those same nodes are projected into one section after the final prose block and ordered by first reference, regardless of where or in what order their definitions occur in source. References jump to definitions, definitions link back, and renaming a reference updates its matching pair. Removing a footnote through its definition action removes that definition and all matching references in one editor transaction. Removing only one side through ordinary editing is allowed and visibly marks the remaining reference as missing or the remaining definition as unreferenced.

The built-in editor is visually aligned with Hunch while retaining BlockNote's web interaction model: the bundled Inter face at 16px/24px body metrics, a centered 708px writing column with 20–48px responsive padding, a 40px first-H1 page title and 30/24/20px later headings, 24px nesting, and sibling-aware vertical rhythm. Light and dark colors follow the system. Properties begin collapsed, stable saved state does not occupy persistent chrome, and Undo, Redo, and Recover live in the page menu; pending, external, conflict, and failed states remain visible when action is useful. These are presentation rules and never synthesize a title or change Markdown.

Document and property edits autosave after a short debounce through a generation-aware compare-and-swap coordinator. Each authored generation uses a content revision and mutation ID; a save is complete only after its durable receipt. The editor distinguishes pending, saving, saved, external, conflict, and failed states; structural filesystem mutations first drain the current document generation. Undo and redo use authored edit checkpoints and reversible filesystem mutations, while failed mutations do not consume a history step. A page keeps one editor instance across saves and external observations. Clean server revisions are reconciled through a non-history transaction rather than reconstructing the editor; editor normalization is not an authored generation. Reconciliation preserves the active text range by text-block position, so a background save or reload does not move focus to the end of the document.

An open page follows arbord events from the cursor attached to its initial snapshot, eliminating the fetch/subscribe gap. Reconnect replays the in-memory window or returns `resync-required`, after which TreeHopper refetches its open page and visible directory. The browser owns local generation admission, `flush`, selection, and undo; arbord exposes no editor-session lifecycle resources ([arbord-rest.md](arbord-rest.md) §5–6).

Immediate physical children render as managed child-page rows inside the ordinary BlockNote body through a custom BlockNote block spec. Their native BlockNote drag handle retains its menu but exposes filesystem Rename and Move to Trash actions. The same handle moves one row, or the visibly selected rows as an ordered batch, using BlockNote's drop-target feedback; a drop between prose blocks rewrites the directory body without regrouping its other children. Anchored placement includes the directory-body byte revision, and a stale revision or vanished block/path anchor rejects the batch rather than appending somewhere else. Page-level creation and rename actions live in a compact More menu, and the contextual sidebar exposes New Page, New Folder, Rename, and Move to Trash. Finder drops copy files and recursively enumerated folders into the selected directory without touching their originals.

Arbor additionally recognizes Clamshell toggle lists. A line `▸ Title` starts a toggle; blank lines and following lines indented at least two additional spaces are its children, recursively. The first nonblank line at-or-above its indentation ends it, and fenced code is opaque during that scan. A toggle may contain any normal block, including another toggle. BlockNote exposes it through its toggle block, slash menu, and `▸ ` typing conversion. Expand/collapse state is session-local, defaults collapsed on reopen, and never changes the Markdown file. This is deliberately an Arbor extension—CommonMark and GFM have no disclosure-list block—and standards-based `<details>/<summary>` HTML remains a raw-Markdown block rather than being converted.

The built-in browser keeps CSV, JSONL, and Postgres table cells read-only; it does not pretend that every store has Markdown editing semantics. Markdown collections use the same table, but schema properties are editable inline and opening a row reveals the ordinary props panel plus body editor. Row validation failures stay local to the affected row and never crash the collection. Database/file row mutations run through their explicit store/script transaction operations rather than a generic editable-table abstraction.

## 3. Beyond mounted trees

Opening an unmounted `arbor://` name or invitation creates a transient mount recorded in `system:visited`; bodies arrive lazily by Merkle walk. Inline assets and ordinary files of a visited tree stream through arbord's tree-qualified file read ([arbord-rest.md](arbord-rest.md), parity reads): the browser never fetches from the remote endpoint directly, so grants, caching, and same-origin behavior stay at the loopback boundary. Annotating—or beginning an edit under the reader's auto-overlay policy—creates an overlay. “Add to workspace” promotes the mount. Back/forward uses recorded revisions; changed-since-read becomes a visible state rather than silent replacement.

If a public domain has no Arbor record, TreeHopper may offer plain `https://` as the legacy-web hatch; a legacy page that advertises a tree via `<link rel="arbor">` or an `Arbor-Tree:` header ([wire.md](wire.md) §7) offers the reverse upgrade into the live tree. If an endpoint is unavailable, cached content renders with explicit staleness.

## 4. Agent pages

An agent is a markdown file: prompt as body, frontmatter carrying the model, `tools:` as references to mutations, and `context:` as references to queries. Opening one in the browser shows its prompt and frontmatter — editable like any page — alongside a chat interface backed by arbord. Tool calls render inline with the same computed consent sentences as any component, and their effects land in the tree like any mutation, so a chat can be watched changing the pages it touches. Prompt edits are ordinary edits with ordinary revisions, and transcripts are themselves ordinary tree content.
