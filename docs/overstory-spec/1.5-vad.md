# VAD, the views-and-data language
*Part of the [Overstory spec](README.md), layer 1 (trees): VAD, the one declarative language in which collections and apps are written, in `.vad` files, in view blocks in pages, and in a collection's `schema.vad`. Its tables, views, state, rules, mutations and expressions, collection views, fingerprints, relational layout and grammar.*

*Owns: VAD's syntax and meaning, tables and their storage and presentation layers, schema fingerprints, the relational layout, views, state, rules, mutations, public error codes and expressions. References: the [data model](1.1-data-model.md) for synchronized values, [collections](1.4-collections.md) for how a collection holds rows, and [reading and watching §4](1.2-reading-and-watching.md#4-views) for addresses, authority, hosting and running views and mutations.*

VAD has no general-purpose code. A collection's tables are declarations; a view's reads are plans a host finds in the file alone, and its markup is a view tree; a mutation is a set of facts that hold once it has run. Interpreting a file never executes code: a conforming implementation parses and checks it under the limits of [§7](#7-limits-and-diagnostics) and derives everything else from the checked result. Extending the data with code of a general-purpose language is not yet specified ([plugins](../../plans/later/apps-014-usl-plugins.md)).

## 1. Overview

VAD declares data and the views and changes over it. A collection's `schema.vad` can hold
all three:

```
// practices/schema.vad
main table Practice:
  name   Text
  about  Markdown?
  likes  Int = 0

mutation like(p Practice):
  p.likes = p.likes + 1

view():
  <Column>
    <Row for={p in Practice} orderBy={p.likes desc}>
      <Text>{p.name}</Text>
      <Button action={like(p: p)}>👍 {p.likes}</Button>
    </Row>
  </Column>
```

`Practice` is a **table**: its rows are the collection's children, `/practices/walking`
([§2](#2-tables)). The unnamed **view** is what the collection shows at `/practices`. Its
`for` is a read, a plan the host finds in the file without running anything, and the `Row`
appears once per practice ([§3](#3-views)). `like` is a **mutation**: its lines are facts
that hold once it has run, here that the practice has one more like ([§4](#4-mutations)).
Views and mutations may also sit in their own `.vad` files and in view blocks in pages
([§3.6](#36-vad-files), [§3.7](#37-view-blocks-in-pages)).

The rest of this chapter defines tables (§2), views (§3), mutations (§4), and what a
collection's `schema.vad` adds: its views and how its tables are stored
(§5). §6 sets limits and §7 summarizes the grammar. [reading and watching §4](1.2-reading-and-watching.md#4-views) defines how a
host serves views and runs mutations.

### 1.1 Syntax

A `.vad` file is UTF-8 text without a byte-order mark. A comment runs from `//` to the
end of the line. Space, tab and carriage return separate tokens, and a line feed ends a
line.

**Indentation groups.** A declaration's header ends with `:`, which always ends its line,
and its body is the lines below it indented further, by spaces. A body ends at the first
line indented no further than its header. Inside parentheses, lists `[ … ]` and record
values `{ field: value, … }`, line feeds and indentation are ignored and items are
separated by commas. Braces hold only record values here, and `{expression}` in a view's
markup ([§3.1](#31-elements)).

An identifier is `[A-Za-z_][A-Za-z0-9_]*`. A number is an optional `-`, decimal digits,
and an optional fraction. A string is double-quoted on one line, with `\"`, `\\`, `\n`
and `\t` escapes.

The words `main`, `table`, `my`, `session`, `enum`, `re`, `seed`, `ordered`, `unique`,
`path` and `as`, and the words the rest of this chapter uses, are keywords
only where they are placed, so a field or table may still be named `id`, `seed` or
`path`.

## 2. Tables

A collection's `schema.vad` declares its data tables and how they connect:

```
main table Game:
  name        Text
  status      Status
  description Markdown?
  tags        Text[]
  authors     Person[]
  first       Date = today

table List:
  name  Text
  games Game[]

Game.authors[] @fold <-> Person.games[]
ordered List.games[] @fold <-> Game.lists[]
Game.status <-> Status.games[]

enum Status:
  Draft       ~color("#9aa0aa")
  Playtested  ~color("#bd861a")
```

Attributes starting with `@` and `~` say how a placement stores a table and how clients
color it; they never change the rows ([§5.1](#51-layers-and-attributes)).

### 2.1 Tables and fields

`table Name:` declares a table, whose body is its fields, and `main table Name:` the
collection's main table. A table or enum name is unique, and `Person` and the value type
names are reserved.

`main table Practice:` makes Practice the collection's main table: its rows are the
collection folder's own children (`/practices/walking`). Every other table with data rows
is a child of the folder named after the table, holding that table's rows
(`/practices/Tag/t1`), so adding a table never moves the main table's rows. A schema has
at most one `main` table, and an enum or connection table can't be one. A main row whose
name equals another table's name is invalid.

A field is `name [modifiers] Type [= default]`. The type is a value type or a table name,
optionally followed by `?` (at most one value) or `[]` (any number). Modifiers go between
the name and the type:

| Modifier | On | Meaning |
|---|---|---|
| `ordered` | a many-valued field or connection end | its members are a sequence; merges as one |
| `unique` | a single value field | no two rows share its value |
| `path` | one required `Text` field | its value is the row's name in the tree; otherwise the key names it |

A **default** after `=` is the value a mutation writes when it creates a row without
giving that field ([§4.1](#41-facts)). It is a
literal, an enum value, `me`, `now` or `today`, evaluated when the row is created, so a
field written only on creation (`first Date = today`) needs no mutation to say so. A
required field with no default must be given when a row is created.

The value types are:

| Type | Values |
|---|---|
| `Text` | one line of text |
| `Markdown` | paragraphs of text; merges by lines |
| `Int` | an integer within ±(2^53 − 1) |
| `Number` | a finite number |
| `Bool` | `true` or `false` |
| `Date` | an ISO 8601 date or date-time |

A value array (`tags Text[]`) is held on the row. A field whose type is a table is a
cross-reference to a connection ([§2.3](#23-connections)); it must agree with the connection
in target and arity.

`Person` is a built-in table: Overstory profiles, referenced by profile id. It has
no rows in any collection. A `Person` value is a profile id (the profile's
TreeID: `tr_` and lowercase base32, `a`–`z` and `2`–`7`), or a
*placeholder* `contact:<key>` for someone with no profile yet, where `<key>`
(1 to 128 of `A`–`Z`, `a`–`z`, `0`–`9`, `_` and `-`) names a row of the
viewer's directory People collection. Any other text beginning `contact:` is
invalid. A reader shows a placeholder by the name its directory has for that
row, or by its key when it can't resolve it, and never drops it. When the
person gets a profile, their placeholders are rewritten to the profile id.

Every row has the implicit fields `id`, `created` and `modified`, which a table can't
declare and a mutation can't write. `created` and `modified` are date-times that only
accepted changes set ([collections §2](1.4-collections.md#2-rows-and-values)).

### 2.2 Enums

An enum is a table whose rows are written in the schema: its values, one per line.

```
enum Status:
  Draft
  Playtested
```

A reference to an enum is the value's name, written unquoted in expressions
(`g.status == Draft`), and an enum has no stored table. A value name that isn't an
identifier is a string (`"Current focus"`).

An enum whose values carry data declares its fields first, then its values, each with a
record of its fields' values:

```
enum Genre:
  blurb Text

  Puzzle    { blurb: "Think it through" }
  Strategy  { blurb: "Plan ahead" }
```

An enum can't be a connection table, and its values can't be changed by editing data.
When people need to add values, the enum becomes a `table` with a `seed:` block, written
in the same form: seed rows are data, inserted when their `id` (the value's name) is
missing and never overwritten, so stored references stay valid. A seeded table needs a
`name Text` field, and colors become data in a field marked `~color`.

### 2.3 Connections

Every connection is written as a connection, with both ends named, outside the tables it
connects: `A.x <-> B.y`. An end `Table.field` declares the field that table gains; `[]`
makes it many and `?` optional, and `ordered` before the end makes its members a sequence
(`ordered List.games[] <-> Game.lists[]`). Each `Table.field` is declared by at most one
connection, and at most one end of a connection is `ordered`. The connection's arity is
that of its ends: many on both is n:m, on one is 1:n, on neither is 1:1.

A named table whose body holds two or more ends is a **connection table**: it connects
them and may carry fields of its own.

```
table Item:
  ordered List.items[]
  Practice.items[]
```

Each end gives it a field named after the end's table in lower case, or the name after
`as` (`Person.friends[] as from`). An unnamed connection holds exactly two ends and
nothing else.

### 2.4 Keys

A table's rows are keyed by `id`, except:

- a connection table is keyed by its ends' fields, so it holds at most one row
  per combination;
- a key in the table's header, `table Tag (list, id):`, keys rows by the named
  single-valued fields (`id` included), here an id unique within its list;
  `table Review (id):` gives a connection table its own `id`;
- an enum's rows are keyed by their names.

## 3. Views

A **view** is a view tree whose elements may carry reads. `view Name(params):` declares
a named view, which other views draw as an element `<Name …/>`, and `view(params):` a
file's unnamed view, which is the view of its node ([§3.6](#36-vad-files)):

```
view PracticeCard(p Practice):
  <Card>
    <Text style="heading">{p.name}</Text>
    <Markdown source={p.about} lines={6} />
  </Card>
```

A parameter is written like a field, `name Type`, with a type from
[§2.1](#21-tables-and-fields) (`l List`, `name Text?`, `tags Text[]`). A parameter with no
type is text. A parameter typed with a table takes a row; given a key, from a query string
or a form, it resolves the key to the table's row, and a key with no row the caller can
read is `missing`.

A view's body is one element, optionally preceded by `state`, `keep` and event lines
([§3.9](#39-state), [§3.10](#310-actions-forms-and-events)), or, in a **data view**, a
record in braces that a host returns as JSON ([§3.12](#312-data-views)). Its parameters are its input: from
the query string when it is visited at its address ([locators §7](1.6-locators.md#7-view-addresses)), and from
attributes when it is drawn as an element ([§3.8](#38-using-other-files-and-views)).

A view's **plan** is every read in it and in the views it draws, found by checking the
file, not by running it ([reading and watching §4.2](1.2-reading-and-watching.md#42-plans-and-live-dependencies)). What the host
reads depends only on the view's input and the user. Conditions that read state are
evaluated on the viewer's device instead ([§3.9](#39-state)).

### 3.1 Elements

An element is `<Type attributes>children</Type>` or `<Type attributes />`. `Type` is a
named view the file declares or uses, or a type of the UI language, whose vocabulary of view types and controls
([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)) a client draws natively or as
HTML. An attribute is `name="text"`, `name={expression}`, or a bare `name`, meaning
`name={true}`. Text children may hold `{expression}`, and so may quoted attribute text:
`subtitle="@{person.handle}"`.

These attributes belong to the language, on any element:

| Attribute | Means |
|---|---|
| `for={name in source, …}` | introduce names and expand ([§3.5](#35-expansion)) |
| `where={condition, …}` | conditions on the matches of the element's `for` ([§3.3](#33-conditions-and-rules)) |
| `if={condition, …}` | on an element without `for`: draw it only when the conditions hold |
| `orderBy={expression [desc], …}` | order the matches; ties fall back to canonical order |
| `group={expression}` | group the matches by the expression's values; a match is in each group its value reaches |
| `limit={n}` | keep the first `n` matches |
| `fallback={element}` | drawn when the element expands to nothing or its conditions fail |
| `key={expression}` | the element's identity among its siblings; defaults to the row keys of its names |
| `slot="name"` | which named place in its parent the element fills |

`where` goes only with `for`, and `if` only without it; either in the wrong place is a
check error. A view tree is plain `{type, props, children, key}` data. `Markdown` renders
a Markdown source string with Overstory's ordinary link resolution, safe URL and asset
policy, and source semantics. It is the standard way for a view to present stored
Markdown. It resolves a relative Markdown destination from the directory holding the
file, as [locators §2.1](1.6-locators.md#21-links-written-in-markdown) defines. For a
destination carrying the reserved `#overstory-key=` alias, it emits the equivalent
server-visible path suffix and preserves the authored application query. It does not
forward the reserved identity alias as an HTML fragment.

**`Rows`** is the standard element for a list of rows that a reader can edit in place. It
draws one line per match of its `for`, with its children as the line's cells, grouped
under a heading per value of `group` when it has one (a row with several values appears
under each), and ordered by `orderBy`:

```
<Rows for={l in List} group={l.owner} orderBy={l.modified desc}>
  <Bullet value={l.visibility} />
  <Text>{l.name}</Text>
  <Count of={l.items} />
</Rows>
```

A client may draw a `Rows` as its own native, editable list. A cell that shows one of the
matched row's own fields, or the rows a connection field reaches, edits that field or the
connection; regrouping a row writes its `group` field when that is one of its own fields.
A cell computed from other rows, such as a count or the latest of several dates, is
read-only. A field whose table is a **connection table** keyed by exactly its two ends
(`Item` between a list and a practice) shows and groups by what it connects to: a list's
`items` are its practices, in the connection's order, and connecting or regrouping writes
the connection's rows. Any other row whose key has several fields (`Tag (list, id)`) is
named by its whole key. Which cells a client draws natively, and how a `Rows` with other
cells falls back to ordinary drawing, are not yet specified
([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)).

### 3.2 Reading rows

`for` on an element introduces names and the rows they range over:
- **A table's rows:** `for={l in List}`.
- **A relationship's rows,** from a name already bound: `for={t in i.practice.tags}`.
- **Several names,** separated by commas; a later one may range over an earlier one:
  `for={p in Practice, other in p.authors}`.

A **path** follows fields from a bound name: `l.owner.name`, `i.practice`. A path
through a to-many field reaches every row it leads to, without duplicates:
`l.items.practice.authors` is everyone who wrote a practice on the list. Paths may
be read anywhere an expression is allowed, and a plain relationship read needs no
`for`: `<Avatar person={l.owner} />`.

### 3.3 Conditions and rules

`where` holds the conditions a match must meet, as boolean expressions joined by
commas, which mean *and* ([§3.4](#34-expressions-and-built-ins)):

| Condition | Means |
|---|---|
| `l.visibility == Public` | a field equals a value; an enum value is written by name |
| `q in p.name` | a text field contains text |
| `l.owner == person` | a to-one relationship points at a row, a key, or `null` |
| `person in p.authors` (`person ∈ p.authors`) | a to-many relationship includes a row or a key |
| `p.authors excludes person` (`person ∉ p.authors`) | it doesn't |
| `person in l.items.practice.authors` | a path: some item's practice has this author |
| `a or b`, `not a` | alternatives and negation |
| `curatedBy(l, person)` | a **rule**: a named condition defined once |

Each condition is a fact over the names in scope, and a name that appears in two
facts joins them. A view's reads are its facts: there is no other narrowing, and
nothing else in a view decides which rows it reads.

A **rule** is a named condition, usable in any `where` or `if`. Its body's lines are
conditions joined by *and*, and two rules with the same name and parameters are
alternatives, joined by *or*:

```
rule curatedBy(l List, person Person):
  l.owner == person
rule curatedBy(l List, person Person):
  person in l.contributors.person
```

A rule may not refer to itself, directly or through other rules.

There are no per-table read rules. What a view may read is what its caller may read
([access control §4.3](3.2-access-control.md#43-authority-and-consent)), and rows that some readers must not see live in a
tree those readers can't read ([access control §4.4](3.2-access-control.md#44-data-disclosure)).

`orderBy` orders an element's matches, `group` groups them and `limit` cuts them
([§3.1](#31-elements)). All three are part of the plan.

### 3.4 Expressions and built-ins

Expressions are literals, names, paths, calls and operators. Literals are text in double
quotes (which may hold `{expression}`), numbers, `true`, `false`, `null`, lists `[a, b]`,
records `{ name: value }`, and durations (`16ms`, `1s`, `5m`, `2h`, `7d`). An enum value
is written by name (`Public`). A path through a many-valued field is a set of distinct
values ([§3.2](#32-reading-rows)).

| Operators, by precedence | Means |
|---|---|
| `.` | follow a field |
| `not`, unary `-` | negation |
| `*`, `/` | arithmetic |
| `+`, `-` | arithmetic; `+` joins text; a date plus or minus a duration, and a date minus a date; on a set, `+ x` adds a member and `- x` removes one |
| `==`, `!=`, `<`, `<=`, `>`, `>=` | comparison; comparing a set with `==` is a check error |
| `x in S` (`x ∈ S`), `S excludes x` (`x ∉ S`) | membership in a set or list, or containment of text, and its negation |
| `and` | both |
| `or` | either |
| `a ?? b` | `a`, or `b` when `a` is `null` |
| `c ? a : b` | choice |

Nulls have no third truth value: `null == null` is true, any other comparison with `null`
is false, and a path through a `null` is `null`.

Built-in functions are pure: `count(path)`, `count(name in source where …)`,
`exists(name in source where …)`, `sum(path)`, `min(path)`, `max(path)`, `lower(text)`,
`upper(text)`, `trim(text)`, `length(text)`, and `set` in actions. `me`, `community`,
`page`, and, in mutations and defaults, `now` and `today` are built-in names. A name a
file declares may not reuse a built-in name.

### 3.5 Expansion

An element with a `for` **expands**: it appears once for each distinct combination of
values of the names it introduces and uses, in its attributes, its text or anywhere
among its children. A name it introduces but uses only in `for` and `where` joins
without multiplying the element. So

```
<Avatar person={other}
  for={p in Practice, other in p.authors}
  where={person in p.authors, other != person} />
```

draws one avatar per collaborator, while a `Text` that shows both `{other.name}` and
`{p.name}` draws one line per pair.

An element with `if` appears when its conditions hold and not otherwise.
`fallback` gives what to draw when an element expands to nothing or its conditions
don't hold.

Inside an element, the names its `for` binds are fixed. A nested element's reads
therefore run once per match of its ancestors, and the result is tree-shaped:
`<Badge for={t in i.practice.tags} where={t.list == l}>` inside an expansion over a
list's items draws each item's tags for that list.

A name that no `for` binds and no parameter or state declares is a check error.

### 3.6 `.vad` files

Views are written in `.vad` files, in view blocks in pages ([§3.7](#37-view-blocks-in-pages)),
and in a collection's `schema.vad` ([§5](#5-a-collections-schema)). To the language each
is a file, and any file may declare views, rules, mutations and state tables
([§3.9](#39-state)); a collection's data tables are declared only in its `schema.vad`.

A `.vad` file is a node's body, as a `.md` file is
([data model §8](1.1-data-model.md#8-mapping-files-and-directories-to-nodes)), and its
unnamed view is that node's view. A collection's `schema.vad` is the exception: it is a
file entry of the collection's folder, not a body ([§5](#5-a-collections-schema)).
`Drafts.vad` is the view at `Drafts`, and `Drafts?status=review` shows the essays under
review:

```
// Drafts.vad. Essay is a table of the nearest schema.vad.
view(status):
  <Column>
    <Row for={e in Essay} where={e.status == (status ?? "draft")} orderBy={e.date desc}>
      <Text>{e.title}</Text>
      <Text style="secondary">{e.date}</Text>
    </Row>
  </Column>
```

A file is a sequence of declarations, in any order, written as [§1.1](#11-syntax) says:

| Declaration | Declares |
|---|---|
| `use "path"`, `use "path" (names)` | another file, `.vad` or page, whose names this file uses ([§3.8](#38-using-other-files-and-views)) |
| `view(params):` and an element | an unnamed view ([§3](#3-views)): a `.vad` file's view, at most one per file, or a view drawn where its block sits |
| `view Name(params):` and an element | a named view, addressable and drawn as an element `<Name …/>` ([§3.8](#38-using-other-files-and-views)) |
| `rule name(params):` and conditions | a rule ([§3.3](#33-conditions-and-rules)) |
| `mutation name(params):` and facts | a mutation ([§4](#4-mutations)) |
| `my table`, `session table`, `enum` | a state table ([§3.9](#39-state)), or an enum ([§2.2](#22-enums)) |
| `table`, `main table`, connections, `re` | a collection's data tables, only in its `schema.vad` ([§2](#2-tables)) |

VAD is versioned with this specification. The tree's shape never depends on code: a
`.vad` file is a body whether or not it checks, and a file of any other extension,
`.tsx` included, reads as an ordinary file. Structured editors that cannot preserve a
`.vad` file or a view block exactly must use a raw or code-capable mode. They never
rewrite it as ordinary Markdown.

### 3.7 View blocks in pages

A fenced code block whose info string is `view` holds declarations and at most one
element on its own, which draws where the block sits:

````md
# Today

```view
<Text>{count(c in page.children where c.done)} of {count(page.children)} done</Text>
```

```view
view Late():
  <Column>
    <Text for={c in page.children} where={not c.done, c.due < page.date}>{c.name}</Text>
  </Column>
```
````

- **All of a page's view blocks are one file** ([§3.6](#36-vad-files)): a
  name declared in one block is usable in every other, and `use` in any block applies to
  all. Other files use a page's named views, rules and mutations with `use "Today.md"`.
- **A block's own element** is an unnamed view with no parameters, drawn where the
  block sits. `view(params):` in a block is the same with parameters, and
  `view Name(params):` adds an address, `Today?view=Late` ([locators §7](1.6-locators.md#7-view-addresses)).
  Unnamed views on a page take the page's query string as their input.
- **A named view without parameters also draws where its block sits.** One with
  parameters draws only where it is drawn as an element or addressed, and a block holding
  only those, rules, mutations or state tables draws nothing.
- **`page`** is the page a view is drawn in: the page holding the view block that draws
  it, or the view's own node when it is visited by itself. Its fields are the page's
  properties, read as their values with no schema, plus `name`, and `page.children` is its
  child nodes, each read the same way. Reading `page` is a read like any other: it joins
  the plan and is a live dependency.

A page's prose stays non-executable Markdown: a page runs nothing because it links a
view. A client that doesn't evaluate views shows each block as code. Story shows a block's
source while it is being edited and its drawing otherwise.

### 3.8 Using other files and views

A file uses what other files declare in one of two ways:

```
use "List.vad"                                        // all of its names
use "ui/cards.vad" (PracticeCard, Card as PlainCard)  // only these
use "views/reading-room.vad" (view as ReadingRoom)    // its unnamed view
```

- **`use "path"`** makes the used file's tables, named views, rules and mutations
  available by their own names, and a `.vad` file's unnamed view available as an element
  named after the file's node, `List` for `List.vad`.
- **`use "path" (names)`** makes only the listed names available. `Name as Other` makes
  one available as `Other`, and `view as Name` names a `.vad` file's unnamed view, which a
  file whose node name isn't a name, such as `reading-room.vad`, needs before its view
  can be drawn. A listed name the file doesn't declare is a check error, so a library
  that renames something fails where it is used. A pick list is the form for libraries.

Names a file declares shadow the names it uses. Two uses making the same name
available is a check error at the point of use; the fix is a pick list that leaves one
out or renames it.

The path names a `.vad` file, a page or a collection's `schema.vad` as a Markdown link
would, relative to the using file; another tree's file is named by an absolute Overstory
locator and resolves to one immutable code version for one build or execution. A file
can't use itself, directly or through others. Everything a file declares can be used;
there are no export lists.

A file binds the collection schema of its folder or nearest ancestor that has one without
a `use`, and `use "data/schema.vad"` binds another. Checking resolves each table, field
and path against the schemas and state tables a file binds, and fails on a name it can't
resolve. Schema information and explicit relationship declarations are mapped to
canonical tree-rooted collection paths, so files remain portable across placements. A
change to a collection's data layer changes its schema fingerprint
([§5.3](#53-fingerprints)) and invalidates dependent checked handles; a storage or
presentation change alone invalidates none.

A **named view** can be drawn as an element whose type is its name, with its
parameters as attributes. This one, from `parts/cards.vad`, is also addressable as
`parts/cards?view=PracticeCard&p=…`:

```
view PracticeCard(p Practice):
  <Card>
    <Link style="heading" to="Practice?id={p.id}">{p.name}</Link>
    <Row>
      <Text style="secondary">by</Text>
      <Avatar person={a} for={a in p.authors} orderBy={a.name} />
    </Row>
    <Markdown source={p.about} lines={6} />
  </Card>
```

A drawn view reads only through its own `for`, `where` and paths, which join the plan
of each view that draws it. Drawing another view, or using a file from another tree,
acquires no grants ([access control §4.3](3.2-access-control.md#43-authority-and-consent)). A link to a view
is its address, written like any link and resolved from the file that holds it:
`to="Practice?id={p.id}"`.

### 3.9 State

A view's state is rows of **state tables**, declared with `my table X:` or
`session table X:` like any table ([§2.1](#21-tables-and-fields)), but beside the views
that use them, in any `.vad` file or view block. Their rows are not in any collection
folder, and a state table can't be `main` or an end of a connection that a data table
also ends; its fields may refer to data tables' rows. State tables belong to one viewer
and differ in how long they last:

| | kept | this session |
|---|---|---|
| **one viewer** | `my table`, `keep` | `session table`, `state` |

- A **`my` table** holds one viewer's own rows, across the app. Its rows are read and
  written only by their viewer, need no consent, and are written on the viewer's device
  first.
- A **`session` table's** rows are never stored and live for one viewer's session on one
  device. They suit fast-changing state, such as the positions in a game.
- A state table is declared beside the views that use it, in the same file or view block:

  ```
  my table Lap:
    at     Date
    label  Text

  mutation lap(label Text):
    Lap(at: now, label: label)
  ```

- `state x = value` in a view declares a one-row session table with one field, and
  `keep x = value` a one-row `my` table per placement, where a **placement** is one view
  block's drawing in one page, and a view visited on its own has one placement per
  address. Both are read by name like a parameter and changed with `set(x, value)`
  ([§3.10](#310-actions-forms-and-events)). A view drawn as an element inside another view
  has its own `state` and `keep` for each instance, told apart by the element's `key`.

There are no tables shared by everyone at one placement. A widget's configuration is its
view block's attributes (`<Timer minutes={50} />`), and rows that several people share at
one place are ordinary data, with a field saying which place.

A view reads state the way it reads any rows, and changing state reevaluates only the
expansions that read it.

**State never leaves the viewer's device.** Checking splits each read: the conditions,
orderings and paths that don't read `state`, `keep` or a state table form the plan the
host runs, and those that do are evaluated by the client over the rows the host returns.
So a host never learns state, and a state change redraws without a request. Inputs are
the opposite: they are what the host sees and what a URL carries. A view that wants the
host to filter by a value, for example a search over many rows, takes it as an input
(`?q=…`), which also makes it linkable. A `limit` on an element whose conditions or
ordering read state is a check error, because the host can't cut what it can't order;
the value must be an input instead.

Where `my` rows are stored, and how they reach the viewer's other devices, are not yet
specified ([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)).

### 3.10 Actions, forms and events

An **action** is a call written as an attribute value: a mutation with its input,
`addPractice(name: n)`, or `set(x, value)` for state. `Button action={…}` runs one when
pressed. A client runs a mutation action with a stable mutation identity and exposes
pending state, then its result, durable receipt, or public error.

`Form action={mutation}` supplies the mutation's input from its controls, by name. Form
conversion is shallow and deterministic: a name occurring once becomes its string or file
value, a repeated name an array in document order, and an omitted name is absent; the
mutation's parameter types convert and validate it. `then={action or link}` runs or
navigates after success. Expected failures are a mutation's public errors
([§4.2](#42-public-errors)), input validation among them. Server exceptions, private
values and stack traces never become action state.

A control's `value={x}`, naming state, binds the control to it in both directions.

A view may name actions for events a client delivers, one per line before its element:

```
on key "ArrowLeft" → movePaddle(-12)
every 16ms → step()
```

A client delivers them only while the view is shown, and at most as often as it can draw.
The view still has no clock: an event can only run an action.

### 3.11 An example

A whole view, using rules, expansion and drawn views:

```
// Profile.vad, the view at Profile
use "data/schema.vad"
use "parts/cards.vad"

rule curatedBy(l List, person Person):
  l.owner == person
rule curatedBy(l List, person Person):
  person in l.contributors.person

view(id):
  <Shell title={person.name} subtitle="@{person.handle}"
    for={person in Person} where={person.id == id}
    fallback={<Shell title="Profile not found" />}>

    <Section title="Practices">
      <Grid columns={3}>
        <PracticeCard p={p}
          for={p in Practice} where={person in p.authors}

      </Grid>
    </Section>

    <Section title="Lists featuring their practices">
      <Grid columns={2}>
        <ListCard l={l} for={l in List} where={person in l.items.practice.authors} />
      </Grid>
    </Section>

    <Section title="Lists they curate">
      <Grid columns={2}>
        <ListCard l={l} for={l in List} where={curatedBy(l, person)} orderBy={l.name} />
      </Grid>

    <Section title="Collaborators">
      <Row>

      </Row>

```

### 3.12 Data views

A **data view** returns JSON instead of drawing. It is declared like any view, with `{`
after its parameters instead of `:`, and its body is the shape of the JSON it returns.
A record may be followed by the same attributes a UI element takes, `for`, `where`, `orderBy`,
`limit` and `if` ([§3.1](#31-elements)):

```
view ListsByOwner(owner Person) {
  lists: {
    name
    size: count(l.items)
    owner { name, handle }
    practices: { name } for={p in l.items.practice} orderBy={p.name}
  } for={l in List} where={l.owner == owner} orderBy={l.modified desc} limit={20}
}
```

returns `{ "lists": [{ "name": …, "size": …, "owner": { "name": …, "handle": … },
"practices": [{ "name": … }] }] }`. Inside braces, entries are separated by line feeds or
commas, and each is one of:

| Entry | Gives |
|---|---|
| `key: expression` | the expression's value; a path through a many-valued field is a list |
| `key: { … } for={x in source} where={…} orderBy={…} limit={n}` | a list, one record per match, with the attributes meaning what they mean on an element; the record's bare fields are the match's |
| `field` | the field of the row the enclosing braces are about, under its own name; a relationship gives the key, or a list of keys, of the rows it reaches |
| `field { … }` | follows a relationship from that row: a record for a to-one field, `null` if it reaches none, and a list for a to-many one |
| `key: { … } if={condition}` | the record when the condition holds, and `null` otherwise |

The outermost braces are about no row, so their entries need a `key:`. A data view has
parameters, rules, a plan, an address and live results exactly as a UI view does, and it
has no state, actions or events. A host answers it with its JSON
([reading and watching §4.1](1.2-reading-and-watching.md#41-answer-forms)), and a client
may show that JSON with its own default presentation.

## 4. Mutations

A **mutation** is a named set of facts over the tables its file binds: each line says
something that holds once the mutation has run. Every line reads the rows as they were
before the mutation began, and together the lines make one set of row operations, so
their order doesn't change the result. Two facts that can't both hold, such as two values
for one field of one row, or a row that must and mustn't exist, are a check error when
checking can prove it and a public `conflict` error otherwise.

```
rule editor(l List):
  l.owner == me or l.openToEdits

mutation setListPractice(l List, p Practice, included Bool):
  if not editor(l):
    forbidden "You cannot edit this list"
  if included and l.items.practice excludes p:
    Item(list: l, practice: p)
  if not included and p in l.items.practice:
    not Item(list: l, practice: p)
```

A mutation's parameters are written like a view's ([§3](#3-views)). A parameter
typed with a table receives a key, resolved to that table's row before any other line
applies; a key with no row fails the mutation with `missing`. A mutation runs as
[updates and merging §4](1.3-updates-and-merging.md#4-mutations) defines.

### 4.1 Facts

A mutation's body is lines, each one fact or one block:

| Line | Holds once the mutation has run |
|---|---|
| `Table(field: value, …)` | such a row exists: the row whose key the fields give is updated, or inserted if missing; with no key among the fields, a new row is inserted |
| `not Table(field: value, …)` | no such row exists: every row matching the fields is deleted |
| `row.field = value` | the row's field has the value; on a connection field, the value is the far-end rows, in order for an `ordered` end, so `l.items = practices` reorders a list |
| `let name = Table(…)` | names the row the fact makes, for the lines below |
| `name(param: value, …)` | another mutation's facts hold too |
| `if condition:` and indented lines | the lines hold when the condition does |
| `for name in source where condition:` and indented lines | the lines hold for each match |
| `code "message"` | the mutation fails with this public error ([§4.2](#42-public-errors)) |

A new row takes each field it isn't given from the field's default
([§2.1](#21-tables-and-fields)), and a required field with neither is a check error.
An existing row keeps every field a fact doesn't give. A row added to an `ordered`
connection goes at its end. A new row's generated ID comes from the mutation identity, so
an exact retry inserts the same row. A mutation can't write `id`, `created` or `modified`.

A many-valued field is written as a whole: `t.practices = t.practices + p` adds a member
and `- p` removes one ([§3.4](#34-expressions-and-built-ins)).

A mutation has no return value: its receipt names every row it wrote, by table
([updates and merging §4](1.3-updates-and-merging.md#4-mutations)). A `let` name is local to the
mutation.

`mutation name(row Table) for Table.op:`, where `op` is `create`, `edit`, `delete` or
`move`, declares the mutation as that table's row action, so any list of the table
offers it.

### 4.2 Public errors

A mutation fails on purpose with a **public error**: a line holding one of five codes and
an optional message, in an `if` block that says when.

| Code | Means | HTTP |
|---|---|---|
| `unauthorized` | the caller must sign in | 401 |
| `forbidden` | the caller may not do this | 403 |
| `missing` | a row the mutation needs doesn't exist, or the caller can't read it | 404 |
| `invalid` | the input is wrong | 422 |
| `conflict` | the rows have changed in a way that rules this out | 409 |

```
mutation toggleListReaction(l List):
  if me == null:
    unauthorized "This operation requires a Story user"
  if l.visibility != Public:
    missing "Only public lists can be liked"
  if me in l.reactions.person:
    not Reaction(list: l, person: me)
  if l.reactions.person excludes me:
    Reaction(list: l, person: me, emoji: "👍")
```

Every error's condition is checked before any write, and the first that holds, in the
order the lines are written, ends the mutation with its error and writes nothing. A block
holding an error holds nothing else. Input validation fails with `invalid` and field
errors. Server exceptions, private values and stack traces are never public errors.

## 5. A collection's schema

A collection's `schema.vad` declares its data tables ([§2](#2-tables)), and may declare
views, rules and mutations beside them. It is a file entry of the collection's folder,
not a body ([collections](1.4-collections.md)), and what it declares is used with
`use "data/schema.vad"` like any file's.

- **Its unnamed view is the collection's view.** `view():` in a schema is what the
  collection's folder shows when it is visited, at the folder's own address
  (`/practices`), unless the folder has an `_index.md`. A folder with an `_index.md` is
  that page, which draws the collection's view with a view block like any other
  (`use "schema.vad" (view as Practices)`).
- **Its named views are other ways to show the collection.** They are addressed by the
  schema file's path, `data/schema.vad?view=ByOwner`
  ([locators §7](1.6-locators.md#7-view-addresses)), and a client may offer them as
  alternatives to the collection's view.
- **A collection with no views** shows a plain `Rows` list of its main table, or of its
  first table with rows, and a client may offer the same list grouped by each enum,
  connection or `Person` field.

```
view():
  <Column>
    <Text style="heading">Lists</Text>
    <ByOwner />
  </Column>

view ByOwner():
  <Rows for={l in List} group={l.owner} orderBy={l.modified desc}>
    <Text>{l.name}</Text>
  </Rows>
```

A view in a schema is a view like any other: a host serves it through
[reading and watching §4](1.2-reading-and-watching.md#4-views) with the same plan,
authority, live behavior and result forms, and a client draws it wherever a view can
appear.

### 5.1 Layers and attributes

How a placement stores a collection's tables is set by attributes, in the schema and in the
placement's own mapping, and determines its layout. None of it changes the rows a tree
holds.

A schema says three kinds of thing, and each has its own spelling:

| Layer | Spelling | Says | Shared by |
|---|---|---|---|
| data | plain declarations and keywords | tables, fields, types, keys, connections, enum values | every placement; it is what the tree holds ([§5.3](#53-fingerprints)) |
| storage | attributes starting with `@` | how a placement stores a table: folding, table and column names, indexes, a row's body | defaults every placement starts from, which a placement's own mapping may override |
| presentation | attributes starting with `~` | colors | clients, as defaults a page may override |

There is one sigil per layer and no doubled sigil. An attribute's position decides what
it applies to: one on a line of its own in a body applies to the table, enum or value the
body is for; one after a field, a connection end or an enum value applies to that. Each
attribute name belongs to one layer and one level, as the table below says; an attribute
in the wrong place is a diagnostic.

A table or enum is declared once. `re Name:` adds attributes to a table
or enum declared elsewhere in `schema.vad`, or from a placement's storage mapping: its
lines re-mention fields by bare name (`color ~color`) and an enum's values by name
(`Draft ~color("#9aa0aa")`), and never declare fields, types or values. Every attribute is
legal in a `table`, `enum` or `re` body. By convention, which `vad fmt` applies,
table-level attribute lines come last in a body, after a blank line.

| Attribute | Layer | On | Meaning |
|---|---|---|---|
| `@fold` | storage | one end of an n:m connection | in data files, an array on that end's rows instead of a table of its own |
| `@fold(Table)` | storage | a connection table | in data files, stored on the rows of one table it connects |
| `@column("name")` | storage | a value field, or the end that stores a connection | the stored column's name |
| `@table("name")` | storage | a table with stored rows | the stored table's name |
| `@index(field, ...)` | storage | a table with stored rows, any number of times | databases index those single-valued fields (`id`, `created` and `modified` included) in that order |
| `@body`, `@title` | storage | one `Markdown` field; one `Text` field | in Markdown row files, the field written as the body, and the one written as the page title |
| `@stored("text")` | storage | an enum value, in a `re` block | the text a store holds for that value |
| `~color` | presentation | one single-valued `Text` field of a table | holds each row's color |
| `~color("#rrggbb")` | presentation | an enum value | its color |

Without `@body` and `@title`, a Markdown row file's body is the `Markdown`
field named `content` and its title the `Text` field named `title`, when the
table has them.

**Precedence.** Storage is derived from the tables, then from `@` attributes in the
tree's schema, then from the placement's own mapping: `re` blocks of `@` attributes that
the placement keeps outside the tree, where its implementation chooses
([placements on disk §7](2.2-placements-on-disk.md#7-local-placements)). A mapping is
needed only where a store's names differ, such as an existing database the schema didn't
create. Presentation is derived from the tables, then from `~` attributes, then from a
page's override. Setting one attribute twice at one level of precedence is an error.

### 5.2 Layout

The checked schema and its storage determine the tables, columns and keys a
placement's store holds: its *layout*. A layout is a projection of the logical
form ([collections §2](1.4-collections.md#2-rows-and-values)), so the
two layouts below hold the same rows and changing one never changes data.

- A table with data rows is stored as a table named after it, or `@table`.
  `Person` and enums have none: a reference to a person is a profile id (or a
  `contact:` placeholder), and a reference to an enum is the value's name (or its
  `@stored` text).
- A stored table's primary key is its table's key. A key field that refers to another
  table expands to that table's key columns: one column named after the field
  when the target's key has one column, otherwise `field_key` for each.
- A 1:1 or 1:n connection is a column (or columns) on its single side,
  nullable when that end is optional. An n:m connection is a join table named
  `Table_field` after its first end, keyed by both ends.
- A connection table is stored keyed by its ends, unless `@fold(Table)`.
- An `ordered` many end adds a `field_position` number where the connection is
  stored. Positions are the store's own: a placement writes and renumbers
  them freely, and only their order is data.
- Every stored table has `created` and `modified` columns.
- Database tables index each reference that doesn't lead the primary key,
  profile ids included, and each `@index`. An index whose columns begin
  another index is left out. Indexes never change what a database holds, so
  implementing a schema doesn't depend on them.
- **Data files** follow the same tables, except that an n:m connection with a
  `@fold` end is an array, on that end's rows, of the other side's keys, in
  order when the end is `ordered`. Databases always use a join table.

Two fields stored under one column name are an error. Setting up a database
from a layout creates only what is missing and inserts seed rows only when
missing; it never alters or drops anything.

A database implements a layout when every table and column exists with a
compatible type and nullability, keys and foreign keys match, and any extra
column is nullable or has a default. Extra tables are allowed.

Each connection end is also a named relationship from its table:
`List.owner` reaches one `Person`, `List.items` the `Item` rows of a list, and
`Practice.authors` the people through the join table. Views and mutations
read along these as paths ([§3.2](#32-reading-rows)).

### 5.3 Fingerprints

A collection binds to its schema's **schema fingerprint**: the canonical CBOR hash
([data model §7](1.1-data-model.md#7-cbor-and-hashes)) of the checked data layer, with
tables, enums, fields, values and connections in UTF-8 order of name. Comments,
formatting, defaults, every `@` and `~` attribute, state tables, and the schema's views,
rules and mutations are left out. Changing only storage, presentation or the schema's
code therefore leaves every collection's logical state and hash unchanged.

Storage and presentation have no fingerprint of their own.

## 6. Handles and code versions

Overstory adds no application object, application identifier, entry component, route table, or location language. An app is an Overstory tree holding ordinary pages, `.vad` files and collections ([§3.6](#36-vad-files)). A host that supports execution serves a view at its node's own address.

The tree holding an app's files is identified by its existing `TreeID`; Overstory adds no application-ID
or script-ID namespace. `(TreeID, logical path, name)` identifies a named **handle**:
- a `.vad` file's unnamed view, by its node's path and an empty name;
- a schema's unnamed view, by its `schema.vad` path and an empty name;
- a named view, by its file's path and the view's name;
- a view block with no name, by the page's path and `#n`, its position among the page's
  unnamed views counting from 1, which only the page's own presentation uses;
- a mutation, by its file's path and its name.

A file's **code version** is the SHA-256 over the paths and text of the files and
schema files it uses, transitively, in path order, and is the version of each of its
handles. A `.vad` file's text is its bytes; a page's is the text of its view blocks in
order, so editing a page's prose changes no code version. Moving a file or renaming a
declaration creates a different handle, just as moving any other node changes its URL;
changing a file a handle uses changes its version.

For each handle, checking exposes its parameters and their types, its code
version, the tables and paths it reads and writes, and public result metadata,
without disclosing source a caller may not read.

| Token | Identifies | Minted by | Survives |
|---|---|---|---|
| handle | one view or mutation, as `(TreeID, logical path, name)` | the author | code changes; not a move or a rename |
| code version | one checked file and everything it uses | hashing | moving the tree; prose edits in a page; not a change to any file it uses |
| schema fingerprint | one collection schema's data layer ([VAD §5.3](1.5-vad.md#53-fingerprints)) | hashing the checked data layer | storage, presentation and code changes; not a data-layer change |

Adding a view does not publish it, run it, or grant it access: a host runs
views and mutations only for trees whose hosting it has enabled. It may check
eagerly or on demand, but a request uses one coherent code version of the addressed view and all of its handles,
and a file that fails checking never replaces the last usable version.

A reviewed manifest of what checked code needs, and static baking of reads,
are not yet specified
([Apps 010](../../plans/later/apps-010-activation-and-lending.md)).

## 7. Limits and diagnostics

| Limit | Value |
|---|---|
| Source bytes | 1,048,576 |
| Tokens | 65,536 |
| Nesting depth of values | 32 |

Each limit applies to one file, and exceeding one rejects the file.

A rejected file reports diagnostics with a stable code, a file and a 1-based
line and column. The [`collection-schemas.json`](conformance/collection-schemas.json)
vectors bind the codes they list; messages are not normative.

## 8. Grammar

An informal summary of VAD's syntax; the sections above define what each form means.
A `:` ending a header line groups the indented lines below it as its body.

```text
file        = { use | table | connection | enum | re | view | rule | mutation }
use         = "use" string [ "(" pick { "," pick } ")" ]
pick        = ( name | "view" ) [ "as" name ]

table       = [ "main" | "my" | "session" ] "table" Name [ "(" name { "," name } ")" ] ":"
              { field | end | attribute | seed }                        (§2.1, §5.2)
field       = name { modifier } Type [ "?" | "[]" ] [ "=" default ] { attribute }
end         = [ "ordered" ] Name "." name [ "?" | "[]" ] [ "as" name ] { attribute }
connection  = end "<->" end                                             (§2.3)
enum        = "enum" Name ":" { field } { value }                       (§2.2)
value       = ( Name | string ) [ record ] { attribute }
seed        = "seed:" { value }
re          = "re" Name ":" { ( name | Name ) { attribute } | attribute }
attribute   = ( "@" | "~" ) name [ "(" args ")" ]

view        = "view" [ Name ] params ( ":" { stateLine | eventLine } element | record )
record      = "{" [ entry { ( "," | newline ) entry } ] "}"                (§3.12)
entry       = name [ record ] | name ":" ( expression | record { attribute } )
rule        = "rule" name params ":" { expression }
mutation    = "mutation" name params [ "for" Name "." op ] ":" { line }
params      = "(" [ param { "," param } ] ")"
param       = name [ Type [ "?" | "[]" ] ]
stateLine   = ( "state" | "keep" ) name "=" expression
eventLine   = ( "on" "key" string | "every" duration ) "→" action
element     = "<" Type { attribute } ( "/>" | ">" { element | text } "</" Type ">" )
attribute   = name [ "=" ( string | "{" expression "}" ) ]                (in elements)
action      = call                                                      (§3.10)
line        = [ "not" ] Name "(" args ")" | "let" name "=" Name "(" args ")"
            | path "=" expression | call | code [ string ]
            | "if" expression ":" { line }
            | "for" name "in" expression [ "where" expression ] ":" { line }   (§4)
code        = "unauthorized" | "forbidden" | "missing" | "invalid" | "conflict"
expression  = literal | name | path | call | operator form              (§3.4)
```
