# Reading and watching
*Part of the [Overstory spec](README.md), layer 1 (trees): the routes that read and watch a tree, carrying the [data model](1.1-data-model.md); the encodings every route shares; and presence. Writing is [updates and merging](1.3-updates-and-merging.md). A caller here is one who may read the tree; [access control](3.2-access-control.md) defines who that is.*

## 1. Reading trees

### 1.1 Current tree, accepted snapshots, and watch

A working tree bootstraps by reading the current tree descriptor, obtaining
that descriptor's content-addressed accepted snapshot, and then following the
watch endpoint after the descriptor's `update`.

A snapshot MAY be installed sparsely: directory objects and Markdown file
objects present, every other file object referenced by hash only. A sparse
install counts as the complete accepted snapshot only when every referenced
hash is resolvable on demand and the client has validated the spine (the root
is a present directory, every present object is reachable, and the graph is
acyclic). A payload-less entry the client cannot classify as a file fails the
install.

A client MAY also hold only some directories and load the others by hash when a
path below them is first read (a lazy node index). Each directory it loads must
be checked against the hash its parent names, and a candidate it builds carries
every directory it has not loaded under that same hash, unchanged.

```text
GET /.overstory/trees/{TreeID}
GET /.overstory/trees/{TreeID}/snapshots/{root}
GET /.overstory/trees/{TreeID}/watch?after={update}
```

A client that holds only the pages it has opened reads them with path reads
([§1.2.4](#124-reading-a-path)) instead of a snapshot, and may watch with `objects=none`.

#### 1.1.1 Reading the current tree

```text
GET /.overstory/trees/{TreeID}
```

The response atomically identifies one current accepted root and the accepted
update that produced it, which is also where a client starts watching without a
read/watch race:

```ts
type CurrentTree = {
  tree: RemoteTreeDescriptor;
};

type RemoteTreeDescriptor = {
  id: TreeID;
  kind: "ordinary" | "tree-configuration";
  access: "read" | "write";
  root: Hash;
  update: string;
  conflicted: boolean;
  canonical: {
    path: LogicalPath;
    endpoint: string;
    parentTree: TreeID | null;
    url?: string;
  } | null;
};

type Hash = `sha256:${string}`;
```

The descriptor's `access` summarizes the caller's effective whole-tree access.
A caller who cannot read the tree gets no descriptor: the read is `404`.
Scoped or executable-constrained authority is evaluated by
[access control](3.2-access-control.md), not encoded as named mutation permissions.
The descriptor's `root` is the bytes hash of the current accepted tree state
and `update` is the accepted-update id that produced it. A client watches
with `after={update}` ([§1.1.3](#113-watching)), so the read and the watch meet without a gap.
Throughout the protocol a member that points at an accepted update (`update`
here, in an update answer's `head` and in `AcceptedRef`, and the `base`,
`ifCurrent` and `after` that name one) holds its id. Only where the accepted
update itself is the payload, an update result's and a watch frame's
`update`, is it the whole `AcceptedUpdate` record ([§1.1.3](#113-watching)).
Hosted trees have, in addition, a canonical path, endpoint, and might be nested
inside a parent tree. `canonical.url`, when present, is the tree's canonical URL at a
person's domain ([locators §5.1](1.6-locators.md#51-trees-at-a-persons-domain)); without it
the canonical URL is the endpoint's origin followed by `path`.

The same root may be accepted again by a later update. Its graph remains the
same content-addressed snapshot, while the later descriptor's `update` identifies
the new accepted state, and a watch after it starts there.

#### 1.1.2 Reading an accepted snapshot

```text
GET /.overstory/trees/{TreeID}/snapshots/{root}
```

An accepted snapshot is the self-contained transition from nothing to one
retained accepted root, so its body carries only a format version and complete
objects:

```ts
type SnapshotBundle = {
  version: 1;
  objects: Uint8Array[];
};
```

The response uses `application/cbor` and is the canonical CBOR encoding of
exactly that map. Each member of `objects` is a CBOR byte string containing the
exact bytes of one object (raw file bytes, or a canonical CBOR directory,
page, table or rows object). Members are ordered
lexicographically by the SHA-256 hash derived from those bytes; hashes are not
repeated in the body.

The requested root in the URL identifies the graph and is not repeated in the
body. As the top directory object's hash, it transitively commits to every
reachable object. A client hashes every supplied byte string, rejects duplicate
hashes, requires the requested root to be a present canonical directory,
and walks its graph using the kind on each reference. A referenced directory,
page, table or rows object must decode canonically; file bytes are never decoded. A
hash referenced as two kinds in the same graph is invalid. It rejects missing reachable objects and
unreachable extras, stopping at nested-tree boundaries. The definite-length
`objects` array supplies the object count; the snapshot carries no tree or
accepted-update metadata.

The quoted `ETag` is the requested root. The bundle is a deterministic
encoding of the root's graph, so the root already names the body; a host
does not hash the response bytes again, and the ETag introduces no second
snapshot identity.

The server returns a snapshot only when the caller can currently read the
named tree and the requested root belongs to one of that tree's retained
accepted updates. Possession of a root is not authorization. Unauthorized,
unknown, wrong-tree, and no-longer-retained roots all return the same `404`
response, and no route enumerates historical roots or their accepted-update
metadata.

Snapshot responses carry
`Vary: Authorization, Overstory-Access-Link`. A response to a request carrying
neither header for a tree currently readable by `everyone` uses
`Cache-Control: public, max-age=31536000, immutable`; a response to a request
carrying either header uses
`Cache-Control: private, max-age=31536000, immutable`. A client may retain a
verified response indefinitely. A host need only answer a future origin
fetch while that accepted root remains retained.

Changing the current root or ACL does not change an already returned snapshot.
Revocation prevents a new authorized origin fetch but cannot retract bytes a
client or cache already received. In particular, a publicly cached accepted
root can remain publicly available after the tree ceases to grant public
access. Removing content from the current tree is therefore not erasure from
retained accepted snapshots or caches.

The objects a snapshot holds, and how each is encoded and hashed, are defined
in [data model §5](1.1-data-model.md#5-objects).

#### 1.1.3 Watching

```text
GET /.overstory/trees/{TreeID}/watch?after={update}
```

The request carries `Accept: text/event-stream`. `after` is the only resume
point: it names the accepted update the client last applied, and without it the
watch starts at the tree's current head. With `objects=none` the
host sends every frame without `objects` or `deltas`: a client that holds
only part of the tree (one that reads page by page, [§1.2.4](#124-reading-a-path)) learns the new
`update` and root and refetches only what it holds. Any other `objects` value
is `400 invalid-request`. A host ignores `Last-Event-ID`; a
client that reconnects opens a new watch with a new `after`. Servers may emit
an explicit `from` spanning intermediate accepted updates without client
negotiation; a frame per accepted update remains valid.

Successful state-change frames are `tree.update` events. Each represents one
or more accepted updates; derived hosting and device status does not appear on
this portable tree stream. `resync-required` is the terminal control event
described below.

A frame's SSE `id` is the accepted update it brings the client to
(`update.id`) and its `event` is its kind; the
`data` is the change alone, and says nothing the URL or the `id` already
says:

```ts
// id: AcceptedUpdate["id"]
// event: tree.update
type TreeUpdate = TransitionPayload & {
  update: AcceptedUpdate;
  from?: AcceptedRef;
  requestDigest?: Hash;
  access: "read" | "write";
  canonical: RemoteTreeDescriptor["canonical"];
};

type TransitionPayload = {
  objects?: ObjectBytes[];               // omitted: []
  deltas?: ObjectDelta[];                // omitted: []
};

type ObjectDelta = {
  base: Hash;
  result: Hash;
  instructions: Array<
    | { copy: [offset: number, length: number] }
    | { insert: string }
  >;
};

type AcceptedUpdate = {
  id: string;
  tree: TreeID;
  root: Hash;
  previous: AcceptedRef | null;
  acceptedAt: number;
  subject: string | null;
  conflicted: boolean;
};

// One accepted state of a tree: the update that produced it and its root.
// The descriptor, an update answer's `head` and a decision page spell the
// same pair as `update` and `root` members, with `conflicted` beside them.
type AcceptedRef = { update: string; root: Hash };
```

The two arrays are alternative transfer encodings for the result objects
needed to construct the candidate graph:

- `objects` carries a result object's complete canonical bytes.
- `deltas` carries instructions that reconstruct a result object's complete
  canonical bytes from an available base object.

For example, a transition that changes a large file and its parent directory
may carry the file as a compact delta and the smaller directory as a complete
object. After verification, both results are ordinary content-addressed
objects; how they travelled has no effect on the candidate tree.

Either array may be omitted, meaning empty, as in an update ([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)); a sender
never sends `null` for one. Every supplied result hash appears exactly once
across them. A transition that needs no new objects carries neither.

An `ObjectDelta` names an available object as `base` and the object it will
produce as `result`. Its ordered instructions build the result's complete
canonical bytes: `copy` reuses a byte range from the base, while `insert`
supplies new bytes as canonical padded base64. The receiver applies the
instructions and requires the produced bytes to hash to `result`.

Accepted update IDs are opaque strings; clients compare them only for equality
and take order from the `previous` chain, never from their spelling. The `previous`
link establishes accepted order within a tree; it is null only for activation.
It names both predecessor identity and projected root. A same-root semantic update
therefore advances the identity chain even when no new object bytes are required.
Rule execution, automatic resolution and restoration are provenance, not mutually
exclusive accepted-update kinds. Rule evidence is retained under the semantic
requirements in [updates and merging §3.5](1.3-updates-and-merging.md#35-format-aware-merge-rules).

The transition may carry complete `objects`, [deltas](1.3-updates-and-merging.md#13-sparse-transfer-with-object-deltas),
or both. Its transport basis is `from` when present, otherwise `update.previous`.
`from` names a retained accepted identity and root in the same tree, preceding
`update` in accepted order. It permits one net transition across several accepted
updates. `update.previous` always remains the actual historical predecessor;
coalescing delivery does not rewrite accepted history.

A frame carries exactly one transition: its `update`, `from` and payload. Its transport basis must match the
client's confirmed accepted identity and root, and its `update.tree` must be
the watched tree. A mismatched basis requires resynchronization, not a
successful root-only check. The payload must suffice to reconstruct the
destination graph from its transport basis without fetching or applying
intermediate transitions. The tree's new descriptor is the client's own
(`id`, `kind`) with the frame's `access`, `canonical`, `update.id`,
`update.root` and `update.conflicted`; nothing in a frame restates them.

On reconnect, authorities should normally coalesce a retained backlog into one
net transition to the captured current accepted state. Intermediate updates,
including same-root updates, need not be delivered individually. The destination
still carries its exact accepted identity and unresolved-state signal, even when
its root equals the starting root. Clients may materialize the final state once
and durably advance their accepted update.

One frame can span several accepted updates, through `from`; its `id` is the
last of them. A client that reconnects watches after the update it last
applied. A frame whose transport basis is not the client's confirmed update
is not applied (above), so an overlapping replay cannot apply old transitions
to a newer head.

A frame's `requestDigest` is present only when the stream is authenticated as the device (or execution token) that submitted that accepted request, whichever of its sessions it uses. This allows watchers to identify the revision that includes an update they sent.
A digest on a net transition identifies the request for its destination accepted
update, not every request accepted within the span. An absent or different digest
therefore does not prove that a pending request was excluded. Clients preserve
unconfirmed requests and use the ordinary exact-retry/receipt procedure to settle
them; advancing past an update on the watch alone never acknowledges those requests.

When retained context cannot support either net catch-up or ordinary replay,
for example because the `after` update or its basis graph is no longer retained,
or when catch-up would cost more than a snapshot, the server produces one
terminal `resync-required` event, with no `id` and `data` of
`{ "reason": string }`, and closes. `resync-required` means only that: a
snapshot will serve where catch-up does not. The client reads a new current descriptor,
obtains its addressed snapshot, and resumes strictly after the descriptor's
`update`. This catch-up path does not acknowledge or discard
unconfirmed local edits: clients retain and reconcile them through the ordinary
update/retry path. Retained accepted history need not be deleted merely because
a watch uses snapshot catch-up.

When the caller's authorization is revoked (a session that expires or whose
device is revoked, or access to the tree withdrawn), the server closes the
stream without an event. The client reconnects as after any lost connection,
and the host refuses that request as it would any other: `401` for a
credential that no longer authenticates, `404` for a tree the caller can no
longer read.

#### 1.1.4 Accepted unresolved state

`AcceptedUpdate.conflicted` and `RemoteTreeDescriptor.conflicted` signal that
an accepted state retains unresolved alternatives. The field is required; a descriptor and its accepted update MUST agree. This state is distinct
from a rejected update's structured `409 conflict` response. The selected `root`
remains an ordinary valid directory graph with no conflict markers or special
entries. An accepted change to unresolved state MUST receive a new update id
even when the predecessor root equals `root`; its transition may be empty.
Clients MUST durably advance accepted metadata in that case.

Ordinary updates are based on the exact accepted update, not only its projected
root. Leaving a conflicted region's projected bytes unchanged MUST NOT resolve
or discard its alternatives. Authorities MUST preserve unresolved state when admitting ordinary changes.
Representable ambiguity is accepted under the reconciliation contract; invalid
claims, failed guards and exceeded limits remain explicit failures. Clients without conflict-review support may
continue ordinary synchronization and MUST indicate unresolved state rather
than reporting the tree as conflict-free.

[Source intent and provenance](1.3-updates-and-merging.md) defines operation identities,
alternative edits, format-aware explicit automatic resolution, and continued
editing of accepted decisions on the ordinary update route. The
[working trees contract](2.1-working-trees.md#6-accepted-conflicts-and-held-local-work)
requires safe independent work to continue around held changes without rewriting
an immutable request or changing sequential prefix semantics.
These semantics require no extension negotiation or parallel API version.
Unknown optional response fields remain ignorable; unknown mutation semantics
must be rejected before accepting any part of their request.

### 1.2 Other ways to read trees

#### 1.2.1 Reading an object at a time

Clients that do not retain a whole tree can use this endpoint to fetch files
and directories on demand.

```text
GET /.overstory/trees/{TreeID}/objects/{hash}
```

This route returns the same object bytes carried in a snapshot bundle
or an `objects` array, but directly as the response body. The hash is present in
the URL and repeated as the quoted ETag. The response uses `application/octet-stream`,
must hash to the requested value, and uses the same access-sensitive `Vary` and
`Cache-Control` policy as an accepted snapshot.

A new origin fetch is authorized by read access to the named tree. Objects are
content-addressed and shared across a host, so the route does not prove that
the hash is reachable from that tree: any retained object whose hash the caller
knows is returned, and an unknown hash or an unreadable tree is `404`. Knowing a
hash is therefore treated as knowing its content; this route is a per-host
existence oracle gated by any tree read, and a host that must not confirm
content across trees needs a stricter deployment policy. Root hashes of
unreadable trees are never disclosed by any read, and a tree-boundary entry
carries only the nested TreeID.
A client may use it to refetch one missing or corrupt object of a
retained root instead of downloading a complete snapshot. Because objects are immutable and addressed by their bytes,
successful responses can be cached and reused after verification.

#### 1.2.2 References and selectors

```ts
type Ref = (
  | { path: string; object: Hash }                           // basis material
  | { change: string; operation: string }                    // an operation's result
  | { update: string; conflict: string; alternative: string } // an alternative
) & {
  within?: string[];
  range?: [number, number];
};
type EntryDestination = { parent: Ref; name: string };
```

Change, operation, conflict and alternative keys are 1–128 ASCII letters, digits,
underscores or hyphens.

A reference's kind is told by its keys, as a directory entry's is: `path`
and `object` name *basis* material, `change` and `operation` an operation's
result, and `update`, `conflict` and `alternative` an alternative. A reference
carrying keys of two kinds is invalid.

All references are scoped to the addressed TreeID and remain subject to current
authorization. On reads, a basis reference names the exact object at a logical path in the
requested accepted state. On writes, it names that object in the element's authored
basis. For the first element this is the accepted state at request `base`;
for later elements it is the preceding submitted candidate together with its authored
semantic effects, not merely its root hash. Paths are NFC, absolute and at most
4096 UTF-8 bytes; `/` is permitted to reference the tree root or a destination parent.
Other paths have no trailing slash, empty/dot components, backslashes or NUL.
Root material cannot itself be moved, removed or replaced as an entry.

An operation reference names a retained material result. On writes, it may also name the result
of an earlier operation in this change or submitted prefix. Forward references, cycles and references to an
operation with no material result are invalid. An operation result is not a backend
graph ID and does not inherently create a new origin. The host retains its
immutable binding and the provenance needed to transport selections through later
changes. Missing history requires an explicit failure, never fuzzy text matching.

An alternative reference names material in an exact retained accepted `update`. Update IDs are
opaque, nonempty strings of at most 1024 UTF-8 bytes. Conflict and alternative IDs
come from the host. The update identifies the reviewed alternative revision;
bytes, display order and current paths cannot substitute for identity.

Omitting selectors means the complete material. A nonempty `within` array selects
a descendant of directory material using names at the identified basis/result/state,
not current path lookup. Components obey the path-name rules, have a combined
slash-joined length of at most 4096 UTF-8 bytes, and number at most 256. A `range`
then selects text in that material or descendant: two nonnegative safe integers
(`<= 2^53 - 1`) defining a half-open UTF-8 byte range on scalar boundaries. A
zero-width range is an insertion point. No range means the entire selected text
for source operations and the entire selected entry for entry operations. Applying
text ranges to binary or directory material is invalid. Entry references cannot
have ranges. Logical boundaries never grant access to another TreeID's interior.

The host resolves the identified selection before transporting its identity
through changes; it MUST NOT retarget by matching current names or bytes. For an
entry destination, `parent` identifies a directory and `name` is one NFC component.
The authored destination slot, including its observed occupant or absence, is part
of the basis. Concurrent moves or occupants are reconciled rather than overwritten.
Text insertion uses `at: Ref` and `side: "before" | "after"` at the selected edges.

Editors open ordinary source with its accepted update and file hash. They need no
per-character identity map or provenance graph. Format-aware analysis may map blocks,
keys or symbols to exact source; it does not introduce a separate identity namespace.

#### 1.2.3 Reading conflicts

`GET /.overstory/trees/{tree}/conflicts?update={acceptedUpdate}` lists decisions in an
exact retained accepted state. Optional `after` continues an opaque page token;
optional `conflict` selects one decision. Each query field occurs at most once;
`update` is required, nonempty and exact. `after` and `conflict` are mutually exclusive.
The host authorizes every read, including continuation pages. Unknown or
unauthorized trees, unavailable states and unknown selected decisions return `404`;
malformed or mismatched page tokens return `400`. A page token is bound to tree,
accepted state and traversal position, never an authorization grant.

```ts
type DecisionPage = {
  tree: TreeID; update: string; root: Hash; conflicted: boolean;
  decisions: Decision[];
  next: string | null;
};
type Decision = {
  id: string;
  kind: string;
  affected: Ref[];
  selected: string;
  row?: { model: Name; key: string; field: Name | null };
  property?: Name;
  alternatives: Array<{
    id: string; revision: string;
    value: { text: string } | { file: Hash } | { directory: Hash } | { page: Hash }
         | { tree: TreeID } | { absent: true } | { value: JSONValue };
    placement?: EntryDestination;
    contributions: Array<{ change: string; operation: string | null }>;
  }>;
  dependencies: string[];
};
```

There is no fixed protocol cap on decisions, alternatives, dependencies,
contributions or aggregate inspection text. In particular, accepting the 33rd
unresolved decision is not an error. Page size is a transfer choice, never a limit
on accepted conflict state. Documented storage/resource constraints remain honest
implementation failures; a full response or absent automatic merge rule must not
be misreported as a resolved tree or an unsupported decision count.

`tree`, `update` and `root` must match the requested accepted context on every page.
`conflicted` describes the entire state, not just the current page. `next: null`
ends the traversal. A complete traversal yields each decision once in stable order,
with no omission or duplication. Pages remain at their original accepted state even
if current advances. A nonterminal page must make progress and return a different
continuation token; unavailable retained evidence requires explicit failure. A
resolved state has no decisions and no continuation. A filtered read returns the
one requested complete decision, with `next: null`; it does not claim to enumerate
all tree decisions. Clients cannot infer resolution from an empty partial result.

Each decision record contains its complete alternative and dependency sets; it is
not split into partial choices. Dependencies may name decisions on other pages.
The client may fetch those by `conflict` at the same update. Not appearing on this
page does not mean a dependency is missing or resolved. Before preparing a joint
resolution the client obtains the evidence required for the affected dependency
closure. Unrelated sync requires neither a complete traversal nor that closure.
The host still validates all guards and combinations at acceptance.

`affected` uses the same references as updates. A basis reference is
interpreted at the page's `update`. Absence decisions can address a destination parent
or retained material rather than inventing a nonexistent file path. Whole-entry,
placement and text selections therefore share the same identity vocabulary.
An alternative is addressed in a mutation by an alternative reference
using this page's update and its decision/alternative IDs. Its value supplies exact
text or the existing explicitly typed entry representation; `absent` represents
nonexistence. `placement`, when present, identifies the proposed parent and name
for an entry value, not a second independent copy. It is invalid for text or absence.

Decision and alternative IDs are stable across continuation. Revisions change when
value, placement, contributions or other meaningful alternative evidence changes;
earlier revisions remain associated with retained accepted states. Equal bytes do
not collapse alternatives. Contributions identify authored input rather than a full
transitive history download. Null `operation` explicitly denotes a snapshot input.
Selected identity must name an alternative. The host retains and verifies its
correspondence to the ordinary projection; clients validate exact source and placement
before attaching actionable controls. A text value must match the selected projected
UTF-8 range. A directory/file kind is never guessed from bytes. Unknown decision
kinds may be displayed as unavailable, but cannot authorize invented mutation
behavior. Core read fields may be extended without changing their meaning.

A `field` decision is a choice about one field of one row of a logical
collection ([updates and merging §3.6](1.3-updates-and-merging.md#36-merging-properties)).
`affected` names the collection's folder, and `row` names the model, the row's
canonical stable key and the field; `field: null` is a choice about whether
the row exists. Each alternative's `value` is that field's value, or the whole
row, with `null` for absent. A client resolves it by writing the chosen value
with row operations and declaring the resolution.

A `property` decision is the same choice about one property of a page.
`affected` names the page entry, `property` names the property, and each
alternative's `value` is that property's value, with `null` for absent. A
client resolves it with a property operation on the page
([updates and merging §2.5](1.3-updates-and-merging.md#25-property-operations)).

Entry-valued alternatives are read through the ordinary
[object route](#121-reading-an-object-at-a-time) by the hashes the decision page
discloses; the host retains them for as long as the state is retained.
Inline text requires no extra read.

Every decision can be resolved, and an alternative edited, with ordinary operations
and resolution declarations ([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)); a decision lists no actions. Requests remain
subject to current authorization and guarded evidence.
Optional offline inspection caching does not grant current-state authority.

IDs and references use [§1.2.2](#122-references-and-selectors) syntax. Decisions, alternatives, dependencies and
contributions must be unique within their stated scopes; dependencies cannot refer to
self but cycles between decisions are permitted. Empty alternative sets, invalid
selected IDs, malformed references and invalid values fail decoding. Open decisions
have at least two alternatives. Responses are private and must not be stored by shared
HTTP caches. The [target read vectors](conformance/protocol-accepted-state.json) bind
paired TypeScript and Swift models; they do not assert server execution.

#### 1.2.4 Reading a path

```text
GET /.overstory/trees/{TreeID}/snapshots/{root}/path/{logical path}
```

A path read gives a client that opens a tree page by page what it needs to
show and edit one node, in one round trip: the directory objects from a
retained accepted root down to the node, and the objects of the entries the
node is made of. The body is a snapshot bundle ([§1.1.2](#112-reading-an-accepted-snapshot)) in its exact shape,
`{ version: 1, objects }` in hash order, holding exactly these objects:

- every directory from `root` down to the parent of the path's last
  component;
- for the last component `x`, the objects of the entries named `x` and
  `x.md` in that parent, and, when one of them is a directory, the object of
  its `_index.md` entry;
- for `/`, the root directory and its `_index.md` object.

The path is a logical path ([locators §3](1.6-locators.md#3-parsing-and-canonicalization)), each segment percent-encoded once;
`x.md`, `x/` and `x/_index.md` read the same objects as `x`, and a file is
read by its own name, such as `photo.bin`. A segment that decodes to one
holding `/`, or a path that escapes the root, is `400 invalid-request`.

A component that names no directory, or a nested tree's boundary, ends the
walk: the bundle then holds the directories down to the deepest one that
exists, so the reader sees from that directory's entries that the node is
absent or belongs to another tree, without a second request. The reader
decodes the bundle, walks the same path from `root` through it, and rejects
a bundle that lacks an object the walk reaches or holds one it does not.
`protocol-path-reads.json` fixes the walk.

Access, `404` for an unknown or unretained root, `Vary` and `Cache-Control`
are those of the snapshot read; the root and the path together name the
body, so it is as immutable as the snapshot. Its quoted `ETag` is the root
followed by the normalized path, each segment percent-encoded once as in the
URL, such as `"sha256:…/Trips/Caf%C3%A9"`.

## 2. Encoding details

### 2.1 Stream framing and errors

Tree watch, query result and [§3](#3-presence) streams use one UTF-8 SSE framing rule: blank lines
separate frames, multiple `data:` lines join with newlines, and clients ignore
comments and keepalives. A host sends a comment as soon as a watch opens and
at least every 30 seconds while it is idle, with no request header to ask for
them, so a client may treat a longer silence as a lost connection. The `event` field names the typed event and `data` is
one canonical JSON value. Producers share escaping, cancellation,
bounded-buffer, and terminal-close behavior.

Each stream defines its own events: a tree watch in [§1.1.3](#113-watching)
(the accepted update in the SSE `id`, the kind in `event`, the change as
`data`, resuming from `after`), a query stream in
[apps and views §12.1](4.1-apps-and-views.md#121-evaluate-and-stream-views) (no `id`; fresh derived
state is established with `ready`, and reconnection repeats the complete
query), and presence in [§3](#3-presence). The shared framing implies
no shared cursor semantics.

The shared error envelope and common codes are normative. Narrow server-only
codes include `already-claimed`. Base/update mismatch,
reserved boundaries, policy failures, and merge conflicts use `conflict` with
discriminated `server-update` or `tree-configuration` details where
applicable.

### 2.2 Request and response encodings

A request that carries objects — `POST /.overstory/trees/{TreeID}/updates` and the
account claim, `PUT /.overstory/accounts` ([accounts and devices §1.2](3.1-accounts-and-devices.md#12-claiming-an-account-with-the-profile-key))
— and the success response to it travel as JSON or as CBOR. The encoding is
chosen by ordinary HTTP content negotiation, never required:

- A client sends `Content-Type: application/cbor` for a CBOR request body and
  `Accept: application/cbor` for a CBOR success response. Without them the
  body and the response are JSON (`application/json`). A host accepts and produces both; a client may use either, and may mix
  them (a CBOR request with a JSON response, or the reverse).
- A CBOR body is the canonical CBOR ([data model §7](1.1-data-model.md#7-cbor-and-hashes)) of exactly the value the JSON body
  would carry, with a byte string wherever JSON carries padded base64: each
  member of `objects` and an object delta's `insert`. In CBOR, `objects` is
  therefore exactly a snapshot bundle's `objects`. Keys, nesting,
  `null`, and the rules for optional fields are unchanged. There is no second
  schema.
- A receiver decodes canonical CBOR only. A non-minimal length, an indefinite
  length, map keys out of canonical order, a float where an integer belongs,
  or text where a byte string belongs is an invalid request (`400
  invalid-request`); a client refuses such a response.
- Error envelopes ([§2.1](#21-stream-framing-and-errors)), a `409` conflict's included, are JSON on every
  route and in every encoding.
- A request's identity does not depend on its encoding. Request digests are
  computed over the intent, not the body ([updates and merging §1.2](1.3-updates-and-merging.md#12-results-conflicts-and-retry)), so a JSON and a CBOR
  submission of the same request are the same request: they share digests,
  receipts, and exact replay.

The tree watch ([§1.1.3](#113-watching)) stays JSON over SSE: SSE is text, and most frames are
small. Accepted snapshots ([§1.1.2](#112-reading-an-accepted-snapshot)) are already a canonical CBOR bundle.
The [`protocol-cbor-transport`](conformance/protocol-cbor-transport.json)
vectors give the CBOR bytes of every request, response, and claim vector,
and CBOR bodies a receiver must refuse.

## 3. Presence

Presence tells the readers of a tree who else is there: which page each
person, or each person's agent, is on, and where their caret is when two of
them share a page. It is the one deliberately ephemeral exception to
"multiplayer state comes from the tree": presence is never part of a tree,
its history, a watch or a snapshot, and a host keeps none of it across
restarts. A reconnect starts over.

### 3.1 Model

A presence **entry** exists while its stream is open. Being subscribed is
being present: opening the stream joins and closing it leaves. There is no
heartbeat, time-to-live or resume cursor.

```ts
type PresenceID = string;   // opaque, unguessable, valid only for its stream

/** `path` is the page's canonical node path, such as `/Groceries`. */
type PresencePage = { path: LogicalPath; stableKey: string | null };

/** UTF-8 byte offsets into the text whose SHA-256 is `source`: a page's body,
 *  or a file's bytes. */
type PresenceSelection = { source: Hash; anchor: number; head: number };

type PresenceAgent = {
  label: string;           // the agent's name, at most 40 characters, one line
  status: string | null;   // at most 140 characters, one line
  run: string | null;      // the run it is doing (§6), if any
};

type PresencePeer = {
  id: PresenceID;
  profile: TreeID;         // the person's profile, or the agent's person's
  name: string | null;     // the host's display name for the profile, if it has one
  page: PresencePage | null;
  agent: PresenceAgent | null;   // null for a person
  device: "mac" | "ios" | null;  // what the client says it runs on, if it said
  runner: string | null;   // a runner's label (§6), at most 40 characters, one line
};
```

1. **One roster per tree.** A subscriber sees every listed entry of the tree
   and the page each is on.
2. **Visible by default.** A device that asks not to be shown subscribes with
   `visible=false`: it receives the roster but is not in it. A caller
   authenticated only by an access link, or not at all, may subscribe if it may
   read the tree, but is never listed.
3. **Agents.** A stream opened with `agent=<label>` is an agent's entry, listed
   under the caller's profile and always visible. Only an agent's entry has a
   status. One person on two devices, or with several agents, appears once per
   stream.
4. **The host names people; clients colour them.** `name` is the display name
   the host holds for the profile, or `null` (for example for a placement
   account whose profile is homed elsewhere). A client derives a stable colour
   from `profile`. A presence ID never reveals a device ID.
5. **Device kind.** A client may say what it runs on with `device=mac` or
   `device=ios` when it opens its stream; a host ignores any other value and
   lists the entry with `device: null`, as it does when the client doesn't say.
   The kind is a hint for showing the entry and says nothing about which
   device it is. A client should not rely on it for an agent's entry, and
   treats a missing member or a kind it doesn't know as `null`.

### 3.2 Cursors

A cursor is a byte range in a named source: the text the sender is showing, by
the SHA-256 of its bytes (a page's body without its properties, or a file's
bytes), which may be a local edit not yet accepted. For a file this is its
object hash; for a page it is not, since a page object also holds properties. A receiver
showing the same object places it exactly. A receiver showing another version
may approximate it within its own version, but must not present the
approximation as exact; if it cannot map it, it does not show it.

Cursors are reciprocal and page-local: a cursor event reaches only visible
subscribers on the sender's page, and a hidden subscriber receives none. A
client sends cursor updates only while the roster shows someone else on its
page. Changing page clears the entry's selection; a receiver drops a peer's
cursor when the peer's page changes.

### 3.3 Routes

```text
GET  /.overstory/trees/{TreeID}/presence[?visible=false][&agent=<label>][&device=<kind>][&runner=<label>]
POST /.overstory/trees/{TreeID}/presence/{PresenceID}
POST /.overstory/trees/{TreeID}/presence/{PresenceID}/messages
```

The GET is a stream with the shared framing
([§2.1](#21-stream-framing-and-errors)),
with no `id` and no `after`. Its events, each `data` one JSON value:

| `event` | `data` | Sent |
| --- | --- | --- |
| `presence.ready` | `{ self: PresenceID \| null; peers: PresencePeer[] }` | First, once. `self` is the stream's own entry, listed or not, for a caller with an account (for updates and messages, [§3.3](#33-routes) and [§3.6](#36-runners-and-messages)), and null otherwise; `peers` excludes it. |
| `presence.peer` | `PresencePeer` | A listed entry joined, changed page, or (an agent) changed status. |
| `presence.cursor` | `{ id: PresenceID; selection: PresenceSelection \| null }` | Per [§3.2](#32-cursors). |
| `presence.leave` | `{ id: PresenceID }` | A listed entry's stream closed. |
| `presence.message` | `{ from: PresenceID; body: PresenceMessageBody }` | Per [§3.6](#36-runners-and-messages), only to the stream it names. |

A client rejects any other event. An agent stream requires an account; an
execution token may not open or change presence.

The POST body is a JSON object with any of `page`, `selection`, `status` and
`run`; an omitted member leaves its value unchanged, and an unknown member is
refused. `status` and `run` are accepted only on an agent's entry. The POST is accepted
only from the caller (account and device) that opened the stream, and only
while it is open; any other request, including one naming a page the caller
cannot read, is answered `404`, the same as a missing entry, so a presence ID
is not a credential. Success is `204`.

### 3.4 Access

Presence streams are admitted and kept as watches are
([access control §3.3](3.2-access-control.md#33-watches-and-revocation)): the
caller must be able to read the tree, the stream ends when that stops, and
an entry is never disclosed outside what a subscriber may read. Opening,
changing and leaving an entry is not an update and changes nothing in the
tree.

### 3.5 Bounds

- A client SHOULD send at most 4 cursor updates a second, coalescing to the
  latest.
- A host keeps only an entry's latest page, selection and status, and only
  the latest pending event about each peer for each subscriber; a subscriber
  that falls far behind MAY be closed, and starts over on reconnect.
- A host MAY refuse a POST body over 1 KiB (`413`) and MAY answer `429` to a
  stream that changes faster than it allows.
- A selection's offsets are integers from 0 to 2³²−1.
- A host MAY refuse a message body over 4 KiB (`413`).

### 3.6 Runners and messages

A person can have tasks run for them by an agent somewhere else: a Mac that
is awake, a cloud session, a server. Whatever runs a task is a **runner**,
and every runner receives the same request:

```ts
type RunRequest = {
  tree: string;                     // the tree's canonical URL
  page: PresencePage;
  task: { text: string; range: PresenceSelection | null };  // in the sender's source, if known
  run: string;                      // chosen by the sender: one line, no spaces, at most 64 characters
};

type PresenceMessageBody =
  | { kind: "run"; request: RunRequest }
  | { kind: "stop"; run: string }
  | { kind: "done"; run: string; result: string };
```

- **A present runner** is a person's visible stream opened with
  `runner=<label>`; the roster shows it with that label while it is open. A
  hidden stream or an agent's cannot be a runner (`400`).
- **Messages** pass between one person's own streams. The messages POST is
  made on the sender's own entry, with `{ to: PresenceID, body }`; the host
  delivers it as a `presence.message` frame to that stream only, and keeps
  nothing. A sender may be a hidden stream. A message to a stream that is not
  open, or that another profile opened, is answered `404`, as a missing entry
  is. Success is `204`. A runner that receives `run` starts an agent that
  reports the request's `run` in its entry; `stop` asks it to stop; `done` tells
  the sender the result. A client that cannot run tasks ignores `run`.
- **Other runners** receive a run request some other way, such as an HTTP
  POST; it is the same `RunRequest`.
- A host that serves this states `protocol` 2 or more in its health
  ([locators §5](1.6-locators.md#5-finding-trees)).
