# Collections
*Part of the [Overstory spec](README.md), layer 1 (trees): a folder whose children are rows. What the tree holds for a collection, row identity and order, validation and merge. How a placement writes rows to files or SQLite is [placements on disk](2.2-placements-on-disk.md); Query and transaction semantics belong to [reading and watching §4](1.2-reading-and-watching.md#4-views).*

A folder whose entries include `schema.beetle` is a collection. Its rows are
logical state whose history the tree holds as a log ([§1](#1-what-the-tree-holds)), in the canonical form of [§2](#2-rows-and-values), and
every file or database that shows them is one placement's
[projection](2.2-placements-on-disk.md#4-projections) of that state. Two placements of one tree may
project a collection differently, and both hold the same rows and the same
root.

The folder's `schema.beetle` is its [schema](1.5-beetle.md#5-a-collections-schema), held as an
ordinary authored file entry with exact bytes. `_index.md` and other
ordinary files in the folder stay ordinary entries and pages: the folder is a
page that has a logical collection. The rows of the schema's
[`main` table](1.5-beetle.md#21-tables-and-fields), if it has one, are
the folder's logical children. Every other table with data rows is a logical
child named after its table, whose children are that table's rows.
Rows have no children; a subpage of a row belongs in a separate
folder that links to it.

Interpreting a collection never executes authored code. The schema is data: a
conforming implementation parses and checks it under the language's finite
limits and validates rows against it without inserting defaults or
transforming values. The schema is the whole contract for a collection's
rows: anything a projection holds that the schema doesn't declare, such as an
extra CSV column, JSON key order or a comment in a Markdown row's front
matter, is that placement's own and does not cross to another placement.

## 1. What the tree holds

```text
Entries below /games:
  _index.md   → indexHash        (an ordinary page)
  schema.beetle  → schemaHash
Collection of /games:
  modelFingerprint
  log → entry → entry → … → snapshot entry → SQLite file
Logical children below /games (Game is the main table):
  chess, go
  List/favorites
```

A collection's rows are held once, by its host, in a database; the tree holds
the collection's **log**: its accepted row changes, in order. The directory
object's `collection` reference and the log's objects are defined in
[data model §5](1.1-data-model.md#5-objects). The reference names the log's head
entry. Each entry names the one before it and holds either the row changes of
one accepted update or a snapshot:

- A **changes** entry lists each row the update changed, once, as its whole
  new [§2](#2-rows-and-values) form, or as removed. Its rows are the previous
  entry's rows with these applied. Merging has already happened when an entry
  is written ([§4](#4-accepted-update-validation-and-merge)): an entry holds
  outcomes, never authored operations, and applying one needs no schema.
- A **snapshot** entry names a file object holding every row as of that
  entry: a SQLite database implementing the schema's
  [database layout](1.5-beetle.md#52-layout) under its own names, with no
  storage mapping. Its bytes are whatever the host's SQLite wrote; only its
  rows are compared. Only the tree's host writes snapshots, so every placement
  holds the same entries.

Every entry carries the **rows hash** and row count after it. The rows hash is
LtHash16 ([Lewi et al., 2019](https://eprint.iacr.org/2019/227)) over the rows:
each row contributes SHAKE256 of the canonical CBOR of `[model, row]`, 2,048
bytes read as 1,024 little-endian 16-bit lanes, and the state is the lane-wise
sum of every row's contribution modulo 2<sup>16</sup>. `rowsHash` is the
SHA-256 of the state's 2,048 bytes. A change takes out a row's old
contribution and adds its new one, so keeping the hash costs one contribution
per changed row, and any store can check it, since it is defined over rows,
not bytes. The empty collection's state is all zeros.

The collection's **logical hash** is the canonical CBOR hash of
`{ modelFingerprint, rowsHash }` from its reference and head entry. It is the
collection's contribution to the folder's model hash: the same for the same
rows, whatever history led there and however a placement holds them. The
root, as for any object, commits to the log itself.

An authority checks a log by applying it: from a snapshot entry, it opens the
file, reads its rows, and requires their count and rows hash to equal the
entry's; then it applies each later entry in order, requiring the same after
each. It also requires:

1. The folder's `schema.beetle` to parse and check under the language's
   limits, and `modelFingerprint` to equal the
   [schema fingerprint](1.5-beetle.md#53-fingerprints) it produces.
2. Every object to decode canonically, every changes entry to name each row
   at most once and only tables with data rows, and every removed row to be
   present.
3. Every row of the head state to validate against its table
   ([§2](#2-rows-and-values)), and every reference to name an existing row or
   enum value.

Then it exposes the head state's tables as the folder's logical children, and
preserves the `schema.beetle` file and other entries as ordinary authored
entries. A host accepting updates checks each new entry as it writes it, so a
full check is needed only for a log that arrives from elsewhere: a tree a host
takes over, or a backup restored.

### 1.1 Snapshots and history

Walking objects from a root reaches the log's head entry and every entry
before it back to the newest snapshot entry, and that snapshot's file: a
snapshot walk, a snapshot bundle and a copy of a tree all stop there, and need
no other route. A snapshot entry's `previous` may name entries the host no
longer keeps.

The host writes a snapshot entry when the changes since the last snapshot
outgrow the database, with no row changes and the same rows hash as the entry
before it, in an accepted update it makes itself with no other effects. A host
keeps entries and snapshots for its history budget. A collection may keep less
history than pages: reading a collection at a root whose state the host can no
longer rebuild from a snapshot it keeps answers `410 not-retained`.

A host advertises its row and entry quotas.

## 2. Rows and values

A row's [§2](#2-rows-and-values) form is a map with `key`, `fields`, `created` and `modified`:

- **`key`** is its table's key ([Beetle §2.4](1.5-beetle.md#24-keys))
  as an array of `[field, value]` pairs in key order. Its canonical key JSON
  is the row's stable key ([locators](1.6-locators.md#2-stable-keys-revisions-and-fragments)),
  immutable under an ordinary row update; changing it is removal of one row
  and creation of another. A row's logical name is its `path` field's value,
  which must be one valid logical `Name`; without one, the name derives from
  the key as [§3](#3-row-identity-and-order) says.
- **`fields`** holds every other declared field that has a value, by name.
  An optional field without a value and an empty many-valued field are
  absent, never `null` or empty.
- **`created`** and **`modified`** are Unix milliseconds in UTC, like a
  file or page entry's times
  ([data model §6](1.1-data-model.md#6-entry-times)). They are stamped from accepted operations' `at`, and
  never set directly ([updates and merging §2.5](1.3-updates-and-merging.md#25-property-operations)).

Values have one canonical form per type, so no projection's conventions
reach the tree: `Text` and `Markdown` are UTF-8 strings, `Int` is a CBOR
integer, `Number` is a number in canonical CBOR (an integral value is
encoded as an integer, so `1` and `1.0` are one value; the schema, not the
encoding, says which type a field has), `Bool` is a boolean, a `Date` is a date or a date-time tagged as in a page
property (tag 1004 around `YYYY-MM-DD`, tag 0 around an RFC 3339 date-time in
UTC), so rows and pages spell dates one way and a date is never a plain
string, a reference to a table's row is the target's key value (an array
of its pairs when the key has several fields), a reference to an enum is the
value's name, a `Person` is a profile TreeID, and a value array is an array.

Only tables' rows are addressable: `/games/Game/g1`, and a connection table's rows
too. A plain n:m connection is not a node set. It is a set of pairs held once,
as a field on the rows of one end: the `ordered` end, else the end declared
first. The other end shows it as a field derived from those pairs, and either
end's row operations change the same pairs. An `ordered` field is a sequence
of member keys, never position numbers. A 1:1 or 1:n connection is a
reference on its single side.

A row has no content outside its fields. A Markdown projection's body and
title are fields ([Beetle §5.1](1.5-beetle.md#51-layers-and-attributes)).

## 3. Row identity and order

- **Row identity.** A collection's declared primary key is the
  stable-key rule for its children. It must be stable, non-null,
  serializable, and independent of row position, SQLite `rowid`, display
  label, or query plan. A row's third reference component is its canonical key
  JSON as defined by
  [locators](1.6-locators.md#2-stable-keys-revisions-and-fragments); each key
  field's validated value must be a JSON string, boolean, or finite number.
  Key values are already in that form ([§2](#2-rows-and-values)). Changing a key is observed as
  removal of one child and creation of another. A row's logical child segment
  is its single string key when that is a valid nonempty logical path component
  not beginning with the reserved `~row-` prefix; otherwise it is `~row-`
  followed by the unpadded base64url encoding of the canonical row key. This
  is the one surface that still uses base64url rather than the locator key
  token; the rule is under review in
  [Postgres 001](../../plans/later/postgres-001-postgres-backed-collections.md#open-from-the-old-plans).
- **Ordering.** Collection-file and database rows enumerate in canonical stable-key
  order, falling back to canonical path, using the portable comparison; a
  backing's default collation is not an acceptable substitute. Where a
  relational extension supplies explicit ordering, the proved stable key is the
  deterministic final tie-breaker.

## 4. Accepted update validation and merge

An update changes a collection by row operations, which the host replays on
its basis rows; a client that does not encode a collection's tables leaves the
resulting roots out and the host derives them
([updates and merging §2.3](1.3-updates-and-merging.md#23-derived-candidates)). A snapshot
update (a `null` trace) that changes a collection is accepted only from a
caller allowed to `write` the collection's path, and its effects are the row
differences from its basis. The host validates all keys, references and
constraints, merges concurrent changes by
`collection-fields-v1` ([updates and merging §3.6](1.3-updates-and-merging.md#36-merging-properties)),
appends one changes entry with the rows the accepted update changed
([§1](#1-what-the-tree-holds)), and never trusts a client-supplied fingerprint
or hash. An update that changes no row appends no entry.

A merge conflict on a field becomes a decision scoped to that row field
([reading and watching §1.2.3](1.2-reading-and-watching.md#123-reading-conflicts)); a
merged result the schema rejects is a conflict on the collection's folder.
Changing the schema's data layer is a schema migration: the update carries
the new `schema.beetle` and the rows rewritten to it, is validated as a
whole, and its entry is a snapshot.

## 5. Value validation and limits

Validation is a pure decision over one row. A row matches its table when
every required field is present, every value has its field's type and arity
([§2](#2-rows-and-values)), every reference names an existing row or enum value, and `unique`
fields are unique. Diagnostics name a stable code (`type-mismatch`,
`missing-member`, `no-matching-choice`, `invalid-text`, `budget-exceeded`)
and the failing field, in the order fields are declared. The
[`collection-schemas.json`](conformance/collection-schemas.json) vectors bind
this section.

[Beetle's limits](1.5-beetle.md#7-limits-and-diagnostics) apply to the
schema. Validating one row takes at most 1,000,000 steps (values visited plus
map members examined), and one collection at most 50,000,000; exceeding
either rejects the row or the update with `budget-exceeded` naming
`row-steps` or `collection-steps`. The quotas of [§1.1](#11-snapshots-and-history) apply in addition.
