# Authoring API
*Part of the [Overstory spec](README.md), layer 5 (apps): the `overstory/data` and `overstory/ui` packages views and mutations are written against. This is a library contract versioned with those packages; the execution model it exposes is defined by [executable documents](5.1-executable-documents.md).*

*Owns: the `overstory/data` and `overstory/ui` exports. References: [executable documents](5.1-executable-documents.md) for every semantic guarantee, and the UI language ([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)) for the view tree's vocabulary.*

Package names are part of the authored portability surface: a compatible runtime provides these two modules with these exports, so the same source runs anywhere the [execution model](5.1-executable-documents.md#11-portability-and-limits) allows.

## 1. Packages

`overstory/data` is authoring for data and handles: `node(path)` logical node sources, schema-derived children handles with `.all` and `.one`, `view`, facts (`or`, `not`, `rule`), `mutation`, `publicError`, `RowOf`, and `ResultOf`.

`overstory/ui` is the JSX runtime and the UI language's components, among them `Markdown`, `Button` and `Form`. There is no React: no hooks, Suspense, or React Actions.

## 2. Views

A view ([executable documents §4.1](5.1-executable-documents.md#41-views)) is a function
from validated input and the user to JSON or a view tree, made with `view`. A file's
default export is its linkable view ([executable documents §1](5.1-executable-documents.md#1-views-and-their-addresses));
named exports are imported:

```tsx
import { node, or, rule, view } from "overstory/data"
import { z } from "zod"

// Components (Shell, PracticeGrid, ListGrid), row types and sorting helpers are omitted.
const List = node("./data/List").children
const Person = node("./data/Person").children
const Practice = node("./data/Practice").children

// Who may see a list is a read rule on the List model, which the host applies to every
// read (executable documents §4.1). Views don't repeat it. `rule` is for an app's own
// reusable facts, such as this one:
const curatedBy = rule<{ l: ListRow; person: PersonRow }>(({ l, person }) => [
  or([l.owner.is(person)], [l.contributors.person.is(person)]),
])

// A data view: JSON, drawn by a client's default renderer when it has no code of its own.
export const list = view(z.object({ id: z.string() }), ({ id }) => {
  const l = List.one(l => [l.id.is(id)])
  if (!l) return null
  return {
    name: l.name,
    about: l.about,
    practices: sorted(l.items, byPosition).map(i => ({
      id: i.practice.id,
      name: i.practice.name,
      tags: i.practice.tags.all(t => [t.list.is(l)]).map(t => ({ name: t.name, color: t.color })),
    })),
  }
})

// A JSX view: the same reads, drawn. Components take rows and read what they show.
export const ProfilePage = view(z.object({ id: z.string() }), ({ id }) => {
  const person = Person.one(p => [p.id.is(id)])
  if (!person) return <Shell title="Profile not found" />
  return (
    <Shell title={person.name}>
      <PracticeGrid practices={sorted(Practice.all(p => [p.authors.has(person)]), byName)} />
      <ListGrid lists={List.all(l => [l.items.practice.authors.has(person)])} />
      <ListGrid lists={List.all(l => [curatedBy({ l, person })])} />
    </Shell>
  )
})
```

Input comes from the query string ([executable documents §1](5.1-executable-documents.md#1-views-and-their-addresses)),
validated by the view's Standard Schema-compatible input schema. Zod is supported
directly, without an Overstory-specific validator vocabulary. A view with no input
omits the schema.

The view tree is plain `{type, props, children, key}` data built by the JSX runtime.
The vocabulary of view types, controls, local state and styling is the UI language
([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)); a client draws it natively
or as HTML.

`Markdown` renders a Markdown source string with Overstory's ordinary link resolution,
safe URL and asset policy, and source semantics. It is the standard way for a view to
present stored Markdown.
It resolves a relative Markdown destination from the directory holding the
source file, as [locators §2.1](1.6-locators.md#21-links-written-in-markdown)
defines. For a destination carrying the reserved `#overstory-key=` alias, it emits
the equivalent server-visible path suffix and preserves the authored
application query. It does not forward the reserved identity alias as an HTML
fragment.

`RowOf` and `ResultOf` expose the types the development compiler infers from declared property and child schemas, so authored source maintains no second result schema.

## 3. Mutations

`mutation` accepts an optional Standard Schema-compatible input schema. The mutation's
call input is the schema input type; its handler receives the validated, transformed
output. Validation occurs before data access.

Views and mutations declare `authority: { author: [...], user: [...] }`.
Requirements identify resolved source handles and operations, not credentials or
arbitrary authority-bearing strings supplied by callers. Both parties' requirements
are checked separately, then their granted capabilities combine for execution.
Expansion beyond existing resource rules requires renewed consent; module/export
renames within a code TreeID do not discard grants. Omission never confers ambient
authority. Ordinary caller read permission, including `everyone`, works through code.

The following is illustrative authoring syntax; [Apps 006](../../plans/later/apps-006-durable-authoring.md)
freezes the exact overloads, resource-selection typing and step API using the Supplies
corpus before implementation. The previous `permission()` and `{ requires }` forms
are superseded, not compatibility obligations.

```ts
export const savePractice = mutation({
  input: inputSchema,
  authority: {
    author: [practices.read(), saves.create()],
    user: [notebook.createChildren()],
  },
  async run({ input, user, step }) {
    const prepared = await step("prepare", () => database.transaction(async tx => {
      const practice = await tx.practices.get(input.practiceID)
      return tx.saves.prepare({ practice, user })
    }))
    const page = await step("page", () => notebook.create(prepared.page))
    return page
  },
})
```

Runtime handles choose their provider through the host's provider bindings, after their locators resolve by the ordinary [resolution rules](1.6-locators.md#4-resolution-rules).
Single-domain handlers retain an implicit runner-owned transaction where declared;
multi-domain handlers use explicit transaction blocks and stable durable steps.
Straight-line handle calls may receive compiler-generated stable steps; loops,
branches or dynamic repetition require explicit keys where stability is not proved.
The runtime owns receipts and deterministic IDs; authors do not implement receipt
or outbox tables. A transaction callback is one atomic step, not a sequence of
independently replayed row writes. Throws roll back only the active transaction.

## 4. Actions and forms

Calling a mutation without `await` gives an **action value**, which `Button action=` and
`Form action=` take. `handle.with({…})` adds input, and `.then(result => link)` names
where to go after it succeeds. A client runs the action, supplying a stable mutation
identity, and exposes a typed result, durable receipt, or sanitized public error.

Form conversion is shallow and deterministic: a name occurring once becomes its string
or file value, a repeated name becomes an array in document order, and an omitted name
is absent. Coercion belongs to the authored schema. Expected failures use
`publicError(code, message, options?)`; other thrown values become a generic internal
error without stack traces, SQL, paths, or private row data. Expected errors have
stable codes, safe messages, retryability, and optional field errors.

`mutation.for(Model, "create" | "edit" | "delete" | "move")` declares a mutation as that
model's row action, so any list of the model offers it.

## 5. User

A view receives the optional safe Overstory user projection as `{ user }`, its second
argument. A plan may dereference the nullable-safe symbolic `user.profile`, or use
`user.required.profile` to declare that anonymous execution must fail before data
access. An authored tree never receives credentials or implements authentication.
