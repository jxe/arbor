# Updates and merging
*Part of the [Overstory spec](README.md), layer 1 (trees): the update route; authored changes, their traces and operations; and how a host accepts, merges and resolves them. There is one target contract, with no API version or negotiation.*

Every update, guard, retry receipt and read is subject to
[current authority](3.2-access-control.md#3-tree-scoped-authorization), checked over its actual effects.

## 1. The update request

```text
POST /.overstory/trees/{TreeID}/updates
```

The client submits a nonempty, ordered string of candidate updates against the
last accepted watchpoint it has confirmed. The request travels as JSON or as
canonical CBOR of the same value
([request and response encodings](1.2-reading-and-watching.md#22-request-and-response-encodings)); the
examples here are JSON:

```ts
type UpdateRequest = {
  base: string | null;
  updates: CandidateUpdate[];
};

type CandidateUpdate = {
  change: string;
  at: string;                            // RFC 3339 UTC, millisecond precision
  candidate: Hash | null;
  trace?: Frame[] | null;                // omitted: null, snapshot semantics
  resolves?: ResolutionDeclaration[];    // omitted: []
  ifCurrent?: string;
  objects?: ObjectBytes[];               // omitted: []
  deltas?: ObjectDelta[];                // omitted: []
};
```

Each element is one authored change ([§2.1](#21-the-change)).

`base` is the id of the accepted update and `tree.update` watchpoint from which
the string begins, or `null` when its first element activates a reserved tree.
Each element proposes one distinct accepted-history boundary. The first is
authored on the root at `base`; every later element is authored on the preceding
element's submitted `candidate` together with its authored semantic effects, whether
or not that candidate has received a host response. Root equality never
collapses the semantic basis of two elements.

A client usually coalesces a burst of editing into one element and keeps one
request in flight ([working trees](2.1-working-trees.md)), but it may submit
progressively longer strings without waiting for an earlier answer, and the
host accepts them: that is the recovery path once a request has become
ambiguous. These two may be in flight at once:

```json
{
  "base": "248",
  "updates": [
    {
      "change": "change-one",
      "at": "2026-11-11T09:30:01.000Z",
      "candidate": "sha256:1111111111111111111111111111111111111111111111111111111111111111"
    }
  ]
}
```

```json
{
  "base": "248",
  "updates": [
    {
      "change": "change-one",
      "at": "2026-11-11T09:30:01.000Z",
      "candidate": "sha256:1111111111111111111111111111111111111111111111111111111111111111"
    },
    {
      "change": "change-two",
      "at": "2026-11-11T09:30:02.000Z",
      "candidate": "sha256:2222222222222222222222222222222222222222222222222222222222222222"
    }
  ]
}
```

Within one client epoch, every later request keeps the earlier elements
exactly and only appends; only their objects and deltas may be sent
differently. A client never rewrites an element's change, trace, candidate,
resolutions or precondition, and never forks two successors from one prefix.
It starts a new epoch, with a new `base`, only once the whole string has been
acknowledged and its result durably applied.

The host serializes update strings per tree. Before processing new work,
it finds the longest supplied prefix already represented by successful
device-scoped request digests in accepted history and trims that prefix.
If the longer request arrives first it may apply every element; if a shorter
request arrives first the longer request resumes after it; an old shorter
request arriving last changes nothing. A previously returned `unchanged` element
need not have its own durable resolution record: a later accepted element
proves its prefix was processed, while an otherwise unresolved `unchanged`
element may be evaluated again without creating accepted history.

For each untrimmed element, the logical base root is the preceding submitted
candidate (for a derived candidate, the root the host derived), not the preceding
accepted or merged root. An element that follows a derived candidate in the same
string is in practice derived too, because its author has not seen the root it
builds on; other work waits for that element's result and is replayed onto it
like any accepted change. Thus, if `B` to `C1` is
merged into `M1`, the next element is reconciled as `(base: C1, candidate: C2,
current: M1)`. Only the incremental `C1` to `C2` change is applied to the
merged state. Each successful state-changing element is committed and emitted
on watch separately. A rejection stops the string at that element; its
successful prefix remains accepted and later elements are not attempted. An accepted
unresolved decision is a successful result and does not stop the remaining string.

Each `candidate` names the exact Overstory root encoding the desired complete tree
state. The host decodes and validates its modeled state and all
projection-specific fidelity required by that encoding. Each element may omit
objects available from the preceding graph, but the complete request must be
self-contained from its retained accepted `base` plus its `objects` and valid
`deltas`. The host may reconstruct an already-applied prefix from the
repeated request instead of retaining its submitted candidate graph. The
[delta rules](#13-sparse-transfer-with-object-deltas) define interchangeable
transfer representations; they do not change a candidate's identity.

### 1.1 Request identity

The host derives a device-scoped request digest for each element: the SHA-256 of the
[canonical CBOR encoding](1.1-data-model.md#7-cbor-and-hashes)
of `{ domain: "overstory-update/1", tree, base, change, at, trace, candidate, resolves, ifCurrent }`,
with absent `ifCurrent` encoded as CBOR null, an omitted `trace` as CBOR null,
an omitted `resolves` as an empty array, and a derived candidate's
`candidate` as CBOR null. Omitting a field and sending its default therefore
give the same digest. Execution is deterministic (an update and each row operation carry their
`at`), so a retried derived candidate derives the same root under the same digest. The digest covers the whole trace,
including each frame's `before` and `after` as stated or omitted, so the same operations divided into
different frames are a different change. Ordered arrays retain their submitted
order, including resolution declarations and reviewed alternative IDs. Identity is
scoped to the authenticated device, across its sessions.
For the first element, `base` is the request's accepted update id or `null`.
For each later element, `base` is
`{ requestDigest: previousDigest, candidate: previousCandidate }`, where a
preceding derived candidate's `candidate` is null. This latter
object is part of semantic identity but is implicit in the ordered JSON request. Consequently every digest
commits to the complete prefix, and the same prefix has the same identities in
every longer request.
`objects`, `deltas`, their ordering, and the body's
[encoding](1.2-reading-and-watching.md#22-request-and-response-encodings) are
transport choices and are excluded, so an ambiguous retry may send complete
bytes for a delta, or CBOR for JSON, as the same request. An exact retry of an
accepted element replays its original result and creates no second update; an
`unchanged` element may be evaluated again.

Three tokens that serve different purposes are often encountered together:

- An accepted-update `id` identifies one durable accepted transition of one tree.
  Its predecessor link gives accepted order, and a watch resumes after it.
- A client-authored `change` identifies an immutable authored change; operation
  material results are named by that change and their operation keys, without an
  independently named output. A moved result retains existing origins.
- A device-scoped `requestDigest` identifies one canonical update
  semantic request across retries and different object/delta packaging.

### 1.2 Results, conflicts, and retry

A successful response is always plural and contains one result for every
element, including any element trimmed as an exact replay. It is JSON, or CBOR
when the request asked for it; a rejection is always the JSON error envelope
([request and response encodings](1.2-reading-and-watching.md#22-request-and-response-encodings)):

```ts
type UpdateResponse = {
  results: UpdateResult[];
  head: UpdateHead;
};

type UpdateHead = {
  update: AcceptedUpdateID;
  root: Hash;
  conflicted: boolean;
};

type UpdateResult = {
  outcome: "unchanged" | "accepted";
  update: AcceptedUpdate;
  requestDigest: Hash;
  candidate?: Hash;            // derived candidates only
  reconciliation?: TransitionPayload;
};
```

`results` is nonempty and preserves request order. HTTP status is `201` if at
least one result is `accepted`, including replay of a previously accepted result;
otherwise it is `200`. `unchanged` means no semantic transition was committed for
that element. `accepted` includes direct application, reconciliation, restoration
and metadata-only changes. How a result was produced is recorded as provenance,
not duplicated in an outcome enum or accepted-state kind.

`update` is the accepted state standing after that element: existing state for
`unchanged`, or the newly accepted state for `accepted`. `head` is the tree's
current accepted state as the response was written, after the whole string was
processed; the client installs it without reading the descriptor and watches
after `head.update`. Exact replay returns the
original per-element receipt even if current has since advanced, so a
replayed string's last receipt need not be `head`. A rejected string carries
neither.

`reconciliation` is present exactly when the accepted root differs from the
submitted candidate: it is the transition from the candidate root to
`update.root` under the [deltas](#13-sparse-transfer-with-object-deltas) rules, so
a superseded, merged, or replayed result is applied with the same code that
applies a watch frame. A result whose projected root equals the candidate returns none, including
metadata-only acceptance. Its accepted identity still must be applied.

A derived candidate's result also carries `candidate`, the root the host derived,
and its `reconciliation` is the transition from the preceding result's
`update.root` (for the first element, the root at `base`) to `update.root`,
present whenever they differ. The client never held the derived candidate's
objects, so it applies the result as it applies a watch frame and drops the
operations from its pending queue.

A rejected reconciliation uses the shared error envelope
([reading and watching §2.1](1.2-reading-and-watching.md#21-stream-framing-and-errors)) with
`details.kind: "server-update" | "tree-configuration"`. Its details include
`completed`, the ordered successful prefix results; `failedIndex`; `head`,
the tree's current accepted state as an `UpdateHead`, exactly as a successful
answer's; and `conflicts`, structured reasons naming each conflicting
node. The client already holds the rejected candidate and its logical base, so
the rejection does not repeat them; the candidate stays the client's draft.

A direct client treats `failedIndex` as a sequencing boundary. It reviews only
that failed element; later elements have not conflicted because the host
has not examined them. After the reviewed result is accepted, the client
replays each retained suffix change in order against the resulting accepted
state. Replay preserves the original change between adjacent submitted
candidates. It does not reuse an old complete candidate under a new logical
base or collapse the suffix into one root. A guarded replay that cannot be
applied exactly becomes a new client-owned conflict before submission.

### 1.3 Sparse transfer with object deltas

A transition transfers the content-addressed graph sparsely. Each changed
object travels either as its complete canonical bytes or as a delta against an
object reachable in the relevant basis graph:

| Representation | Update submission | Accepted transition | Intended use |
|---|---|---|---|
| `objects` entry | Yes | Yes | New objects, or whenever complete canonical bytes are smallest |
| `ObjectDelta` | Yes | Yes | Any changed file or directory whose predecessor shares most of its bytes |

An `ObjectDelta` concatenates ordered instructions into the complete canonical
bytes of the `result` object. `copy` is `[offset, length]` into the exact canonical bytes of the
`base` object and `insert` is canonical padded base64 in JSON or a byte string
in CBOR ([reading and watching §2.2](1.2-reading-and-watching.md#22-request-and-response-encodings)). Copy ranges are
nonempty, nonnegative safe JSON integers wholly within the base bytes; inserts
and the instruction list are nonempty. Because instructions address encoded
bytes rather than a decoded payload, one rule covers every object kind: a
one-entry change to a large directory or a one-paragraph change to a large file
can use a few instructions, and a moved region is a copy rather than a
retransmission.

A file delta addresses file bytes directly: editor replacements copy unchanged
ranges at their original byte offsets and insert replacement bytes. Any instruction sequence that
reconstructs the exact result is valid; the diff algorithm is the sender's
choice and never part of identity.

The base must be reachable in the relevant basis graph: the request's retained
accepted watchpoint for its first element, the preceding candidate graph for a
later element, or the transport basis root (`from.root` when present, otherwise
`update.previous.root`) for a watch transition. The
receiver hash-verifies that base, applies the instructions, requires the
reconstructed bytes to hash to `result`, and decodes them as a valid canonical
object. It then treats the result exactly like a complete object. Within one
update element, or one transition, a result appears exactly once across its
complete objects and deltas. A later element of a request may carry an object
that an earlier element carried, as a chain that returns to an earlier state
does. New objects use
complete bytes; otherwise the sender normally chooses the smaller form. The
encoding is a transport choice: the identified result object and accepted
roots remain canonical, and retries or later storage packing may choose
another transfer representation without changing semantic identity. Within an
element, duplicate results and a result also supplied as a complete object are
invalid, as are noncanonical base64, out-of-bounds copies, arithmetic
overflow, and quota excess.

## 2. Authored changes

### 2.1 The change

Every candidate has `change`, `at` and `candidate`, and may carry `trace`,
`resolves`, `ifCurrent`, `objects` and `deltas`
([§1](#1-the-update-request)). An omitted `trace`,
`resolves`, `objects` or `deltas` means `null` or `[]`, so the smallest update
is `{ change, at, candidate, objects }`. Request identity is computed over the
filled-in values ([§1.1](#11-request-identity)), so omitting a field and
sending its default are the same request. A sender may omit them; it never
sends `null` for a list.

`at` is when the edit was made. It stamps the times of the entries this
update creates or changes ([data model §6](1.1-data-model.md#6-entry-times)), so it is part of the candidate's root,
and a derived candidate's root is derived with it. Within one request each
`at` is no earlier than the one before it.

`candidate` names the exact root of the desired tree, or is `null` for a
derived candidate ([§2.3](#23-derived-candidates)).

`change` identifies an immutable authored change within its TreeID and uses
the [reference key syntax](1.2-reading-and-watching.md#122-references-and-selectors).
A random UUID is suitable for a new change. Exact retry and
adoption retain its identity and semantics; clients MUST NOT reuse it for different
intent. Change identities within a request are distinct.

`trace: null`, or an omitted trace, means snapshot semantics. Otherwise the trace is a chain of frames
([§2.2](#22-the-trace)) whose operations explain the entire authored transition, including effects
on hidden material. There is no residual field. Known operations followed by
snapshot-only edits are separate candidate elements. `resolves` is an array, empty
or omitted when there is no human-authored resolution. An empty trace is valid only
with nonempty `resolves`, for an explicit resolution that leaves the projection
unchanged. Snapshot candidates may also carry explicit resolution declarations;
snapshots alone never resolve. A trace is evidence the host checks in full, never a hint it may
skip. Unknown semantic fields or operation kinds are invalid, and there is no
capability discovery or negotiation: a request the host does not support fails
closed, with no translation and no alternate route.

An operation key is unique within its change, across every frame of its trace. `(change, operation)` identifies its
single material result when it has one; there is no independently named output.
Result identity and material origin are distinct: a move preserves origins, a copy
creates new origins with derivation, and an edit preserves only verified lineage.
Result coordinates describe the result at execution on its authored basis. A result
may contain several retained or newly created origins. Equal bytes do not establish
shared origin. A snapshot asserts no fine-grained origins; the host may derive
conservative correspondence, but MUST NOT invent move, copy, undo or resolution intent.

### 2.2 The trace

```ts
type Frame = { before?: Hash; after?: Hash; operations: Operation[] };
```

A trace is an ordered chain of frames, each one tree root to the next. It records
the authored transition as the client actually made it, rather than flattening
several editor generations into one claim that no single basis explains. A
frame's roots are optional and independent: each one stated is an assertion the
host checks, and each one omitted the host derives ([§2.3](#23-derived-candidates)).

- A frame's basis is positional: `trace[0]` executes on the candidate's authored
  basis root (the element's logical base), and each later frame on its
  predecessor's result. A stated `before` MUST equal that basis.
- A stated `after` MUST be reproduced exactly, including untouched bytes, when
  the frame's operations execute on its basis ([§2.4](#24-operations)). A frame that does not is
  invalid; the host never falls back to the candidate's bytes.
- `candidate` is the last frame's `after`, or `null` when that `after` is
  omitted. A *stated* candidate is one whose last frame states its `after`.
- A frame that carries row operations ([§2.5](#25-property-operations)) carries no other kind.
- Each frame carries at least one operation. A change with nothing to state uses
  an empty trace or, for snapshot semantics, `null`.

Basis references inside a frame name material in that frame's `before` tree;
operation references name an earlier key anywhere in the same change. Frames are
therefore concatenated without rebasing, which is what lets a client coalesce
several generations into one change.

Limits are in [§2.4](#24-operations).

### 2.3 Derived candidates

A candidate with `candidate: null` is *derived*: its last frame omits `after`, so
the host computes the result. The host executes every frame on its basis exactly
as it checks one that states its roots ([§2.4](#24-operations)), checking each root that is
stated, and the last result is the element's candidate; acceptance then
continues as for any candidate ([§3.2](#32-the-acceptance-procedure)). An operation that does not apply on its
basis, or a stated root the execution does not match, is invalid evidence and
fails the request before any element is accepted. A host that does not execute
some operation outside a stated trace answers `unsupported-operation` for a frame
that leaves its result out; it always executes row operations.
`resolves` and `ifCurrent` work as for any candidate. A derived candidate needs
no objects or deltas beyond the content its operations introduce. A snapshot
(`trace: null`) is never derived: its candidate is its content.

Any operation trace may be derived. Row operations in practice are: a client
that does not encode a collection's tables simply leaves out the roots after
them, and may still state a `before` it knows. A client that holds the tree and
can compute roots should state them: a stated
candidate lets later elements chain on it while earlier ones are in flight, and
an `after` the host does not reproduce exposes a divergence at once.

Basis references still name objects in their frame's basis, so a client can
reference material only in a basis it holds: it puts operations that build on
each other in one frame, as row operations on one collection run in order
within it ([§2.5](#25-property-operations)).

A client that cannot encode a collection's tables never needs to: it sends
row changes as derived candidates, shows them applied over the rows it last received until
their results arrive, and applies each result as a watch frame.

### 2.4 Operations

[reading and watching §1.2.2](1.2-reading-and-watching.md#122-references-and-selectors)
defines `Ref`, `EntryDestination` and their selectors for both reads and
writes. Authored operations additionally use:

```ts
type Lineage = { source: Ref; range: [number, number] };
type OperationRef = { change: string; operation: string };
```

The target host supports every operation below and the property operations
of [§2.5](#25-property-operations). Each has required `key` and
`kind` fields. All listed fields are required except `lineage`. References may
select projected material or alternatives; the reference determines the target,
so there is no separate `editAlternative` operation.

| `kind` | Fields | Authored meaning and material result |
| --- | --- | --- |
| `editSource` | `source: Ref, text, lineage?` | Replace selected text; empty selection inserts and empty text deletes. Result is the replacement text, including preserved lineage. |
| `moveSource` | `source: Ref, at: Ref, side` | Relocate the same material and transport independent edits. Result is the relocated text with its original origins. |
| `copySource` | `source: Ref, at: Ref, side` | Create a distinct copy of observed text with derivation. Result is the new text; later edits to either copy remain independent. |
| `moveEntry` | `source: Ref, destination: EntryDestination` | Move the same entry/subtree. Result is the relocated entry with retained descendant identities. |
| `copyEntry` | `source: Ref, destination: EntryDestination` | Create a distinct entry/subtree derived from observed material. Result is the new subtree. |
| `removeEntry` | `source: Ref` | Remove the observed entry; concurrent modifications remain evidence to reconcile. No material result. |
| `replaceEntry` | `source: Ref, value: { file: Hash } \| { page: Hash } \| { directory: Hash } \| Ref` | Replace the selected entry's content/subtree while retaining its outer entry identity. Result is the replaced entry. |
| `addEntry` | `destination: EntryDestination, value: { file: Hash } \| { page: Hash } \| { directory: Hash }` | Create a new entry/subtree under an existing directory; the name MUST be free after the preceding operations. Result is the new entry, whose identity is the operation. |

Undo is not an operation. An editor publishes an undo as the ordinary operations
that restore the earlier text against the generation being undone, which a frame
already expresses exactly.

`replaceEntry` supports whole-file/binary and subtree replacement without a text
payload. A `file`, `page` or `directory` value identifies the explicit entry kind and its object supplied
or reachable under the transport rules. Kind is never inferred from payload bytes.
Such a value asserts new content, not historical
lineage. A material value takes the exact content and descendant provenance of a
referenced entry, including a hidden alternative. It does not assert a copy or permit
two simultaneous placements of one entry identity. A deliberate duplicate uses
`copyEntry`. Boundary attachment kind/authorization and all model constraints remain
in force. `replaceEntry` requires an existing entry in its authored basis.

`addEntry` creates what `replaceEntry` cannot: an entry at an absent name. Its
`destination.parent` is an entry reference (never ranged) to a live directory, and
its value is a supplied `file`, `page` or `directory` object, never material; adding
existing material is `copyEntry`. The value asserts new content with no lineage.
Two additions of one name in concurrent branches are reconciled like two moves
into that name: they leave an explicit choice, even when the added bytes match,
because each addition is a distinct entry identity.

`lineage` maps ascending nonoverlapping ranges in the replacement text to verified
source selections. Each mapping MUST preserve exact bytes and origin. Unmapped text
is new material. False lineage is invalid. Omission supplies no preservation claim;
lineage is not normalization or inferred copy intent.

Operations execute in order against their frame's `before` root, frame by frame.
Basis references retain their meaning as earlier operations transform material;
use operation-result references for newly introduced material. Each frame's
result MUST reproduce its `after`, and so the last frame's `candidate`, including
untouched bytes, while retaining all declared hidden/provenance effects.
Contradictory authored effects, false references and unexplained candidate changes
fail. Valid effects that become incompatible through concurrency are retained as
unresolved decisions when representable within the contract bounds.

Limits: at most 1024 operations per candidate across its trace, 64 frames,
1024 lineage segments per edit, and
1 MiB of UTF-8 text per text field. Implementations may impose documented overall
request/object limits. Grammar validation does not establish source reachability,
UTF-8 boundaries in stored objects, candidate correspondence or authorization; the
authority validates those before acceptance.

### 2.5 Property operations

A row's fields and a page's properties are the same thing in the data model, a
node's properties, and they are edited the same way: by property, never by the
bytes of a projection or of frontmatter. Every property operation names its
node with the fields of one of these targets:

```ts
type PropertyTarget =
  | { collection: Ref; model: Name; row: string }   // a row
  | { page: Ref };                                   // a page entry
```

A row target names the collection's folder (an entry reference, never
ranged), one of its models with data rows, and the row's canonical stable key
JSON, such as `[["id","g1"]]`; a row has no entry of its own
([collections](1.4-collections.md)). A page
target is an entry reference, never ranged, to a `page` entry. `field` names
one property: a declared field of the row, or any property name of the page.
A row's key fields, `created` and `modified`, and a page's `id`, are never
one.

| `kind` | Fields | Authored meaning |
| --- | --- | --- |
| `rowCreate` | `values` | Create the row with these fields. `values` holds the row's key, which MUST equal `row`, and the row MUST be absent. Row targets only. |
| `rowDelete` | | Delete the row, and every pair of a plain n:m connection that names it. Row targets only. |
| `set` | `field, before, value` | Set one single value. `before` is the value the author saw and MUST equal the property on the basis; `null` means absent, and a `null` value removes the property. The two differ. On a page, a new property goes at the end of the order and an existing one keeps its place. |
| `connect` | `field, member` | Add `member` to a many-valued property: a connection pair, a value-array element, or an element of a page's list property. It MUST be absent. In an `ordered` field, and in any page list, it goes at the end. |
| `disconnect` | `field, member` | Remove `member`, which MUST be present. |
| `move` | `field, member, after` | Place `member` directly after the member `after`, or first when `after` is `null`, in an `ordered` field or a page list. Both are present and the order changes. |

Values are JSON. A row's follow its field types; a `Date` is a plain string in
JSON, since its field type already says it is a date, and tagged in CBOR as in
the row itself ([collections §2](1.4-collections.md#2-rows-and-values)). A page's are YAML 1.2 core
values plus timestamps ([data model](1.1-data-model.md#51-pages)), which
JSON spells `{"$date": "2026-10-28"}` for a date and
`{"$dateTime": "2026-10-28T09:00:00Z"}` for a UTC date-time. A map whose
only key is `$date`, `$dateTime` or `$map` is wrapped as `{"$map": map}`, so
each value has one spelling.

A page is created and removed by `addEntry` and `removeEntry`, and its body is
edited by `editSource`, `moveSource` and `copySource` addressed to the page,
whose text is its body.

A plain n:m connection is one set of pairs, so `connect` and `disconnect` on
either end's field change the same pair, and two operations naming one pair
from its two ends are the same fact. `move` names the `ordered` end.

A property operation other than `rowDelete` may carry `at`, when the edit was
made, as an RFC 3339 date-time in UTC with millisecond precision; omitted, it is
its update's `at`. A client states it only when one update coalesces edits made
at different times, and never later than the update's `at`. Replay writes it to
a row's `modified`, and on `rowCreate` to `created` too; nothing else sets them.
A page or file has none of its own; its directory entry takes the update's
`at` ([data model §6](1.1-data-model.md#6-entry-times)). An authority rejects an `at` more than five minutes
ahead of its own clock.

A property operation names its node by identity, so concurrent changes to one
row or page merge property by property ([§3.6](#36-merging-properties)). It has no material result to
reference.

The host replays property operations on their frame's basis, deriving the
resulting tree or checking a stated one ([§2.3](#23-derived-candidates)).

## 3. Accepting and merging

### 3.1 Exact-state preconditions

Ordinary updates reconcile with current accepted state
([§3.2](#32-the-acceptance-procedure)); the one guard is `ifCurrent`.

An optional `ifCurrent` names the exact accepted update ID required immediately
before this element is processed. A mismatch rejects that element with `409 conflict`
without accepting its effects; the completed prefix is retained. Same-root metadata
advancement also fails the guard. Exact successful replay is recognized before
rechecking this precondition, so retry returns the original result. The guard is
per element, not a transaction around the entire request. Callers generally cannot
predict new accepted IDs for later elements and should not invent them.

Tree activation uses `base: null` and the existing reservation/authorization rules;
its first element has no `ifCurrent` or resolution declarations because no accepted
state exists yet. Semantic reference, resolution and model constraints always apply,
with or without an exact-state precondition. A complete property-map replacement
still preserves applicable identity declarations and leaves unrelated content alone.

### 3.2 The acceptance procedure

Acceptance is decided from authored effects and accepted semantic state, not solely
from the candidate and current root hashes. Semantic state includes contributions,
origin bindings, unresolved alternatives and explicit resolutions as well as the
projected file graph. Apply the following procedure to each element after exact
replay handling in [§1](#1-the-update-request):

1. Reconstruct the candidate and validate its authored effects against its logical
   basis. For an operation-bearing update, execution must reproduce the candidate
   projection while preserving all declared semantic effects, including those not
   visible in that projection. For a snapshot, derive only the effects justified by
   the exact observed projection. Validate authorization, references and explicit
   guards before treating the submission as a no-op.
2. Enforce the optional exact-state precondition in [§3.1](#31-exact-state-preconditions). Combine independent
   contributions and apply
   applicable format-aware rules. If valid competing effects cannot be uniquely
   combined, retain them as unresolved decisions within the representation limits
   of [§3.4–3.5](#34-accepted-decisions-and-continued-editing).
   Missing automatic merge rules alone do not require rejection. Entry times
   merge as [data model §6](1.1-data-model.md#6-entry-times) says. Ordinary operations
   and snapshots preserve existing decisions; only guarded explicit resolution
   closes them.
3. Compare the resulting semantic state with current. Return `unchanged` without a
   new accepted update only if there is no new contribution, origin binding,
   alternative continuation, resolution or projected change to record. A snapshot
   with no authored change can qualify. Equal candidate/current roots, equal
   candidate/base roots, or equal alternative bytes do not establish a semantic
   no-op. An independent deletion contribution, hidden-alternative edit or resolution
   choosing the existing projection can require a new update with the same root.
4. Otherwise commit the resulting semantic state and projection atomically. Return
   `accepted` whether or not reconciliation was needed. The resulting state may have
   `conflicted: true`; acceptance does not imply resolution. Assign a new accepted
   update ID and advance observation even if the root is unchanged. Continue processing the remaining elements against their respective
   authored bases, carrying accepted provenance and decisions through the sequence.
5. If a required match/guard fails or the effects cannot be validly retained within
   the contract, reject with the applicable structured error. A reconciliation
   rejection uses `409 conflict`, with current state, reasons and the draft
   transition. Preserve the successful prefix and leave later elements unattempted.
   Never substitute a rejected local draft for accepted alternatives.

Format-aware rules may produce a clean merge or explicitly resolve guarded decisions
under [§3.5](#35-format-aware-merge-rules).
They must honor the applicable model constraints, including
[collection rules](1.4-collections.md#4-accepted-update-validation-and-merge).
The host retains unresolved choices when no rule justifies resolution.

### 3.3 Explicit resolution

A consumer that requires resolved material checks that condition when it
consumes it; there is no resolved-only write mode.

```ts
type ResolutionDeclaration = {
  update: string;
  conflict: string;
  alternatives: string[];
};
```

A declaration in `resolves` explicitly endorses the candidate's resulting projection
for the named decision. It does not carry its own replacement language or clear an
arbitrary flag. The operations or snapshot describe the authored result; the
declaration supplies resolution intent and guards. For hidden material to become
the chosen result, the candidate must materialize it using the appropriate ordinary
operations. Editing a hidden alternative alone does not select it.

`update` identifies the exact reviewed accepted evidence. `alternatives` is the
complete nonempty set of reviewed alternative IDs, with no duplicates. The host
loads their revisions, contributions and dependencies at that state and compares the
relevant evidence with current. New or changed alternatives, affected locations,
projection choices or dependencies invalidate the review. Unrelated advancement need
not invalidate it when the host proves the guarded decision unchanged. `ifCurrent`
is available when the caller requires no accepted advancement at all.

There is no fixed protocol count limit on declarations or reviewed alternatives.
A conflict may appear only once. Array order is retained in request identity, but
all declarations take effect jointly, never sequentially. The host validates
that the candidate fully expresses each resolved choice and preserves all unnamed
open decisions. Ordinary saves, equal bytes and omission of hidden material never
resolve a decision implicitly.

Coupled decisions use one candidate with all required operations and declarations.
The host validates a coherent combined result against dependencies and model
constraints, then accepts everything atomically or rejects that candidate. Several
request elements are not a substitute: they can leave an accepted prefix. A dependency
does not force joint resolution if an individual choice leaves the other alternatives
meaningful and correctly attached. New concurrency affecting a resolved choice causes
rejection, not silent expansion of the person's resolution. Unrelated edits may merge.

Keeping the existing projection can use an empty trace (`trace: []`) plus guarded `resolves`.
It advances accepted identity even with an unchanged root. An automatic rule uses the
same resolution invariants with separately recorded authority authorship under [§3.4](#34-accepted-decisions-and-continued-editing).

### 3.4 Accepted decisions and continued editing

The host keeps three things apart: contributions, unresolved decisions, and
the projected file graph. The projection is always a valid ordinary graph with
no conflict markers; its correspondence to each decision's alternatives is
part of accepted state, and hidden alternatives and their objects stay
readable as long as the state is retained. Decision IDs are stable within a
tree. Alternatives keep their identity, revision and provenance, and equal
bytes, order or paths never identify or merge them. A decision may concern
content, existence, placement or attachment; dependencies constrain which
combinations are valid, without enumerating whole-document combinations.

An ordinary edit continues the alternative it is attributable to and leaves
the others, and the open decision, in place. Returning to base bytes or
matching another alternative is not resolution. Ambiguous attribution is kept
when it can be represented; invalid claims, missing evidence and exceeded
bounds fail.

An accepted unresolved result acknowledges work normally: it pauses no sync and
stops no later element of its request. The host owns attribution and resolution
on every write path, so a client needs no alternative map to keep editing
([reading and watching §1.1.4](1.2-reading-and-watching.md#114-accepted-unresolved-state)).

Inspection is authorized and scoped to accepted state. It supplies the
complete relevant identities, locations and dependencies without requiring
a full provenance graph. [reading and watching §1.2.3](1.2-reading-and-watching.md#123-reading-conflicts)
specifies text, whole-entry and placement inspection using the same reference
vocabulary.

### 3.5 Format-aware merge rules

A merge rule reads exact source, its structure or schema, provenance and open
decisions; a filename extension alone is not enough, since frontmatter and
embedded code may merge differently from prose. A rule justifies a resolved
result, names the remaining choices, or declines. It accounts for every
competing contribution, preserves unaffected bytes and identities, and
validates its result. Binary content needs an applicable rule, or
alternatives, never a text fallback.

A rule that clears an existing decision is an automatic resolution: it records
the state and alternatives it considered, its own identity and revision, the
result with its provenance, and why. A human resolution records the reviewed
operation and alternatives instead. Either preserves independent decisions,
checks dependency guards and commits atomically. A stale rule result is
recomputed or rejected, and changing a rule never reinterprets a past
resolution. A clean automatic merge keeps enough evidence to explain and
reproduce it, without making a visible conflict.

The decision scenarios in [accepted ambiguity](conformance/accepted-ambiguity.json)
state these obligations as cases. A rule may record evidence fields of its own;
they never grant authorization or express human resolution intent, and
resolution evidence stays available for as long as its state is retained.

### 3.6 Merging properties

`collection-fields-v1` merges two changes to one logical collection by row
identity, then field by field, and `page-properties-v1` merges two changes to
one page property by property. Both take changes as property operations or as
differences from a snapshot's basis, and both use the rules below. A row or
page only one side changed takes that side. For one both sides changed:

- A single value conflicts only when the two set different values.
- A many-valued field merges per member: removals and additions from both
  sides apply. An addition to an `ordered` field follows the member it
  follows on its own side. A page's list property merges as an `ordered`
  field.
- An `ordered` field merges as a sequence. If only one side moved members,
  its order holds; when both moved the same member, the later move by `at`
  wins, with a merge note.
- A `Markdown` field merges by lines. Edits that overlap conflict.
- Deleting a row conflicts with a concurrent change to it, and with nothing
  else.
- Times never conflict: `created` takes the earlier value and `modified` the
  later one, as for entries ([data model §6](1.1-data-model.md#6-entry-times)).
- A page property both sides added lands in current's order, followed by the
  candidate's additions in their order.

A page's body merges as text, as any Markdown source does, independently of
its properties.

A conflict keeps current's value in the accepted state. On a row it becomes a
`field` decision about that row field, and on a page a `property` decision
about that property ([reading and watching §1.2.3](1.2-reading-and-watching.md#123-reading-conflicts)),
with current's value and the candidate's as alternatives. Every other property
still merges. The merged rows are validated against the schema; a result the
schema rejects is a conflict on the collection's folder.

## 4. Mutations

A host that runs apps executes [Beetle](1.5-beetle.md) mutations: reviewed transactional intent,
whose writes reach a tree as an ordinary update.

A mutation runs as its caller, with the authority
[access control §1.1](3.2-access-control.md#11-execution-authority) gives its
code. Its error conditions narrow behavior within that authority. There is no
mutation-permission namespace and no implicit whole-tree write.

A mutation runs in one runner-owned transaction: its reads, guards, writes and
receipt commit together, and a public error writes nothing. Its writes reach
their tree as one ordinary update, guarded by the state the mutation read
([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)); a
stale guard reruns the mutation rather than merging a stale decision. Because a
mutation is declarative, a client may evaluate it against its own copy of the
rows to show the result at once. The host's run is authoritative, and that optimistic
presentation never displaces the subscribed result as the source of truth.

The caller supplies one mutation identity and reuses it for an ambiguous retry;
the request below defines the digest
that binds it to the handle, code version, validated input, and activated
source bindings, the replay scoping, and the receipt. The runtime captures one
logical mutation time (`now`, `today`) and deterministic generated-ID namespace
before execution; exact retries observe the same values. The runtime records the
retry identity and its result so that, after a restart, a committed mutation is
never mistaken for one that never ran.

Mutations that span several trees, durable workflow steps, portable
foreign-key actions, and external non-tree effects are not yet specified
([Apps 006](../../plans/later/apps-006-durable-authoring.md),
[deferred 3](README.md#deferred)).

Mutation calls carry the handle identity and version, validated input,
authenticated subject, and caller-stable mutation identity:

```text
POST /.overstory/trees/{SourceTreeID}/mutate
Content-Type: application/json
```

```ts
type MutateRequest = {
  handle: MutationHandleRef;
  mutationID: string;
  input: unknown;
};

type MutationHandleRef = HandleRef;

type MutationResultReceipt = {
  mutationID: string;
  requestDigest: Hash;
  /** The accepted update the mutation's writes made, when it wrote. */
  affected?: {
    tree: TreeID;
    update: string;
  };
  /**
   * The rows the mutation wrote, ordered by table name then key, with `deleted`
   * on a row it deleted. A mutation has no return value
   * ([Beetle §4.1](1.5-beetle.md#41-facts)).
   */
  rows: Array<{ table: Name; key: string; deleted?: true }>;
};
```

`handle.tree` must equal the route `SourceTreeID`. The host validates the
handle's code version, input, source bindings and authority before data
access. Invocation requires authority to run the handle, not to read its
source. Current authority is checked before every new step and receipt
return. Revocation does not undo committed effects. Missing authority cannot reserve
a new effect or leak private handle/resource existence.
Mutation semantic identity is the SHA-256 of the canonical CBOR encoding of
`{ version: "mutate-v1", handle, input, sources }`, where `sources` is the
activated handle's complete, path-sorted set of
`{ authoredPath, tree, path, schemaFingerprint }` bindings. The bindings are resolved when the handle is activated; a caller-selected destination needs concrete resolution and grant coverage. This prevents an
ambiguous retry from executing the same code and input against a newly resolved
store, relation, or schema. Durable lookup is scoped by the source tree, a
trusted caller replay principal, and `mutationID`. The principal is the
authenticated profile TreeID when present, otherwise the presented access-link
digest identity, otherwise an anonymous identity. It is runtime-only authority:
link digests and replay-principal values never enter a mutation's context,
results, errors, logs, or transcripts. Reusing that identity
with a different request digest is a conflict; an exact ambiguous retry returns
the original receipt and creates no second effect. This is the same committed-
intent pattern as an accepted tree update: transport representation is excluded
from the semantic digest, the subject scopes replay, and `affected` names the accepted update the mutation's writes made: a client
knows a view result reflects the mutation once that tree's watch has passed
that update. The mutate payload remains distinct from `UpdateRequest`: it
carries reviewed intent, while an update carries tree material.

A form submitted from a browser may use the view's ordinary canonical
HTTP action surface, while a named Overstory call uses the endpoint above. Both bind through the
checked handle and preserve this exact request/receipt identity.
The durable receipt and corresponding view result may arrive in either order;
clients correlate them idempotently and treat the view result as authoritative.

### 4.1 Relationship to tree synchronization

`updates`, `watch`, `views` and `mutate` share authentication, semantic digests,
SSE framing, and tree-scoped authorization, but not
transaction or replay domains: `updates` and `mutate` have different conflict
domains, and `watch` has retained replay identity while `views` deliberately
has none. An accepted update requires authority covering its actual effects; a named mutation
requires coverage of the rows it declares it writes. Consolidation
is shared machinery, not one polymorphic endpoint.

View streaming is derived-result delivery, not tree history. A mutation of an
Overstory-canonical data tree advances that data tree's ordinary accepted root and
therefore also causes a `tree.update` watch event; it does not change the
app's source-tree root. Neither execution nor
network reachability independently grants accepted-snapshot access, broadens
the readable tree graph, or exposes raw stores, credentials, private source,
unrelated rows, or private diagnostics. Cross-server plan discovery,
delegated authorization, and server-to-server execution routing remain
unspecified ([deferred 2](README.md#deferred)).
