# Federation
*Part of the [Overstory spec](README.md), layer 3 (accounts, access and federation): how a profile acts at hosts other than its home. Placement accounts, invitations accepted as placements, published device keys, and visitor sessions. Accounts at one host are [accounts and devices](3.1-accounts-and-devices.md); what a profile may do there is [access control](3.2-access-control.md).*

## 1. Home and placement hosts

A profile's configuration lives on one host,
its **home host**, which accepts every edit to it, including its
`devices.yaml`. A profile may also hold **placement accounts** at other hosts
([§2](#2-placement-accounts)), so that a person can place trees under several hosts' canonical URLs.
A placement host keeps no device list or configuration of the profile: it
reads the home host's published device keys ([§4](#4-published-device-keys)). A host refuses a claim for
a profile it already has an account for.

## 2. Placement accounts

A host's community may reserve an allocation for a profile whose home is
another host, by naming the profile's canonical locator there
([locators §1](1.6-locators.md#1-forms)):

```yaml
type: group
members:
  - profile: https://home.example/~alice
    handle: alice
```

When the host accepts a community update that adds such a member, it
resolves the locator at its authority, the profile's **home host**, and in the
same commit pins the Profile TreeID, records a **placement account** (profile
TreeID, its local allocation such as a handle, and the home host's origin),
and declares the account's placement root (below). If the locator cannot be
resolved, or resolves to a profile the host already holds, it refuses the
update with a retryable error naming the home host in `details.homeHost`,
changing nothing. When the administrators add the member themselves there is
no placement claim and no proof from the profile key: they say whom they mean,
and the profile's devices then open sessions ([§4](#4-published-device-keys)) with no further step. A
pending invitation becomes such a member when the invited person accepts it
with a profile homed elsewhere ([§3](#3-accepting-an-invitation-as-a-placement)). Removing the member
disables the placement account, ending its sessions and watches as a device
deletion does; its placement root and the trees under it stay. If the locator
later resolves to another TreeID, the account opens no sessions until the
member is edited.

The account is host state like a handle, not authored per-account data. The
profile tree lives at the home host, so the host declares, on the placement
host, the profile's **placement root**: an ordinary tree with a fresh random
TreeID, mounted where the host allocates the account,
whose configuration grants the profile `admin` and mounts nothing. It is the
parent of the person's trees on that host. Every tree on the placement host
has its tree configuration there, with rules that name the profile as on any
host.

On a placement host the profile's devices may read, update and watch as
the profile, edit tree configurations from administrator devices, and declare,
activate and mount trees under the placement root. Code there has the
authority [access control §1.1](3.2-access-control.md#11-execution-authority)
gives code on a placement host. Routes about the profile's own configuration,
its devices and pairing, are the home host's: a placement host refuses them
with `permission-denied`, naming the home host in `details.homeHost`.

On a placement host the account descriptor
([locators §5](1.6-locators.md#5-finding-trees)) carries `placementRoot` and no
`configuration`:

```json
{
  "id": "tr_…",
  "profileTree": "tr_…",
  "homeHost": "https://home.example",
  "placementRoot": { "id": "tr_…", "path": "/~alice", "tree": null },
  "…": "…"
}
```

`placementRoot.tree` is the root's tree descriptor once its first snapshot
has activated it, and `null` until then.

The placement host trusts its community's administrators for which host is
each placement account's home, and that home host, over HTTPS, for the
profile's device keys and for nothing else. A compromised home host can act as
those profiles on the placement host, which is no more than it holds already;
an administrator can reserve any public profile, whose devices can then act
there, and nobody else's.

## 3. Accepting an invitation as a placement

```text
POST /.overstory/challenges
PUT /.overstory/accounts
```

Joining a community is one route with two challenge purposes: a claim
([accounts and devices §1.2](3.1-accounts-and-devices.md#12-claiming-an-account-with-the-profile-key)), purpose `account`, makes the host the profile's
home, and purpose `placement` makes it a member whose home is elsewhere. A person has one profile identity and one home host. An invitation link
([accounts and devices §1.2](3.1-accounts-and-devices.md#12-claiming-an-account-with-the-profile-key)) opened by a client whose profile is already claimed at another host
is accepted as a placement: the pending entry becomes a member naming the
profile by its canonical locator at its home host, exactly as if the
community's administrators had authored it ([§2](#2-placement-accounts)). A profile is never
claimed at a second host.

The client requests a challenge with `purpose: "placement"`, the link's
`account`, its code as `inviteCode`, `profileTree`, and `profile`: the
profile's canonical locator at its home host. The host refuses a `profile`
whose authority is itself. The challenge binds what a claim's does and
`profile` too, and is signed the same way with the profile key.

The acceptance is `PUT /.overstory/accounts`, and its body carries the
`challenge`, the raw `publicKey`, the Ed25519 `signature` and `inviteCode`;
the host reads the account and profile from the challenge. It carries no
device and no configuration: those stay at the home host.

```json
{
  "challenge": { "version": 1, "purpose": "placement", "id": "ax_aaaaaaaaaaaaaaaaaaaaaaaaaa", "…": "…" },
  "inviteCode": "…",
  "publicKey": "…",
  "signature": "…"
}
```

The host verifies the challenge, the key and signature as for a claim, and the
code against the reservation's digest. It then replaces that one pending
entry, keeping its handle, with the member `profile: <profile>`, and accepts
the result as an update of the community profile, so the locator is resolved
and pinned, and the placement account and its placement root are created, in
the same commit as for any member a community adds by locator ([§2](#2-placement-accounts)). A
`profile` that does not resolve, at its authority, to `profileTree` is
refused. The challenge is consumed in that commit.
A home host that does not publish the profile's device keys refuses the
acceptance as [§2](#2-placement-accounts) refuses the update, naming it in `details.homeHost`, and
changes nothing. The response is `{ "account": … }`, the placement
account's descriptor ([§2](#2-placement-accounts)), with no `configuration`: that stays at the home
host. Exact retry after success returns the same answer; any other attempt on
the consumed invitation returns `already-claimed`.

A client that already holds the profile's key needs no new device step: the
profile's devices open sessions at the placement host with the keys their
home host publishes ([§4](#4-published-device-keys)). A client keeps one identity per person. Holding
several profile identities on one device is possible but is not a
configuration a client needs to offer.

## 4. Published device keys

```text
GET /.overstory/peer/profiles/{ProfileTreeID}/device-keys
```

A home host serves, for each profile it is home to and to anyone without
authentication, the part of that profile's `devices.yaml` a placement host
needs, as of the accepted configuration:

```json
{
  "profileTree": "tr_…",
  "devices": [
    { "id": "dv_mac", "key": "ed25519:…", "administrator": true }
  ]
}
```

It never lists labels. Anyone can therefore see how many devices a profile
has, which are administrators,
and when that changes; limiting that would need hosts to authenticate to each
other.

A placement host opens a session ([accounts and devices §4.1](3.1-accounts-and-devices.md#41-device-sessions)) for a device listed in its copy of
the home host's device keys, treating the caller as that profile and device,
an administrator device if listed as one. It serves a copy for at most a
minute before refetching it. It refreshes the copy of
every profile with open sessions at least once per lifetime, and ends the
sessions and watches of any device no longer listed, or listed with another
key, so while the home host is reachable a deletion there reaches the
placement host within the copy's lifetime.

When a refresh fails, the placement host keeps serving its last copy, for
session challenges, opening sessions and administrator-device checks alike,
until the copy is older than a **grace** of one hour, a session's longest
lifetime. Past the grace it fails closed: it opens no session, and answers
what needs the copy with a retryable error naming the home host in
`details.homeHost`. A session it opens expires no later than the moment the
copy it was opened from runs out of grace, so nothing authenticates there
from a list older than the grace. The grace costs little: while the home host
is down nobody can delete a device there, since only the home host accepts
the change, so the only deletion it can miss is one made in the last minute
before the outage. A challenge request naming a DeviceID missing from its
copy makes it refetch early, and a failed fetch is retried, at most once
every five seconds per profile, so that nobody can use a placement host to
flood a home host. A challenge for a missing DeviceID that arrives within
that interval waits for it to pass and the refetch that follows, rather than
being refused, so a device paired at the home host moments before is found.

## 5. Visitor sessions

A profile may read at a host where it has no account. A **visitor** asks
for a session challenge ([accounts and devices §4.1](3.1-accounts-and-devices.md#41-device-sessions)) naming its profile, its device, and its home
host's origin as `homeHost`:

```json
{ "purpose": "session", "profileTree": "tr_…", "device": "dv_…", "homeHost": "https://home.example" }
```

The host reads that home host's published device keys ([§4](#4-published-device-keys)) for the
profile, with the same lifetime, grace, refresh and early-refetch rules a
placement host keeps, and issues a challenge only for a device they list.
The challenge carries the same `homeHost`, so the device signs it too. The
host refuses a `homeHost` that is itself, or that is not HTTPS (a loopback
host may name a loopback home). A profile that has an enabled account at the
host, home or placement, gets an ordinary challenge without `homeHost`, and
the client accepts it: its session is then the account's.

A visitor session is a bearer token like any other, for at most an hour and
no longer than the copy it was opened from serves. It holds no account: the
host stores nothing about the visitor and may keep visitor sessions in
memory only, so a restart ends them and the client opens another after the
`401`. A refresh that no longer lists the device, or lists it with another
key, ends its sessions and watches as it does a placement account's.

A visitor is vouched for only by the home host it named, so it is the
profile only as that host's locators name it. It reads a tree when a rule
(or an `admin` entry) names the profile by a locator at that home host
pinned to its TreeID, when a group does so through a member entry naming it
by such a locator, or when the group is held at that home host and its copy
lists the profile ([access control §1](3.2-access-control.md#1-subjects-and-rules)).
A domain locator ([locators §1.1](1.6-locators.md#11-domain-locators)) is at
the home host its records named when the host last confirmed them.
`everyone` and a presented link reach it as they reach anyone. A bare TreeID
subject names a profile the host holds, so it never matches a visitor. A
visitor only reads, watches and fetches objects: every other route treats it
as no account at all, and it never sees a tree configuration. Writing, and
being someone at a host, still need the community to reserve the profile
([§2](#2-placement-accounts)).
