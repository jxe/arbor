# Data model
*Part of the [Overstory spec](README.md), layer 1 (trees): what a tree is. Trees and nodes, the objects a tree is made of and how they are hashed, the times on entries, which files are pages, and how a page with children reads. Every host and client agrees on this; the [reading and watching](1.2-reading-and-watching.md) carries it.*

## 1. Trees and identity

Overstory is conceptually a global hash table of trees:

```ts
type TreeID = string;
type Name = string;
type LogicalPath = string;
type JSONValue =
  | null
  | boolean
  | number
  | string
  | JSONValue[]
  | { [name: string]: JSONValue };

type Overstory = Map<TreeID, Tree>;
```

The same tree can be placed many times. Copies with the same `TreeID` are
placements or working trees of one tree. The `TreeID` denotes the same logical tree
and history wherever Overstory is implemented. Even local, private, unpublished,
and offline trees have these IDs, although no public service can find them yet.
Each device, community, and application knows only the partial map it can
locate and read.

TreeIDs are generated randomly and locally when people share files or folders.
Person-profile TreeIDs are instead derived from a public identity key, allowing
the person who holds its private key to prove control. See
[accounts and devices §1.1](3.1-accounts-and-devices.md#11-beginning-a-person-identity).

Trees have one history and one ACL.

## 2. Nodes, children, and readings

A tree is a rooted hierarchy of nodes, where each node has properties, optional content, and children.

```ts
interface Tree {
  root: Node;
}

interface Node {
  properties: Record<string, JSONValue>;
  content?: Content;
  children: ChildSet;
}

interface ChildSet {
  members: Map<Name, Node>;
  schema?: ChildSchema;
}
```

In Overstory, records, tables, files, and documents are all ways to read nodes:

| Reading | Representation |
|---|---|
| Document | content, with properties as its frontmatter |
| File | content bytes |
| Directory | children |
| Record | properties as fields |
| Collection | children that share a schema |
| Row | one child of a collection, keyed by a rule its parent declares |
| View | content written in [UVL](4.1-apps-and-views.md), drawn by evaluating it |
| Agent | content that has been granted reviewed execution capabilities |

A Markdown page with frontmatter is therefore both a document and a record. A
folder of such pages can be read as both a directory and a database table. The
tree holds such a page as a [page object](#51-pages): its properties and its exact
content, with no frontmatter bytes. Each placement writes the frontmatter in its
own spelling.

For representing typed collections, a child set may declare a schema shared by its members. A node whose children share such a schema can be read as a collection. The schema defines member property and content shapes, stable identity, logical naming, relationships, ordering, and constraints.

## 3. Representations

A placement chooses how to hold a tree. Files and folders map to nodes as
[§8](#8-mapping-files-and-directories-to-nodes) describes. A child set's
*backing* is how its members are held: expanded files or a logical
collection.

A logical collection's rows are held in the tree itself
([collections](1.4-collections.md)). Each placement chooses how to project
them: collection files, Markdown row files, a database, or nothing at all.
The projection is not part of the tree, and other placements never see it.
Reformatting a projected file, or moving a collection from CSV to SQLite at
one placement, changes nothing in the tree: no update, no history, no hash.
A collection's model fingerprint and logical hash are the same at every
placement. The rows are ordinary children, read through the same node and
children APIs. Projection files are never children themselves.

## 4. Representation and model equality

Exact representation equality and logical model equality answer different
questions. A bytes hash identifies one exact authored byte sequence. The protocol
root is the corresponding exact identifier for a complete accepted snapshot:
as the object hash of the top directory, it transitively commits to the
canonical Overstory encoding of every reachable object. It is not a logical model
hash.

A model hash identifies normalized node state: properties, content, and child
set, including the child schema and the model hashes of its members. Two
representations can therefore have different authored bytes and Overstory roots but
the same model hash. A page is the exception that makes the two meet: a page
object holds only modeled state, so its object hash is its model hash, and two
placements that spell a page's frontmatter differently hold the same root. Model hashes prove that decoding different
representations produced equivalent logical state; they do not turn two trees
with different `TreeID`s into the same tree.

## 5. Objects

A file object is its exact file bytes, with no CBOR wrapper. Its object hash
is `sha256(fileBytes)`. Only directory, page, table and rows objects are
encoded as canonical CBOR.
Kind comes from the referencing directory entry; receivers MUST NOT sniff or
decode file bytes to infer kind. A file may contain bytes that are also a
valid directory encoding without being interpreted as a directory.

```ts
type ProtocolDirectoryEntry =
  | { name: Name; file: Hash; created: number; modified: number }
  | { name: Name; directory: Hash }
  | { name: Name; page: Hash; created: number; modified: number }
  | { name: Name; tree: TreeID };

type ProtocolDirectory = {
  type: "directory";
  entries: ProtocolDirectoryEntry[];
  collection?: CollectionReference;
};

type CollectionReference = {
  version: 1;
  modelFingerprint: Hash;
  // One per model with data rows, in UTF-8 order of model.
  tables: { model: Name; table: Hash }[];
};

type ProtocolTable = {
  type: "table";
  rows: number;                               // the sum of its chunks'
  chunks: { rows: number; chunk: Hash }[];    // each a ProtocolRows object
};

type ProtocolRows = {
  type: "rows";
  rows: LogicalRow[];                         // in stable-key order
};

type LogicalRow = {
  key: [Name, JSONValue][];
  fields: Record<Name, JSONValue>;
  created: number;                            // Unix ms, as entry times
  modified: number;
};

type ProtocolPage = {
  type: "page";
  id?: string;                                // the page's stable key
  properties: [Name, PageValue][];            // in the order they were added
  body: Uint8Array;                           // exact bytes after the frontmatter
};
```

In a directory object `collection` has exactly these three fields, with
`version: 1`, and each object exactly the fields shown; any other version or
member is invalid ([collections](1.4-collections.md#1-what-the-tree-holds)).

A directory entry either addresses another Overstory object by hash or marks a
nested Overstory tree boundary by TreeID. A file or page entry also carries its
times, `created` and `modified` ([§6](#6-entry-times)); a directory or tree entry has none. A snapshot walk stops at such a boundary:
the nested tree has its own roots, history, and access. `collection`, when
present, holds the rows of the directory's logical collection; its table and
rows objects are reached through it, and its validation rules are defined by
[collections §1](1.4-collections.md#1-what-the-tree-holds).

### 5.1 Pages

A `page` entry holds a Markdown page as logical state
([§9](#9-properties-markdown-content-and-identity)
says which files are pages). The entry keeps the file's name, such as
`atlas.md` or `_index.md`, so paths, links and locators are the same as for a
file; only the kind differs.

- `id`, when present, is the page's stable key
  ([locators §2](1.6-locators.md#2-stable-keys-revisions-and-fragments)). It is
  kept across rename and move and is never changed by a property update. It is
  not a member of `properties`.
- `properties` is an array of pairs, not a map, because the order in which keys
  were added is logical state that every placement writes. Names are unique
  and none is `id`.
- `body` is everything after the frontmatter's closing `---` line, byte for
  byte. A page without frontmatter has no properties, and its whole file is its
  body.
- An object has exactly the members shown; `id` is a nonempty string when
  present.

A `PageValue` is a YAML 1.2 core-schema value: `null`, a boolean, a number, a
string, an array or a map with text keys, or a timestamp. Numbers follow [§7](#7-cbor-and-hashes),
so `1` and `1.0` are one value. A map's keys are in canonical CBOR order, so
only the order of top-level properties travels. A timestamp is the one place
CBOR tags are allowed ([§7](#7-cbor-and-hashes)): RFC 8943 tag 1004 around a `YYYY-MM-DD` date
string, and tag 0 around an RFC 3339 date-time in UTC. A date therefore stays
distinct from the string `"2026-10-28"`. YAML features with no value
(anchors, aliases, comments and explicit tags other than timestamps) are not
part of a page.

When another operation, such as an update request or a watch frame, carries
complete objects, it carries them as the snapshot bundle does: an `objects`
array of each object's exact bytes, padded base64 in JSON and a byte string in
CBOR ([reading and watching §2.2](1.2-reading-and-watching.md#22-request-and-response-encodings)), with no hash beside them. The receiver hashes each one, as it
must anyway, and an object is named by that hash wherever it is referenced:

```ts
type ObjectBytes = string; // JSON: padded base64 of one object's canonical bytes
```


## 6. Entry times

A file or page entry carries two times, as Unix milliseconds in UTC:

- `modified` is the `at` ([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)) of the update that last gave the entry a
  different object at its path, or created it there. A snapshot update
  (`trace: null`), such as a folder scan, may instead give an entry it creates
  or changes an earlier time taken from the source, such as the file's own
  modification time on disk, so imported files keep their dates; never a time
  later than its `at`.
- `created` is the `at` of the update that created the entry, or, for a
  snapshot update, an earlier time from the source as for `modified`, and no
  later than the entry's `modified`. A rename or move
  keeps both times, since it does not change the object; so does converting a
  file entry to a page entry, or back
  ([§9](#9-properties-markdown-content-and-identity)),
  which changes its kind, not its content. An entry that is removed and later
  added again is a new entry.

Times are part of the directory object and so of the root: a reader gets them
with any directory, from a snapshot, a path read or an object read, with no
separate request. The objects an entry names stay free of times, so identical
content still hashes identically wherever and whenever it was written. A
directory or tree entry has no time; a reader that wants one for a directory
takes the newest of its entries'.

A time is the editor's stated time, not the host's acceptance time: the client
computes the root it proposes ([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)), so the time must be known before the
host accepts it. An authority rejects an `at` more than five minutes ahead of
its own clock. The accepted update's `acceptedAt` remains the host's time, and
history, not an entry, records when the host accepted it. A date a person means
as content, such as when a page was written, is a page property.

When a merge ([updates and merging §3.2](1.3-updates-and-merging.md#32-the-acceptance-procedure)) combines two sides that both changed an entry, the result
takes the later `modified` of the two, whether or not their objects were
identical; `created` is kept from the basis, or is the earlier of the two when
both sides created the entry.

## 7. CBOR and hashes

Whenever Overstory hashes a structured value, it first encodes that value as
canonical CBOR and then hashes those bytes with SHA-256. The section that
defines a particular hash defines the value being encoded; this subsection
defines the common structured-value encoding.

The permitted CBOR subset is: `null`; booleans; integers in the safe 53-bit
range as CBOR integers with minimal-length heads; every other finite number as
a 64-bit float; UTF-8 text; byte strings; arrays; and maps whose keys are text,
unique, and ordered by the bytes of their encoded form. Non-finite numbers,
indefinite lengths, tags, and non-text keys are invalid, except that date
values in page properties ([pages](#51-pages)) and in rows
([collections §2](1.4-collections.md#2-rows-and-values)) use tags 1004
and 0. Times the host or client stamps, such as an entry's `modified` or a
row's `created`, are integers of Unix milliseconds, never tagged.

An Overstory object's bytes are `fileBytes` for a file, or
`canonicalCBOR(directory | page | table | rows)`, and its hash is
`sha256(objectBytes)`. Wherever objects travel, in a snapshot bundle, an
`objects` array or an object read, only the bytes travel: the receiver hashes
them, and graph validation separately requires each directory, page, table or
rows object to decode canonically.

Model hashes, collections' logical hashes, update and mutation
request digests, and query output hashes apply the same CBOR-then-SHA-256
procedure to the distinct structured values defined by their own contracts.
They are not hashes of an Overstory object unless their contract says so, and
nothing in Overstory is identified by canonical JSON text.

When the value being identified is already an exact byte sequence, Overstory
hashes those bytes directly instead, as for a file object. A collection's
`modelFingerprint` is instead the canonical CBOR hash of its checked model
([schema language §9](1.5-schema-language.md#9-fingerprints)), so it does not
change with the schema's comments, formatting or storage and presentation
attributes. The
[`canonical-cbor-values`](conformance/canonical-cbor-values.json) vectors
freeze valid encodings and rejected byte sequences for every language binding.

## 8. Mapping files and directories to nodes

A directory projects one node. Its ordinary entries supply the node's child
set; reserved body and schema entries instead supply the node's content or
the interpretation of its children. Its own
content lives inside it as `x/_index.md`, so a node that has children keeps
everything in one place. A node may instead keep its content beside the
directory: `x.md` supplies the content of `/x` when `x/` has no `_index.md`,
and the sibling directory `x/`, if present, still supplies the children.
A body is a Markdown page (`x.md`, `x/_index.md`) or a view (`x.view`,
`x/_index.view`), a file written in [UVL](4.1-apps-and-views.md#21-view-files)
that follows the same placement rules; a page may also hold view blocks.
URLs, API paths, and visible names use extensionless logical paths for pages and views; a relative link
written in Markdown names the body file itself and resolves from the directory
that holds the file containing it ([locators §2.1](1.6-locators.md#21-links-written-in-markdown)).

`_index.md` takes precedence. When both `x/_index.md` and a sibling body exist,
`_index.md` is the node's content, the sibling body is not part of the model,
and a conforming implementation reports `shadowed-body` as a diagnostic so a
person can remove or merge the sibling; the node stays readable and editable.
A file entry named `x` beside a body `x.md` likewise claims the
node `/x` twice, and so do a page and a view at the same place (`x.md` and
`x.view`, or `x/_index.md` and `x/_index.view`): the implementation reports
`duplicate-node-representation`, and the node reads its Markdown body.

A sibling body and `x/` coexist as one logical node. Creating a child does not
move or rename the content. Merely reading a contentless directory does not
create `_index.md`; the first edit of its content, properties or `id` writes
it. Rename, move, copy, trash, and restore treat
sibling content and its directory as one logical unit and never silently merge
an occupied destination.

Because relative links resolve from the directory holding the file that
contains them, a body that changes form or place (a sibling `x.md` replaced by
`x/_index.md`, or any rename or move) moves the base of its own relative
links, and links elsewhere that spell its old file name go stale. The writer
that makes the change rewrites the moved body's relative links against its new
directory in the same change and heals the links that name it as for any
other move ([locators §4](1.6-locators.md#4-resolution-rules)). A reader still
resolves a stale `x.md` spelling to the node `x`.

## 9. Properties, Markdown content, and identity

A Markdown file's frontmatter is a placement's spelling of a page's properties
([placements on disk §2](2.2-placements-on-disk.md#2-pages-on-disk)); the
remainder is the page's body. The property API and the Markdown editor
therefore address one page rather than parallel record and document state.

Every `.md` file is a page, held as a `page` entry: `_index.md`, sibling
bodies and every other Markdown file in the projection. A file whose frontmatter doesn't parse as YAML 1.2 stays a
`file` entry with its exact bytes, and the placement reports
`unparsed-front-matter`; it becomes a page when a person fixes it. Markdown
row files of a collection are rows, not pages
([placements on disk §4.1](2.2-placements-on-disk.md#41-file-projections)).

A [property write](1.3-updates-and-merging.md#31-exact-state-preconditions) leaves
the body unchanged, and a body edit leaves the properties unchanged.

A page may carry an opaque durable `id`: the stable key selected by the
tree's identity declaration, any non-empty value, encoded and addressed as
[locators](1.6-locators.md#2-stable-keys-revisions-and-fragments) specify.
The page object holds it apart from the properties. A placement writes it as
the first frontmatter key, `id:`, so it still reads as a property, but it
cannot be changed through an ordinary property update and remains stable
across rename and move.

```md
---
id: a1b2c3
title: Atlas
---

# Atlas
```

A page's body is exact source: an untouched body round-trips byte-for-byte
through every placement. Property order is part of the page; how frontmatter
spells, quotes and comments it is each placement's own
([placements on disk §2](2.2-placements-on-disk.md#2-pages-on-disk)). Editor
block IDs and caches are neither modeled nor authored source.

## 10. Pages with children

A client presents a node with children whose body is Markdown, or absent, as one
operational Markdown document, formed from its stored body
([data model §8](1.1-data-model.md#8-mapping-files-and-directories-to-nodes))
or an empty implicit body. Authored
placement and child membership are distinct:

1. Walk standalone links in source order. The first link that resolves to each immediate child represents that child at its authored position. Inline links never qualify, and later standalone links to the same child remain ordinary duplicate links.
2. Every otherwise-unmentioned immediate child belongs to the document's remainder, which stands after the authored source: a page's children stand at its end ([§10.1](#101-presented-headings)). Source has no syntax that places the remainder elsewhere.
3. The provider enumerates the remainder in canonical logical-path order and may page or virtualize it rather than expanding one literal source link per child. Reading, rendering, indexing, searching, backlinks, hosted output, and export consume the same placement model.

Reading an implicit body or its remainder does not materialize either. The first authored
content/property/placement write persists only the exact authored source; it
does not serialize the remainder.

Link ordering, nesting, labels, and deletion are ordinary source edits. Removing
an explicit child link returns that child to the remainder; it never deletes the
target. Create, move, rename, copy, delete, restore, and row mutations are
explicit structural or provider operations. Filesystem entries, collection
rows, database tables, database records, and mounted boundaries are all children
when their provider exposes them as such. A transient query result is not a node
or child unless an explicit materialization operation creates one.

Links use [Overstory locators](1.6-locators.md). Relative and tree-rooted logical
paths are valid within a resolved tree; cross-tree links use canonical or raw
TreeID locators; a document-link row naming a node in the same tree is a
relative link, not an `overstory://` locator. A relative link names the target's
body file and carries its stable key as `#overstory-key=<key-token>`, as
[locators §2.1](1.6-locators.md#21-links-written-in-markdown) defines. When its
readable path and valid stable key disagree, the key selects the node within
its declaring keyspace and the authored content may be healed through an
ordinary mutation that rewrites only the link's destination; the key,
application query, and content fragment survive. Overstory renderers translate
the alias to the server-visible path suffix before emitting HTTP links. Nodes
with a null stable key remain path-identified.

### 10.1 Presented headings

A client that presents an operational document as a page shows two headings
that its source may lack. Neither is authored source.

- **Title.** When the body does not begin with an H1, the page opens with a
  presented H1 naming the node: the last segment of its logical path, which is
  the body file's name without its extension, or the directory's name for
  `_index.md`, with each hyphen shown as a space.
- **Subpages.** When the remainder is not empty, the page is followed by a
  presented `# Subpages` H1 over the remainder's generated links. It closes
  every authored section above it, so the remainder never reads as part of the
  last authored section.

Clients show a presented heading, and the generated links of a remainder, so
that they read as derived from the tree rather than written: Story mutes
them. Once written they read like any other content.

Indexing, searching, fragment targets, and transfers of authored blocks
ignore presented headings, and a presented heading cannot be deleted: an
authored first H1 removes the title, and a link to every child removes the
Subpages heading. A selection that includes one carries only authored source, so moving
a page's last section leaves the remainder with the page. Hosted output renders
presented headings as a client does.

Editing the presented title materializes it through an ordinary content write:
it is written as the body's first H1, and it does not rename the node. The
Subpages are not editable: they stand outside the page's content. A reader
places a child by linking it in the page, as dragging a generated link into
the page does, which writes an authored standalone link where it lands. A
standalone link to a child dropped on the Subpages is removed, so the child
returns there; the child itself is untouched.

## 11. Recognized authored files

- `schema.usl` declares a collection's models, stable key, and optional
  logical-name rule in the [schema language](1.5-schema-language.md), as
  [collections](1.4-collections.md) specifies. No
  other file name selects a collection schema; a `schema.ts`, for example, is
  an ordinary file.
- `_store.csv`, `_store.json`, `_store.jsonl`, `<Table>.csv`, `.json` and
  `.jsonl`, Markdown row files and `_store.sqlite3` in a collection's folder are
  a placement's [projection](2.2-placements-on-disk.md#4-projections) of its rows,
  not tree entries.
- A `.view` file is a node's body: its unnamed view is the node's view, and it may also declare named views, rules and mutations; a fenced `view` block in a page does the same inside the page. Both are specified by [apps and views](4.1-apps-and-views.md). Files of other extensions, `.ts` and `.tsx` included, are ordinary files.
- Markdown files may define agents as specified by [apps and views](4.1-apps-and-views.md#12-agents).

These recognizers do not make generated declarations, compiled bundles, database credentials, or execution transcripts part of this format unless they are themselves deliberately authored ordinary tree content.

For a collection's folder, `schema.usl` remains an exact authored file entry in the protocol graph, while the directory's
`collection` reference holds the rows as the complete immediate logical child
set. `_index.md` may still supply the folder node's own content, and other
ordinary files stay ordinary entries, but expanded child folders beside a
collection's rows are invalid. The reference's Overstory shape is defined with
[reading and watching](1.2-reading-and-watching.md#112-reading-an-accepted-snapshot);
its validation is defined by
[collections §1](1.4-collections.md#1-what-the-tree-holds).

## 12. Reserved names and sidecars

- `_index.md` is its directory's own content and is never exposed as a child.
- A collection's projection files ([§11](#11-recognized-authored-files)) are never tree entries or row children.
- `.state` is forbidden in a tree configuration graph as specified by [accounts and devices](3.1-accounts-and-devices.md#2-tree-configuration-graph).

A client's local account file, credentials, access-link secrets, private indexes, journals, recovery databases, and private device keys are never tree content.

## 13. Other constraints

Names reject NUL, slashes, backslashes, dot segments, non-NFC text, and
reserved ambiguity. Directory entries are canonically ordered.
