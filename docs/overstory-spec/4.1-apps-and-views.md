# Apps and views
*Part of the [Overstory spec](README.md), layer 4 (apps): views, rules and mutations written in the Overstory view language, in `.view` files and in view blocks in pages, and agents. Their addresses, reads, mutations, state, user identity, hosting and consent. The language itself is §15.*

*Owns: view and handle identity, the view language, view and mutation semantics and their routes, view and model state, user context, checking, hosting, the consent statement, and the no-ambient-authority rule. References: the [data model](1.1-data-model.md) for synchronized values, the [schema language](1.5-schema-language.md) for models and types, and [§15](#15-the-language) for syntax.*

Overstory adds no application object, application identifier, entry component, route table, or location language. An app is an Overstory tree holding ordinary pages, views and collections. A host that supports execution serves a view at its node's own address.

No general-purpose code runs in an app. A view is declarative: its reads are plans the host finds in the source alone, its markup is a view tree, and its mutations are sets of row operations. Extending the data with code of a general-purpose language is not yet specified ([USL plugins](../../plans/later/apps-014-usl-plugins.md)).

## 1. Views and their addresses

A **view** ([§4](#4-views)) lives in one of two places:
- **A `.view` file** is a node's body, as a `.md` file is
  ([data model §8](1.1-data-model.md#8-mapping-files-and-directories-to-nodes)):
  `List.view` supplies the node `/List`, and `views/list.view` the node `/views/list`.
  The file's unnamed view is that node's view, and the file may also declare named
  views, rules and mutations.
- **A view block** in a page ([§15.7](#157-view-blocks-in-pages)) is a fenced code
  block whose info string is `view`. A block that is just an element draws where it
  sits. A named view in a block, `view Drafts(): …`, can be addressed from elsewhere,
  and draws there too when it takes no parameters.

A view's address is its node's address, like a page's. In a tree holding:

```text
Home.md
List.view
Notes.md            (holding a view block `view Drafts(): …`)
parts/cards.view    (declaring `view PracticeCard(p: Practice): …`)
data/schema.usl
```

`List.view` is the view at `List`, spelled the same way in each place it is used:

- **Embedded,** by a link to it alone on its own line in a page, it is drawn in
  place in that page.
- **Linked,** by an ordinary link in text, it opens as its own page.
- **Requested,** `GET {canonical URL}/List?id=…` serves it
  ([§10](#10-rendering-actions-and-live-data)).
- **Used,** `use "List.view"`, its named views, rules and mutations become
  available to the using file ([§3](#3-files-and-named-handles)).

```md
[](List.view?id=42)

Open [the list](List.view?id=42) on its own.
```

As for any page, a link written in Markdown names the body file and every emitted
locator drops the extension ([locators §3](1.6-locators.md#3-parsing-and-canonicalization)). A view
embedded with no query string of its own receives its page's query string.

A named view is addressed by its source with a `view` parameter naming it,
`Notes?view=Drafts` or `parts/cards?view=PracticeCard`, and a declared view ([§4.4](#44-declared-views)) by its schema
file with a `view` parameter naming its entry's label, `data/schema.usl?view=by-tag`,
in the embedded, linked and requested places. A view block with no name has no address
of its own. There is no default: a page without `view` is the page, a `.view` file
without `view` is its unnamed view, a schema file without `view` is the schema's
source, and a name that isn't declared there is not found. A `.view` file with no
unnamed view supplies its node all the same, and that node draws nothing.

The tree's shape never depends on code: a `.view` file is a body whether or not it
checks, and a file of any other extension, `.tsx` included, reads and embeds as source.

Links resolve as [locators](1.6-locators.md) define. A same-tree host may
intercept an ordinary link for client navigation, but the link must remain
correct as an ordinary HTTP navigation with JavaScript absent. Back, forward,
reload, open-in-new-tab, and copying the URL use browser semantics rather than
a parallel application history.

The query string is the view's input. A name that occurs once becomes its
string, a repeated name an array in order, and an omitted name is absent; the
view's typed parameters ([§15.2](#152-views)) convert and validate the result
before any data access, as for a form ([§15.4](#154-actions-forms-and-events)).
Apart from `view` naming a view, there is no reserved parameter, generated
link constructor, or global list of allowed query keys. Unknown parameters are
ignored.

The optional path-attached `;overstory-key=...` identity suffix is consumed
before the view is resolved and never reaches its input. It can therefore heal
or redirect a renamed view without taking a query parameter away from it.
Healing preserves the complete query string unchanged.

Fragments retain ordinary document-fragment behavior. Node identity, server
rendering, authorization, metadata, and initial reads cannot depend on fragment
data unavailable to the server.

## 2. Source forms

`.view` files and view blocks in pages hold views, rules and mutations
([§15](#15-the-language)); `.usl` files hold the models they read and write
([schema language](1.5-schema-language.md)). Nothing else is executable source for
an app. A page's prose stays non-executable Markdown: a page runs nothing because it
embeds or links a view, and a view block shows as an ordinary code block wherever
views aren't evaluated.

Structured editors that cannot preserve `.view` source or a view block exactly must use a raw or code-capable mode. They never rewrite it as ordinary Markdown.

Views, rules and mutations have no ambient authority. The language has no
filesystem, network, process, clock, randomness, credential, secret, or host
API: a view's only inputs are its parameters, the user ([§9](#9-overstory-user-identity)),
its state ([§4.5](#45-state)), its page ([§15.7](#157-view-blocks-in-pages)) and the
rows it reads, and a mutation's time and generated IDs come from its runner
([§5](#5-mutations)). Events a client delivers, such as a key press or a timer
([§15.4](#154-actions-forms-and-events)), reach a view only as actions it names. This
is the single normative statement of that rule; other sections refer to it.

## 3. Files and named handles

A **source** is a `.view` file, or the view blocks of one page taken together. A source
tree is identified by its existing `TreeID`; Overstory adds no application-ID or
script-ID namespace. `(TreeID, logical path, name)` identifies a named handle:
- a `.view` file's unnamed view, by its node's path and an empty name;
- a named view, by its source's path and the view's name;
- a view block with no name, by the page's path and `#n`, its position among the page's
  unnamed views counting from 1, which only the page's own presentation uses;
- a mutation, by its source's path and its name.

A source's code version identifies the handle's version
([§7](#7-compilation-and-hosting)). Moving a source or renaming a declaration creates a
different handle; changing a source a handle uses changes its version.

`use "path"` makes another source's named views, rules and mutations available by
name. The path names a `.view` file or a page as a Markdown link would, relative to the
using source; another tree's source is named by an absolute Overstory locator and
resolves to one immutable code version for one build or execution. Names a source
declares shadow the names it uses. Two used sources declaring the same name is a
check error at the point of use. A source can't use itself, directly or through others.

Every model a source reads or writes is named by a USL model reachable from it: a
source binds the collection schema of its folder or nearest ancestor that has one, and
`use "data/schema.usl"` binds another. Checking resolves each model, field and path
against those schemas, and fails on a name it can't resolve.

For each handle, checking exposes its parameters and their types, its code
version, the models and paths it reads and writes, and public result metadata,
without disclosing source a caller may not read.

The tokens this section introduces, and what each survives:

| Token | Identifies | Minted by | Survives |
|---|---|---|---|
| handle | one view or mutation, as `(TreeID, logical path, name)` | the author | code changes; not a move or a rename |
| code version | one checked source and everything it uses | hashing ([§7](#7-compilation-and-hosting)) | moving the source tree; prose edits in a page; not a change to any source it uses |
| model fingerprint | one collection schema's model layer ([schema language §9](1.5-schema-language.md#9-fingerprints)) | hashing the checked model layer | storage and presentation changes; not a model change |

## 4. Views

A **view** is a view tree ([§15.3](#153-elements)) whose elements may carry
reads. Its **plan** is every read in it and in the views it draws,
found by checking the source, not by running it ([§4.6](#46-plans-and-live-dependencies)).
What the host reads depends only on the view's input and the user. Conditions
that read state are evaluated on the viewer's device instead ([§4.5](#45-state)).

### 4.1 Reading rows

`for` on an element introduces names and the rows they range over
([§15.2](#152-views)):
- **A model's rows:** `for={l in List}`.
- **A relationship's rows,** from a name already bound: `for={t in i.practice.tags}`.
- **Several names,** separated by commas; a later one may range over an earlier one:
  `for={p in Practice, other in p.authors}`.

A **path** follows fields from a bound name: `l.owner.name`, `i.practice`. A path
through a to-many field reaches every row it leads to, without duplicates:
`l.items.practice.authors` is everyone who wrote a practice on the list. Paths may
be read anywhere an expression is allowed, and a plain relationship read needs no
`for`: `<Avatar person={l.owner} />`.

### 4.2 Facts

`where` holds the conditions a match must meet, as boolean expressions joined by
commas, which mean *and* ([§15.6](#156-expressions-and-built-ins)):

| Condition | Means |
|---|---|
| `l.visibility == "Public"` | a field equals a value |
| `q in p.name` | a text field contains text |
| `l.owner == person` | a to-one relationship points at a row, a key, or `null` |
| `person in p.authors` | a to-many relationship includes a row or a key |
| `person in l.items.practice.authors` | a path: some item's practice has this author |
| `a or b`, `not a` | alternatives and negation |
| `curatedBy(l, person)` | a **rule**: a named condition defined once ([§15.2](#152-views)) |

Each condition is a fact over the names in scope, and a name that appears in two
facts joins them. A view's reads are its facts: there is no other narrowing, and
nothing else in a view decides which rows it reads.

A model's **read rules** keep private rows from being disclosed. They belong to the data,
not to any view: the host adds them, as facts, to every read of that model, whether the
read is a `for`, a path or a condition. A view can narrow further but never past them,
and a view that forgets them still can't see a hidden row. Supplies' rule is "a list is
readable when it is public, or by its owner".

`orderBy` orders an element's matches and `limit` cuts them
([§15.3](#153-elements)). Both are part of the plan.

### 4.3 Expansion

An element with a `for` **expands**: it appears once for each distinct combination of
values of the names it introduces and uses, in its attributes, its text or anywhere
among its children. A name it introduces but uses only in `for` and `where` joins
without multiplying the element. So

```
<Avatar person={other}
  for={p in Practice, other in p.authors}
  where={person in p.authors, other != person} />
```

draws one avatar per collaborator, while a `Text` that shows both `{other.name}` and
`{p.name}` draws one line per pair.

An element with `where` and no `for` appears when its conditions hold and not otherwise.
`fallback` gives what to draw when an element expands to nothing or its conditions
don't hold.

Inside an element, the names its `for` binds are fixed. A nested element's reads
therefore run once per match of its ancestors, and the result is tree-shaped:
`<Badge for={t in i.practice.tags} where={t.list == l}>` inside an expansion over a
list's items draws each item's tags for that list.

A name that no `for` binds and no parameter or state declares is a check error.

### 4.4 Declared views

A schema's `~views` ([schema language §8](1.5-schema-language.md#8-views)) are
**declared views**, defined there. A client may draw one's result with its own native list.

Declared and authored views are one kind:
- A host serves either through [§12.1](#121-evaluate-and-stream-views), with the
  same plan, authority, live behavior and result forms.
- A client draws either wherever a view can appear, including on a page that presents a
  collection.
- Both are named the same way ([§12.1](#121-evaluate-and-stream-views)): a tree,
  the logical path of a `.view` file or a schema, and a view name or a `label`.

### 4.5 State

All state is rows, which differ in who shares them and how long they last:

| | kept | this session |
|---|---|---|
| **everyone at a placement** | `page model` | not yet specified |
| **one viewer** | `personal model`, `keep` | `personal session model`, `state` |

- A **placement** is one embed of a view in one page. A view drawn on its own has one
  placement per page address.
- A **page model** ([schema language §3](1.5-schema-language.md#3-models-and-fields))
  holds rows shared by everyone who sees a placement, such as a widget's configuration.
  Its rows are written with mutations like any others.
- A **personal model** holds one viewer's own rows. `personal model X (placement)` gives
  each viewer one set per placement; without `(placement)`, one set per app. A personal
  model's rows are read and written only by their viewer, need no consent, and are written
  on the viewer's device first.
- A **session** model's rows are never stored and live for one viewer's session on one
  device. They suit fast-changing state, such as the positions in a game.
- `state x = value` in a view declares a one-row personal session model with one field,
  and `keep x = value` a one-row personal model per placement. Both are read by name like a
  parameter and changed with `set(x, value)` ([§15.4](#154-actions-forms-and-events)).
  A view drawn as an element inside another view has its own `state` and `keep` for each
  instance, told apart by the element's `key`.

A view reads state the way it reads any rows, and changing state reevaluates only the
expansions that read it.

**State never leaves the viewer's device.** Checking splits each read: the conditions,
orderings and paths that don't read `state`, `keep` or a session model form the plan the
host runs, and those that do are evaluated by the client over the rows the host returns.
So a host never learns state, and a state change redraws without a request. Inputs are
the opposite: they are what the host sees and what a URL carries. A view that wants the
host to filter by a value, for example a search over many rows, takes it as an input
(`?q=…`), which also makes it linkable. A `limit` on an element whose conditions or
ordering read state is a check error, because the host can't cut what it can't order;
the value must be an input instead.

Where page and kept personal rows are stored, and how they reach the viewer's other
devices, are not yet specified ([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)).

### 4.6 Plans and live dependencies

A view's plan is a deterministic function of `(resolved node snapshots, validated
input, trusted user context)`. Its only data door is a finite, declarative
selection over the scoped logical node model, written as the view's `for`,
`where` and paths. A collection's model is a typed node set, not a separate
universe, and a model's rows mean the same in expanded directories, Markdown
records, collection files, and SQLite projections. Every result retains
tree-scoped provenance internally even when the view shows none of it.

A plan means the same whichever representation holds its rows: a host may run
it as SQL, through indexes, or by tree traversal, but cannot change its
meaning. Matches have automatic deterministic ordering by canonical stable key,
falling back to canonical path, unless `orderBy` orders them. Paths, counts,
`exists`, ordering and limits are baseline ([§15.6](#156-expressions-and-built-ins)).
Grouping beyond expansion by a value, other aggregates, pagination operators,
and unbounded traversal are capability extensions rather than baseline semantics
([deferred 6](README.md#deferred)). An unavailable capability fails at checking
rather than silently loading an entire tree.

Before a plan reads or a mutation's transaction begins, the host verifies each
model's binding `(TreeID, logical path, schema fingerprint)` against the mounted
tree, the selected collection, and its active schema. A binding is fixed by the
file in which it was written. An unbound, ambiguous, stale, or differently
resolved binding makes the handle inactive rather than redirecting it to a
same-named collection.

Live behavior is intrinsic to a view. A one-shot caller evaluates its current
value once; a subscribing caller maintains that same value as a stream of
authorized complete states, never raw driver changes, with the no-gap,
deduplication, and coalescing guarantees of
[§12.1](#121-evaluate-and-stream-views).

A plan's live dependencies are a set of (observation cursor, precision scope)
entries: the narrowest proved nodes, child membership, property/content
fields, edges, schema fingerprints, mounted roots, and profile/access facts
that can affect the result, each bound to the cursor it was read through
([tree watching](1.2-reading-and-watching.md#113-watching)). The host follows
them through tree watches or conservative subtree invalidation. Observation precision is an
optimization and cannot change the result.

For a model's rows, execution samples the resolved parent before reading
child pages and retains its child membership, schema fingerprint, and
the tree's accepted `update` as a membership dependency. Continuation cursors are
bound to the membership update used to create them. A subscriber follows or
replays from the retained pre-read update; therefore an insertion or removal
that races sampling or paging forces a rerun and cannot fall into a
snapshot/observation gap. Per-child precision may narrow property invalidation
but does not replace the parent membership dependency.

A plan whose nodes are not materialized locally may be run by the relevant
server when that host enforces the same validation, access, determinism, and
version contract. A read-only placement projection may
materialize a reviewed plan into SQLite and serve its last completely
applied state offline. This specification does not define general cross-server
plan discovery, delegated authorization, or server-to-server routing
([deferred 2](README.md#deferred)).

## 5. Mutations

A mutation ([§15.5](#155-mutations)) is a named set of row operations over the
models its file binds. Its statements all read the state as it was before the
mutation began, and together produce one set of operations, so the order of
statements doesn't change the result. Two statements writing different values to
the same field of the same row are a check error when checking can prove it and
a public `conflict` error otherwise.

A mutation's parameters are typed with USL types. A parameter typed with a model
receives a key, resolved to that model's row before any other statement runs; a
key with no row fails the mutation with `not-found`. Every `require` guard is
checked before any write, and the first that fails ends the mutation with its
public error.

A mutation runs as its caller, with the authority
[access control §1.1](3.2-access-control.md#11-execution-authority) gives its
code. Its guards narrow behavior within that authority. There is no
mutation-permission namespace and no implicit whole-tree write.

A mutation runs in one runner-owned transaction: its reads, guards, writes and
receipt commit together, and a failed guard writes nothing. Its writes reach
their tree as one ordinary update, guarded by the state the mutation read
([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)); a
stale guard reruns the mutation rather than merging a stale decision. Because a
mutation is declarative, a client may evaluate it against its own copy of the
rows to show the result at once; the host's run is authoritative.

The caller supplies one mutation identity and reuses it for an ambiguous retry;
[§12.2](#122-execute-named-mutations) defines the request digest
that binds it to the handle, code version, validated input, and activated
source bindings, the replay scoping, and the receipt. The runtime captures one
logical mutation time (`now`, `today`) and deterministic generated-ID namespace
before execution; exact retries observe the same values. The runtime records the
retry identity and its result so that, after a restart, a committed mutation is
never mistaken for one that never ran.

Mutations that span several trees, durable workflow steps, portable
foreign-key actions, and external non-tree effects are not yet specified
([Apps 006](../../plans/later/apps-006-durable-authoring.md),
[deferred 3](README.md#deferred)).

## 6. Drawing other views, imports, and consent

A named view drawn as an element ([§15.2](#152-views)) reads only through its own `for`,
`where` and paths, which join the plan of each view that draws it. Drawing another view,
or using a source from another tree, acquires no grants: what a view may read and a
mutation may write is decided by its caller's authority alone.

Before code first uses anything beyond what needs no lender
([access control §1.1](3.2-access-control.md#11-execution-authority)), the
client shows a **consent statement**: the resolved trees, the models and paths
the code reads, the rows its mutations write, and the access it asks to be lent.
Because reads and writes are declared, the statement can name them exactly; a
computed path stays visibly broad, and enforcement must make the statement true.
A host process's broader filesystem or credentials never become an app's
capabilities. Named handles are callable from human clients and agent tools
with the same identity, validation, and authorization.

## 7. Compilation and hosting

A source's **code version** is the SHA-256 over the paths and source text of
the sources and schema files it uses, transitively, in path order. A `.view`
file's source text is its bytes; a page's is the text of its view blocks in
order, so editing a page's prose changes no code version. A source's path is
ordinary Overstory identity, not an application ID: moving it changes its
views' addresses just as moving any other node changes its URL.

Adding a view does not publish it, run it, or grant it access: a host runs
views and mutations only for trees whose hosting it has enabled. It may check
eagerly or on demand, but a request uses one coherent code version of the
addressed view and all of its handles, and a source that fails checking never
replaces the last usable version.

A reviewed manifest of what checked code needs, and static baking of reads,
are not yet specified
([Apps 010](../../plans/later/apps-010-activation-and-lending.md)).

## 8. Data disclosure

Access to a collection and access to an app's results are distinct. A public
view may read a private tree, but only what it draws is disclosed: raw stores,
credentials, private source, diagnostics containing private values, and
unrelated rows never reach the browser or a public response. Conversely,
public and private rows in a publicly readable tree are exposed by the tree's
own bytes whatever a view filters, so row-private data lives in a private tree,
or in separate trees, behind views that publish only their results.

Views and mutations never see the caller's credentials, and code identity
asserted in public input never establishes execution authority
([access control §2](3.2-access-control.md#2-authentication-and-secrets)).
A revocation reaches running views and mutations, not merely the request that
started them.

## 9. Overstory user identity

Apps define no password, sign-in or session model of their own. The host
resolves the caller's Overstory session and gives views and mutations an
unforgeable user context: `me`, the caller's profile `TreeID` or `null`, and
`community`, the `TreeID` of the community the caller is signed in to, or
`null`.

Account IDs, device IDs, credentials, and handles are not user identities to
an app, and no parameter can stand in for `me`. Rows referring to a person
store that profile's `TreeID`; display name, handle, portrait, and other public
profile fields are read from the profile tree when the view runs, as live
dependencies, so a profile edit updates the views streaming it.

A mutation that needs a signed-in caller guards with `require me != null else
user-required`; a client receiving `user-required` presents its host's sign-in.
A view shows signed-out readers its `fallback`. The host rechecks the session
on each request and stream; revocation ends existing streams.

Anonymous and signed-in executions are separate cache and subscription
contexts. A view that reads `me` records the identity and access decision as
dependencies, and a result is shared between callers only when its inputs,
authorization, and output are genuinely user-independent.

## 10. Rendering, actions, and live data

The host resolves the requested path to a view, loads one coherent code version,
converts the query string to the view's input ([§1](#1-views-and-their-addresses)),
and answers in one of three forms:
- **HTML**, for a browser `GET`: the view tree rendered with the state's initial
  values, with only what it draws embedded.
- **Rows** ([§12.1](#121-evaluate-and-stream-views)): the plan's authorized rows,
  annotated with field types and row identity, for a client that evaluates the
  view itself. The client evaluates the conditions that read state
  ([§4.5](#45-state)) and draws, so state changes redraw without a round trip.
  This is also the form for a program that wants a view's data.
- **Tree**: the view tree, evaluated by the host with the state's initial values,
  for a client that draws but doesn't evaluate. Such a client can't change state.

The host keeps rows and trees current through the same live stream
([§12.1](#121-evaluate-and-stream-views)). A client holding a placed tree may
evaluate a view against its local copy instead.

A mutation is used from a view as an action ([§15.4](#154-actions-forms-and-events)).
A client may show its result at once by evaluating it locally ([§5](#5-mutations));
that optimistic presentation never displaces the subscribed result as the source of
truth.

## 11. Portability

The same source may be served by any compatible local runtime or
server that provides its declared nodes and runtime features. A handle
means the same thing whether expanded children, collection files, or a
placement's SQLite projection supplies its source; schema compatibility,
model fingerprints, and data migration are checked before a new handle
version is used. Cross-server execution never acquires authority merely
through network reachability.

## 12. Overstory operations

Apps use two operations. Views derive current permissioned values without
exposing raw stores; mutations execute reviewed transactional intent. Neither
is accepted-tree synchronization, even when a mutation also advances a data
tree.

### 12.1 Evaluate and stream views

```text
QUERY /.overstory/trees/{SourceTreeID}/views
Content-Type: application/json
Accept: text/event-stream
```

The request names every view a client currently shows from one source
tree. A server without an app runtime, or without hosting enabled for the
source tree, returns `422 unsupported-operation`.

```ts
/**
 * Names a view or a mutation: a name in a source in a tree (§3). For an
 * authored handle, `path` is the logical path of a `.view` file's node or of a
 * page, and `name` is empty for a `.view` file's view, a view's or mutation's
 * declared name, or `#n` for a page's unnamed view. For a declared view
 * (§4.4), `path` is a collection's `schema.usl` and `name` a `~views` label.
 * `version` is the source's code version (§7) or the schema file's object
 * hash. The host tells which kind it is from the node at `path`.
 */
type HandleRef = {
  tree: TreeID;
  path: LogicalPath;
  name: string;
  version: Hash;
};

type ViewsRequest = {
  views: Array<{
    id: string;
    handle: HandleRef;
    input: unknown;
    /**
     * What to answer (§10). `rows`: the plan's authorized rows, for a client
     * that evaluates the view. `tree`: the view tree, evaluated by the host.
     * Defaults to `rows`.
     */
    form?: "rows" | "tree";
    knownOutputHash?: Hash;
  }>;
};

/**
 * Annotations on a `rows` answer, parallel to its JSON.
 * `row` is set on an object holding one row (its model and key).
 * `type` is set on a field's value (that field's schema type, as in schema
 * language §3). `fields` and `items` describe an object's members and an
 * array's elements.
 */
type ResultShape = {
  row?: { model: LogicalPath; key: string };
  type?: string;
  fields?: Record<string, ResultShape>;
  items?: ResultShape[];
};
```

Every handle's `tree` must equal the route `SourceTreeID`. The `views` array
is nonempty and its IDs are nonempty and unique within this request. The host
verifies each handle's code version, its input against the view's declared
types, the user context, effective access, and the schema fingerprints the
view's models were bound to. A request carries no state ([§4.5](#45-state)). The request and events are independent of whether those nodes are
expanded files, collection files, or SQLite. A
`knownOutputHash` permits omission of unchanged bytes only after fresh
authorization and reevaluation; it is neither
authorization nor evidence of current state. Output hashes are SHA-256 of the
canonical CBOR encoding of the complete public result.

A view's live dependencies are conservative: an ordinary read of a model's rows
depends on its resolved parent's membership and schema, the sampled child
identities and model hashes, and every field used by a condition or drawn.
Narrower dependencies are an optimization, and missing precision never skips a
reevaluation.

The UTF-8 SSE response has these semantic events:

```ts
type PublicQueryError = {
  code: string;
  message: string;
  retryable: boolean;
};

type ViewEvent =
  | {
      type: "result";
      id: string;
      outputHash: Hash;
      value: unknown;
      /** Field types and row identity for a `rows` answer (§10). */
      shape?: ResultShape;
      error?: never;
    }
  | {
      type: "result";
      id: string;
      error: PublicQueryError;
      outputHash?: never;
      value?: never;
    }
  | {
      type: "ready";
      views: Array<{
        id: string;
        outputHash?: Hash;
      }>;
    }
  | {
      type: "reload";
      reason: "source-changed" | "access-changed";
    };
```

The SSE `event` field supplies `type`; JSON `data` supplies the remaining
members. Each `result` is a complete authorized replacement for one view, not
a raw driver event or patch. `ready` is sent only after every view has
established a race-free snapshot-then-follow boundary. Before `ready`, changed
hashes produce complete `result` values and an unchanged retained value may be
confirmed by its hash in `ready`. Identical output hashes produce no payload.
The observation listener is active before sampling. Events racing evaluation
are checked against both the former and newly sampled dependencies; a relevant
event forces another complete evaluation before that result is published. This
is the no-gap guarantee. It does not require a retained view-event replay log.

`QUERY` has the safe and idempotent semantics defined by
[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008.html). Evaluating or
subscribing to a view never performs a mutation. The response is
user/access dependent and long-lived, so it carries `Cache-Control: no-store`;
automatic retry still reauthorizes and reestablishes current state rather than
reusing a cached body.

The response lifetime is the subscription lifetime. There is no durable
execution ID, acknowledgement, SSE replay cursor, or resumable server-side
subscription. Reconnection repeats and reauthorizes the complete `QUERY`. When
the set of views shown or their inputs change, the client opens a complete
replacement request and retains the old response only until the replacement
sends `ready`. Source or access changes send `reload` when possible and close.
Listener loss, backing uncertainty, process restart, or irrecoverable
backpressure closes rather than publishing a result known to be stale; hosts
may coalesce intermediate complete states.

### 12.2 Execute named mutations

Mutation calls carry the handle identity and version, validated input,
authenticated subject, and caller-stable mutation identity:

```text
POST /.overstory/trees/{SourceTreeID}/mutate
Content-Type: application/json
```

```ts
type MutateRequest = {
  handle: MutationHandleRef;
  mutationID: string;
  input: unknown;
};

type MutationHandleRef = HandleRef;

type MutationResultReceipt<Result = unknown> = {
  mutationID: string;
  requestDigest: Hash;
  /** The accepted update the mutation's writes made, when it wrote. */
  affected?: {
    tree: TreeID;
    update: string;
  };
  /** The mutation's `return` value, or null. */
  result: Result;
};
```

`handle.tree` must equal the route `SourceTreeID`. The host validates the
handle's code version, input, source bindings and authority before data
access. Invocation requires authority to run the handle, not to read its
source. Current authority is checked before every new step and receipt
return. Revocation does not undo committed effects. Missing authority cannot reserve
a new effect or leak private handle/resource existence.
Mutation semantic identity is the SHA-256 of the canonical CBOR encoding of
`{ version: "mutate-v1", handle, input, sources }`, where `sources` is the
activated handle's complete, path-sorted set of
`{ authoredPath, tree, path, schemaFingerprint }` bindings. The bindings are resolved when the handle is activated; a caller-selected destination needs concrete resolution and grant coverage. This prevents an
ambiguous retry from executing the same code and input against a newly resolved
store, relation, or schema. Durable lookup is scoped by the source tree, a
trusted caller replay principal, and `mutationID`. The principal is the
authenticated profile TreeID when present, otherwise the presented access-link
digest identity, otherwise an anonymous identity. It is runtime-only authority:
link digests and replay-principal values never enter a mutation's context,
results, errors, logs, or transcripts. Reusing that identity
with a different request digest is a conflict; an exact ambiguous retry returns
the original receipt and creates no second effect. This is the same committed-
intent pattern as an accepted tree update: transport representation is excluded
from the semantic digest, the subject scopes replay, and `affected` names the accepted update the mutation's writes made: a client
knows a view result reflects the mutation once that tree's watch has passed
that update. The mutate payload remains distinct from `UpdateRequest`: it
carries reviewed intent, while an update carries tree material.

A form submitted from a browser may use the view's ordinary canonical
HTTP action surface, while a named Overstory call uses the endpoint above. Both bind through the
checked handle and preserve this exact request/receipt identity.
The durable receipt and corresponding view result may arrive in either order;
clients correlate them idempotently and treat the view result as authoritative.

### 12.3 Relationship to tree synchronization

`updates`, `watch`, `views` and `mutate` share authentication, semantic digests,
SSE framing, and tree-scoped authorization, but not
transaction or replay domains: `updates` and `mutate` have different conflict
domains, and `watch` has retained replay identity while `views` deliberately
has none. An accepted update requires authority covering its actual effects; a named mutation
requires coverage of the rows it declares it writes. Consolidation
is shared machinery, not one polymorphic endpoint.

View streaming is derived-result delivery, not tree history. A mutation of an
Overstory-canonical data tree advances that data tree's ordinary accepted root and
therefore also causes a `tree.update` watch event; it does not change the
app's source-tree root. Neither execution nor
network reachability independently grants accepted-snapshot access, broadens
the readable tree graph, or exposes raw stores, credentials, private source,
unrelated rows, or private diagnostics. Cross-server plan discovery,
delegated authorization, and server-to-server execution routing remain
unspecified ([deferred 2](README.md#deferred)).

## 13. Agents

A person's own agent run by a client, such as a coding agent working in a
placed folder, edits as its person, through that person's placement, and
appears to others through [presence](1.2-reading-and-watching.md#3-presence)
as an agent of that person. Hosted agents, apps whose body is a prompt with
their own tools, confinement and transcripts, are not yet specified
([Apps 002](../../plans/later/apps-002-overstoryd-hosted-agents.md),
[deferred 4](README.md#deferred)).

## 14. Schema identity

Schema information and explicit relationship declarations are mapped to canonical tree-rooted collection paths so `.view` files remain portable across placements. Relative collection references resolve against the source tree and path before use. A change to a collection's model layer changes its model fingerprint and invalidates dependent checked handles. A storage or presentation change alone invalidates none.

## 15. The language

The view language is versioned with this specification; the sections above define
every semantic guarantee it exposes. A `.view` file is UTF-8 text. `//` starts a
comment that runs to the end of the line.

### 15.1 Files

A `.view` file, or a page's view blocks taken together ([§15.7](#157-view-blocks-in-pages)), is a sequence of declarations, in any order:

| Declaration | Declares |
|---|---|
| `use "path"` | another source or a `.usl` file whose names this source uses ([§3](#3-files-and-named-handles)) |
| `view(params): element` | an unnamed view ([§15.2](#152-views)): a `.view` file's view, at most one per file, or a view drawn where its block sits |
| `view Name(params): element` | a named view, addressable and drawn as an element `<Name …/>` |
| `name(params): condition` | a rule ([§15.2](#152-views)) |
| `mutation name(params): statements` | a mutation ([§15.5](#155-mutations)) |

A parameter is `name` or `name: Type`, with a USL type ([schema language §3](1.5-schema-language.md#3-models-and-fields)).
An untyped parameter is text. A parameter typed with a model takes a row; given a key,
from a query string or a form, it resolves the key through the model's read rules, and a
key with no readable row is `not-found`. A body may follow the `:` on the same line or
start on the next, indented. A view's body may start with `state` and `keep` lines
([§4.5](#45-state)), one per line, before its element.

### 15.2 Views

A view's body is one element. Its parameters are its input, from a query string when it
is addressed ([§1](#1-views-and-their-addresses)) and from attributes when it is drawn:

```
// Profile.view, the view at Profile
use "data/schema.usl"
use "parts/cards.view"

// A rule. Who may see a list is the List model's read rule, which the host applies
// to every read (§4.2), so views don't repeat it.
curatedBy(l, person): l.owner == person or person in l.contributors.person

view(id):
  <Shell title={person.name} subtitle="@{person.handle}"
    for={person in Person} where={person.id == id}
    fallback={<Shell title="Profile not found" />}>

    <Section title="Practices">
      <Grid columns={3}>
        <PracticeCard p={p}
          for={p in Practice} where={person in p.authors}
          orderBy={p.name} />
      </Grid>
    </Section>

    <Section title="Lists featuring their practices">
      <Grid columns={2}>
        <ListCard list={l} for={l in List} where={person in l.items.practice.authors} />
      </Grid>
    </Section>

    <Section title="Lists they curate">
      <Grid columns={2}>
        <ListCard list={l} for={l in List} where={curatedBy(l, person)} orderBy={l.name} />
      </Grid>
    </Section>

    <Section title="Collaborators">
      <Row>
        <Avatar person={other}
          for={p in Practice, other in p.authors} where={person in p.authors, other != person}
          orderBy={other.name} />
      </Row>
    </Section>
  </Shell>
```

A **named view** can be drawn as an element whose type is its name, with its
parameters as attributes. This one, from `parts/cards.view`, is also addressable as
`parts/cards?view=PracticeCard&p=…`:

```
view PracticeCard(p: Practice):
  <Card>
    <Link style="heading" to="Practice?id={p.id}">{p.name}</Link>
    <Row>
      <Text style="secondary">by</Text>
      <Avatar person={a} for={a in p.authors} orderBy={a.name} />
    </Row>
    <Markdown source={p.about} lines={6} />
  </Card>
```

A **rule** is a named condition, `curatedBy(l, person): …`, usable in any `where`. Two rules
with the same name and arity are alternatives, as if joined with `or`. A rule may not
refer to itself, directly or through other rules.

A link to a view is its address, written like any link and resolved from the source
that holds it: `to="Practice?id={p.id}"`.

### 15.3 Elements

An element is `<Type attributes>children</Type>` or `<Type attributes />`. `Type` is a
named view the source declares or uses, or a type of the UI language, whose vocabulary of view types and controls
([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)) a client draws natively or as
HTML. An attribute is `name="text"`, `name={expression}`, or a bare `name`, meaning
`name={true}`. Text children may hold `{expression}`, and so may quoted attribute text:
`subtitle="@{person.handle}"`.

These attributes belong to the language, on any element:

| Attribute | Means |
|---|---|
| `for={name in source, …}` | introduce names and expand ([§4.3](#43-expansion)) |
| `where={condition, …}` | conditions on the element's matches ([§4.2](#42-facts)) |
| `orderBy={expression [desc], …}` | order the matches; ties fall back to canonical order |
| `limit={n}` | keep the first `n` matches |
| `fallback={element}` | drawn when the element expands to nothing or its conditions fail |
| `key={expression}` | the element's identity among its siblings; defaults to the row keys of its names |
| `slot="name"` | which named place in its parent the element fills |

A view tree is plain `{type, props, children, key}` data. `Markdown` renders a Markdown
source string with Overstory's ordinary link resolution, safe URL and asset policy, and
source semantics. It is the standard way for a view to present stored Markdown. It
resolves a relative Markdown destination from the directory holding the source file, as
[locators §2.1](1.6-locators.md#21-links-written-in-markdown) defines. For a destination
carrying the reserved `#overstory-key=` alias, it emits the equivalent server-visible path
suffix and preserves the authored application query. It does not forward the reserved
identity alias as an HTML fragment.

### 15.4 Actions, forms and events

An **action** is a call written as an attribute value: a mutation with its input,
`addPractice(name: n)`, or `set(x, value)` for state. `Button action={…}` runs one when
pressed. A client runs a mutation action with a stable mutation identity and exposes
pending state, then its result, durable receipt, or public error.

`Form action={mutation}` supplies the mutation's input from its controls, by name. Form
conversion is shallow and deterministic: a name occurring once becomes its string or file
value, a repeated name an array in document order, and an omitted name is absent; the
mutation's parameter types convert and validate it. `then={action or link}` runs or
navigates after success. Expected failures are the public errors of `require … else`
([§15.5](#155-mutations)) and input validation, which gives `invalid-input` with field
errors. Server exceptions, private values and stack traces never become action state.

A control's `value={x}`, naming state, binds the control to it in both directions.

A view may name actions for events a client delivers, one per line before its element:

```
on key "ArrowLeft" → movePaddle(-12)
every 16ms → step()
```

A client delivers them only while the view is shown, and at most as often as it can draw.
The view still has no clock: an event can only run an action.

### 15.5 Mutations

A mutation's body is statements, one per line, all reading the state from before the
mutation ([§5](#5-mutations)):

| Statement | Effect |
|---|---|
| `require condition else code "message"` | fail with this public error unless the condition holds |
| `let name = insert Model { field: value, … }` | insert a row and name it; `let` is optional |
| `update row { field: value, … }` | change fields of one row |
| `update name for name in source where … { … }` | change fields of each matching row |
| `delete row`, `delete name for name in source where …` | delete one or each matching row |
| `upsert Model { key fields } create { … } update { … }` | insert or update by key |
| `append row to path`, `remove row from path`, `reorder path to list` | operations on an `ordered` relationship ([schema language §5](1.5-schema-language.md#5-connections)) |
| `when condition` and an indented block | the block's statements apply only if the condition holds |
| `do name(args), …` | include another mutation's statements |
| `return { field: value, … }` | the receipt's result |

`mutation name(row: Model) for Model.op: …`, where `op` is `create`, `edit`, `delete` or
`move`, declares the mutation as that model's row action, so any list of the model offers
it.

A statement may end with `where condition`, which applies it only if the condition holds.
A new row's generated ID comes from the mutation identity, so an exact retry inserts the
same row. Public error codes are words such as `user-required`, `permission-denied`,
`not-found` and `invalid-input`; a message is optional.

```
mutation toggleListReaction(l: List):
  require me != null               else user-required "This operation requires a Story user"
  require l.visibility == "Public" else not-found "Only public lists can be liked"
  delete r for r in l.reactions where r.person == me
  insert Reaction { list: l, person: me, emoji: "👍" } where me not in l.reactions.person
  return { reacted: me not in l.reactions.person }
```

### 15.6 Expressions and built-ins

Expressions are literals (text in double quotes, numbers, `true`, `false`, `null`,
`[a, b]` lists, `{ name: value }` records), names, paths, calls and operators:

| Operators, by precedence | Means |
|---|---|
| `.` | follow a field |
| `not`, unary `-` | negation |
| `*`, `/` | arithmetic |
| `+`, `-` | arithmetic; `+` also joins text |
| `==`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `not in` | comparison; `in` is membership in a to-many path or list, or containment of text |
| `and` | both |
| `or` | either |
| `a ?? b` | `a`, or `b` when `a` is `null` |
| `c ? a : b` | choice |

Built-in functions are pure: `count(path)`, `count(name in source where …)`,
`exists(name in source where …)`,
`sum(path)`, `min(path)`, `max(path)`, `lower(text)`, `upper(text)`, `trim(text)`,
`length(text)`, and `set` in actions. `me`, `community`, `page`, and, in mutations,
`now` and `today` are built-in names. A name a source declares may not reuse a
built-in name.

### 15.7 View blocks in pages

A fenced code block whose info string is `view` holds declarations, or a single element:

````md
# Today

```view
<Text>{count(c in page.children where c.done)} of {count(page.children)} done</Text>
```

```view
view Late():
  <Column>
    <Text for={c in page.children} where={not c.done, c.due < page.date}>{c.name}</Text>
  </Column>
```
````

- **All of a page's view blocks are one source** ([§3](#3-files-and-named-handles)): a
  name declared in one block is usable in every other, and `use` in any block applies to
  all. Other sources use a page's named views, rules and mutations with `use "Today.md"`.
- **A block that is a single element** is an unnamed view with no parameters, drawn
  where the block sits. `view(params): …` in a block is the same with parameters, and
  `view Name(params): …` adds an address, `Today?view=Late` ([§1](#1-views-and-their-addresses)).
  Unnamed views on a page take the page's query string as their input.
- **A named view without parameters also draws where its block sits.** One with
  parameters draws only where it is drawn as an element or addressed, and a block holding
  only those, rules or mutations draws nothing.
- **`page`** is the page a view is drawn in: a block's own page, the page that embeds a
  view, or the view's own node when it is visited by itself. Its fields are the page's
  properties, read as their values with no schema, plus `name`, and `page.children` is its
  child nodes, each read the same way. Reading `page` is a read like any other: it joins
  the plan and is a live dependency.

A client that doesn't evaluate views shows each block as code. Story shows a block's
source while it is being edited and its drawing otherwise.
