# Apps and views
*Part of the [Overstory spec](README.md), layer 4 (apps): views, mutations and agents written as ordinary `.ts` and `.tsx` files and Markdown. Their addresses, queries, mutations, user identity, hosting and consent. The `overstory/data` and `overstory/ui` packages they are written against are §15.*

*Owns: view and handle identity, query and mutation semantics and their routes, user context, compilation, hosting, the consent statement, and the no-ambient-authority rule. References: the [data model](1.1-data-model.md) for synchronized values and [§15](#15-authoring-api) for package surfaces.*

Overstory adds no application object, application identifier, entry component, route table, or location language. An app is an Overstory tree holding ordinary pages, code files and collections. A host that supports execution serves a view at its file's own address.

## 1. Views and their addresses

A **view** ([§4.1](#41-views)) is a value a `.ts` or `.tsx` module exports, made with
`view(input, fn)`. A module's default export, when it is a view, is the file's
view, and only that one is linkable. A view the module exports by name is for
other code to import.

A view's address is its tree and its file's path, extension included. In a tree
holding:

```text
Home.md
List.md
views/list.tsx
views/profile.tsx
components/shared.tsx
data/schema.usl
```

`views/list.tsx` is spelled the same way in each place it is used:

- **Imported,** `import ListView from "./views/list.tsx"`, it composes into the
  importing view and joins its plan ([§4.1.3](#413-implicit-shape-and-dual-evaluation)).
- **Embedded,** by a link to it alone on its own line in a page, it is drawn in
  place in that page.
- **Linked,** by an ordinary link in text, it opens as its own page.
- **Requested,** `GET {canonical URL}/views/list.tsx?id=…` serves it
  ([§10](#10-rendering-actions-and-live-data)).

```md
[](views/list.tsx?id=42)

Open [the list](views/list.tsx?id=42) on its own.
```

A page gives a view a readable URL: `List.md`, whose body is that one embed,
answers at `List?id=…`. A view embedded with no query string of its own
receives its page's query string.

The file stays a `file` entry. The tree's shape never depends on code: whether
a `.tsx` holds a view is learned when it is compiled, and a file whose default
export is not a view, such as a component in an ordinary React project kept in
a tree, reads and embeds as source. A declared view ([§4.1.4](#414-declared-views))
is addressed by its schema file with a `view` parameter naming its entry's
label, `data/schema.usl?view=by-tag`, in all four places. There is no default:
a schema file without `view` is the schema's source, and a label the schema
doesn't declare is not found.

Links resolve as [locators](1.6-locators.md) define. A same-tree host may
intercept an ordinary link for client navigation, but the link must remain
correct as an ordinary HTTP navigation with JavaScript absent. Back, forward,
reload, open-in-new-tab, and copying the URL use browser semantics rather than
a parallel application history.

The query string is the view's input. A name that occurs once becomes its
string, a repeated name an array in order, and an omitted name is absent; the
view's input schema converts and validates the result before any data access,
as for a form ([§15.4](#154-actions-and-forms)).
Apart from `view` on a schema file, there is no reserved parameter, generated link constructor, or global list of
allowed query keys. Unknown parameters may be ignored unless the view's schema
rejects them.

The optional path-attached `;overstory-key=...` identity suffix is consumed
before the view is resolved and never reaches its input. It can therefore heal
or redirect a renamed view file without taking a query parameter away from it.
Healing preserves the complete query string unchanged.

Fragments retain ordinary document-fragment behavior. A view may also use a
fragment for explicitly client-local state, but node identity, server
rendering, authorization, metadata, and initial reads cannot depend on
fragment data unavailable to the server.

## 2. Source forms

`.md` is non-executable authored Markdown, and a page never becomes executable
because it embeds or links a view or because code imports it. `.tsx` modules
export views and components; `.ts` modules export mutations and shared code.
JSX compiles against the UI language's runtime (`overstory/ui`), not React: a
view tree is plain `{type, props, children, key}` data
([§15.2](#152-views)). The pinned compiler version
is part of the coherent code version.

Structured editors that cannot preserve TSX source exactly must use a raw/code-capable mode. They never rewrite executable source as ordinary Markdown.

Executable code (views, query plan callbacks, schema evaluation, and mutation handlers) has no ambient authority: filesystem, network, process, clock, randomness, credential, secret, and host APIs are absent unless a separately specified capability or tool grants them. This is the single normative statement of that rule; other sections refer to it.

## 3. Modules and named handles

Modules export views, mutations and components. `view` and `mutation` are explicit execution-boundary markers; Overstory does not infer a security boundary from an arbitrary export graph.

A source tree is identified by its existing `TreeID`; Overstory adds no application-ID or script-ID namespace. `(TreeID, module file path, export name)` identifies a named handle, a view or a mutation, with `default` naming the default export, and the compiled code hash identifies its version. Moving a path-identified module or changing an export name creates a different handle; changing handler code changes its version.

For each exported handle, compilation exposes stable function identity, input validation, code version, declared or inferred tree access, and public result metadata without disclosing privileged implementation code. Literal tree paths contribute precise prefixes; computed paths require explicit declarations. Compilation fails when code can address an undeclared path, closes over UI-only state, or imports ambient host authority.

A handle may declare an input schema in the [§15.3](#153-mutations)'s
Standard Schema form. The handle's call input is the schema input type; the
query plan or mutation handler receives its validated, transformed output, and
validation occurs before data access.

The tokens this section introduces, and what each survives:

| Token | Identifies | Minted by | Survives |
|---|---|---|---|
| handle | one exported view or mutation, as `(TreeID, module path, export name)` | the author | code changes; not a move or a rename of the export |
| code version | one compiled handle | the compiler | moving the source tree; not a code change |
| model fingerprint | one collection schema's model layer ([schema language §9](1.5-schema-language.md#9-fingerprints)) | hashing the checked model layer | storage and presentation changes; not a model change |

## 4. Queries

A query is a deterministic function of `(resolved node snapshots,
validated input, trusted user context)`. Its only data door is a finite,
declarative selection over the scoped logical node model. The runtime gives a
query no clock, randomness, network or file access, so nothing else can reach
its result; a mutation's time and generated IDs come from its runner ([§5](#5-mutations)). Authored sources use
`node(path)` everywhere. The initial portable node-set source is `.children`,
with the same meaning for expanded directories, Markdown records, collection files,
and SQLite projections. Every result retains
tree-scoped provenance internally even when the authored projection omits it.

Authors don't write plans. A [view](#41-views) is written as code over typed node
sources, and the host derives its plan from what the view reads. `Model.one` and
`Model.all` assert the cardinality of a typed node source; they do not imply a database
relation. Facts that prevent private nodes or rows from being disclosed stay in the server
plan and are never delegated to a component.

A query reads the source's schema-declared properties. A collection is a typed
node set within this language, not a separate query universe, and a query means
the same whichever representation holds it: a host may run a plan as SQL,
through indexes, or by tree traversal, but cannot change its meaning.
Results have automatic deterministic ordering by canonical stable
key, falling back to canonical path. Other ordering is the view's own code, except
that a limit (`.orderBy(…).take(n)`) orders in the plan.
Relationship reads, joins through facts, counts and limits are baseline ([§4.1](#41-views)). Grouping,
other aggregates, pagination operators, and unbounded traversal are capability extensions
rather than baseline semantics ([deferred 6](README.md#deferred)). An unavailable capability fails
before data access rather than silently loading an entire tree into executable
memory. There is no authored `database()` source or `.relations` namespace.

Literal node/store locators are resolved by the development compiler. Declared
property and child schemas generate TypeScript source types;
homogeneous children receive one item type and heterogeneous children a declared
discriminated union. Computed locators require an explicit schema and capability
bound. The compiler never guesses from sampled data. Activation pins the
contributing schema fingerprints, and refuses a stale plan or keeps the
last-known-good version. Inferred row and result types
are exposed by the authoring API, so authored source maintains no second
result schema.

Activation retains each literal's authored spelling together with its resolved
`(TreeID, logical path, schema fingerprint)`; the authored basename is never a
store identity. Before a query reads or a mutation's transaction begins, the
host verifies that complete binding against the mounted tree, the selected
collection, and its active schema. Imported helpers retain the binding
of the module in which their `node(path)` was authored. An unbound, ambiguous,
stale, or differently resolved handle is inactive rather than being redirected
to a same-named collection.

The plan selects node/store facts and specified aggregates. A [view](#41-views)'s
other code runs over the plan's authorized results and can read nothing the plan did
not select. The plan is constructed once, not per node.

Live behavior is intrinsic to a query. A one-shot caller evaluates its current
value once; a subscribing caller maintains that same value as a stream of
authorized complete query-result states, never raw driver changes, with the
no-gap, deduplication, and coalescing guarantees of
[§12.1](#121-evaluate-and-stream-views).

A live dependency plan is a set of (observation cursor, precision scope)
entries: the narrowest proved nodes, child membership, property/content
fields, edges, schema fingerprints, mounted roots, and profile/access facts
that can affect the result, each bound to the cursor it was read through
([tree watching](1.2-reading-and-watching.md#113-watching)). The host follows
it through tree watches or conservative subtree invalidation. Observation precision is an
optimization and cannot change the result.

For a `.children` source, execution samples the resolved parent before reading
child pages and retains its child membership, schema fingerprint, and
the tree's accepted `update` as a membership dependency. Continuation cursors are
bound to the membership update used to create them. A subscriber follows or
replays from the retained pre-read update; therefore an insertion or removal
that races sampling or paging forces a rerun and cannot fall into a
snapshot/observation gap. Per-child precision may narrow property invalidation
but do not replace the parent membership dependency.

A query whose nodes are not materialized locally may be hosted by the relevant
server when that host enforces the same validation, access, determinism, and
version contract. A read-only placement projection may
materialize a reviewed node query into SQLite and serve its last completely
applied state offline. This specification does not define general cross-server
query discovery, delegated authorization, or server-to-server routing
([deferred 2](README.md#deferred)).

### 4.1 Views

A **view** is a function over typed node sources that returns data or a view tree
([§10](#10-rendering-actions-and-live-data)). A **data view** returns JSON. A **JSX view**
returns a view tree. Both are written the same way, directly over rows, and neither is
derived from the other.

#### 4.1.1 Reading rows

A view reaches rows in three ways:
- **A model's rows**, through facts: `List.all(l => [facts])` or `List.one(l => [facts])`.
  `List` is a typed node source such as `node("./data/List").children`.
- **A relationship's rows**, by reading it: `l.items`, `p.tags`, `l.owner`. A plain
  relationship read needs no facts.
- **A relationship narrowed by facts**: `p.tags.all(t => [facts])`.

A row's fields are ordinary values (`l.name`), and `.length` on a relationship is a count.
Inside `.orderBy(…)`, which runs in the plan, the same count is spelled `count()`;
everywhere else it is `.length`.

#### 4.1.2 Facts

Facts are the view's narrowing. They are Datalog-style clauses over a row variable:

| Fact | Means |
|---|---|
| `l.visibility.is("Public")` | a field equals a value |
| `p.name.contains(text)` | a text field contains text |
| `l.owner.is(person)` | a to-one relationship points at a row, a key, or `null` |
| `p.authors.has(person)` | a to-many relationship includes a row or a key |
| `l.items.practice.authors.has(person)` | a **path fact**: some item's practice has this author |
| `or([facts], [facts])`, `not(fact)` | alternatives and negation |
| `curatedBy({ l, person })` | a **rule**: named facts, defined once with `rule(…)` |

Rows from enclosing code act as placeholders that are already filled in. In
`p.tags.all(t => [t.list.is(l)])` inside a loop over a list's items, `l` is the list being
drawn. So an inner block's matches nest under each outer row, and the result is
tree-shaped.

A variable that appears in two facts is a **helper variable**, named with an object of
sources: `Person.all({ p: Practice }, (other, { p }) => [p.authors.has(person),
p.authors.has(other), not(other.id.is(id))])`. Its type comes from its source.

Facts are the only narrowing. A view's other code (`.filter`, `.sort`, `===`, branches)
runs over rows it has already read and can't change what the plan reads.

A model's **read rules** keep private rows from being disclosed. They belong to the data,
not to any view: the host adds them, as facts, to every read of that model, whether the
read is a `Model.all`, a `Model.one`, a relationship read or a path fact. A view can narrow
further but never past them, and a view that forgets them still can't see a hidden row.
Supplies' rule is "a list is readable when it is public, or by its owner".

Ordering is the view's own code (`sorted(rows, byName)`). The one exception is a limit:
`List.all(…).orderBy(l => l.reactions.count().desc()).take(12)` orders and cuts in the
plan, because the cut depends on the order.

#### 4.1.3 Implicit shape and dual evaluation

A view's **shape** is which sources it reads, which relationships it follows, which
fields it selects, and the facts that narrow each read. It isn't declared. The host finds
it by evaluating the view twice:
1. **The plan pass**, on the host. The view runs over stand-in rows that record each read.
   Every `.all`, `.one` and relationship read, every field read, and every fact becomes
   part of the plan of [§4](#4-queries). A function the view calls with a row (a component, or a helper
   that returns JSON) joins the caller's plan.
2. **The value pass**, over the plan's authorized results.

A read the plan pass missed, such as one behind a branch it didn't take, widens the plan
once and reruns. View code must therefore be deterministic and free of side effects, as
[§4](#4-queries) already requires, and must be safe to run over stand-ins: a stand-in row is never
`null`, and a stand-in relationship has one row.

Where the value pass runs depends on the kind of view:
- **A data view** runs its value pass on the host. The result is JSON, annotated with
  **field types** and **row identity**: each value copied unchanged from a row field
  carries that field's schema type, and each object built while reading a row carries
  that row's model and key ([§12.1](#121-evaluate-and-stream-views)). A client with no
  view code of its own draws a data view with its default renderer (Story uses
  Quagmire's), using those annotations.
- **A JSX view** runs its value pass on the client. The host answers with the plan's
  authorized rows, in the same annotated form, and the client runs the view over them.
  State changes on the client, such as controls and local selection, rerun the view there
  without asking the host. If the client's run reaches a read the rows lack, it asks the
  host to widen the plan. A client that can't run view code may ask the host for the view
  tree instead.

A view exported with an input schema is **addressable**: a link, an embed or a
[request](#121-evaluate-and-stream-views) can name it. Views replaced the
select-object queries of earlier drafts.

#### 4.1.4 Declared views

A schema's `~views` ([schema language §8](1.5-schema-language.md#8-views)) are
**declared views**, defined there. A client may draw one's result with its own native list.

Declared and authored views are one kind:
- A host serves either through [§12.1](#121-evaluate-and-stream-views), with the
  same plan, authority, live behavior and result form.
- A client draws either wherever a view can appear, including on a page that presents a
  collection.
- Both are named the same way ([§12.1](#121-evaluate-and-stream-views)): a tree,
  the logical path of a module or a schema, and an export or a `label`.

## 5. Mutations

A mutation runs as its caller, with the authority
[access control §1.1](3.2-access-control.md#11-execution-authority) gives its
code. Code is trusted to narrow behavior and disclosure within that authority.
There is no mutation-permission namespace and no implicit whole-tree write.

A mutation runs in one runner-owned transaction: its reads, checks, writes and
receipt commit together, and throwing rolls them back. Checks that depend on
data belong inside it. Its writes reach their tree as one ordinary update,
guarded by the state the mutation read
([updates and merging §1](1.3-updates-and-merging.md#1-the-update-request)); a
stale guard reruns the mutation rather than merging a stale decision.

The caller supplies one mutation identity and reuses it for an ambiguous retry;
[§12.2](#122-execute-named-mutations) defines the request digest
that binds it to the handle, code version, validated input, and activated
source bindings, the replay scoping, and the receipt. The runtime captures one
logical mutation time and deterministic generated-ID namespace before
execution; exact retries observe the same values. The runtime records the
retry identity and its result so that, after a restart, a committed mutation is
never mistaken for one that never ran.

Expected failures are public errors ([§15.4](#154-actions-and-forms)); any
other thrown value becomes a generic internal error with no stack trace, SQL,
path, or private row data.

Mutations that span several trees, durable workflow steps, portable
foreign-key actions, and external non-tree effects are not yet specified
([Apps 006](../../plans/later/apps-006-durable-authoring.md),
[deferred 3](README.md#deferred)).

## 6. Components, imports, and consent

Components run within a confined UI realm. Node data and effects enter through view and mutation handles. The [no-ambient-authority rule](#2-source-forms) applies; UI-local timers, focus, and animation do not become data authority.

Cross-tree source imports use absolute Overstory locators and resolve to immutable code identities for one build or execution. Imported libraries retain source-resolution context but acquire no independent grants. Importing code cannot widen authority.

Before code first uses anything beyond what needs no lender
([access control §1.1](3.2-access-control.md#11-execution-authority)), the
client shows a **consent statement**: the resolved trees, the readable and
writable prefixes, and the access the code asks to be lent. Broad or computed
declarations stay visibly broad, and enforcement must make the statement true.
A host process's broader filesystem or credentials never become an app's
capabilities. Named handles are callable from human clients and agent tools
with the same identity, validation, and authorization.

## 7. Compilation and hosting

A module's **code version** is the SHA-256 over the paths and bytes of the
files its imports reach in the tree, in path order. A module's path is
ordinary Overstory identity, not an application ID: moving a module changes
its view's address just as moving any other file changes its URL. Imported
handles are identified by tree, module path, and export name.

Adding `.ts` or `.tsx` source does not publish it, execute it, or grant it
access: a host runs code only for trees whose hosting it has enabled. It may
compile eagerly or on demand, but a request uses one coherent code version of
the addressed view and all of its handles, and an incompatible compilation
fails without replacing the last usable version.

A reviewed manifest of what compiled code needs, and static baking of reads,
are not yet specified
([Apps 010](../../plans/later/apps-010-activation-and-lending.md)).

## 8. Data disclosure

Access to a collection and access to an app's results are distinct. A public
view may read a private tree, but only its validated results are disclosed:
raw stores, credentials, handler source, diagnostics containing private
values, and unrelated rows never reach the browser or a public response.
Conversely, public and private rows in a publicly readable tree are exposed
by the tree's own bytes whatever a view filters, so row-private data lives in
a private tree, or in separate trees, behind views that publish only their
results.

Authored JavaScript receives handles, never the caller's credentials, and
code identity asserted in public input never establishes execution authority
([access control §2](3.2-access-control.md#2-authentication-and-secrets)).
A revocation reaches running views and mutations, not merely the request that
started them.

## 9. Overstory user identity

Apps define no password, sign-in or session model of their own. The host
resolves the caller's Overstory session and passes views and mutations an
unforgeable user context:

```ts
type OverstoryUser = null | {
  profile: TreeID
  community: TreeID
}
```

Account IDs, device IDs, credentials, and handles are not user identities to
an app, and handlers never accept a caller-supplied profile or account ID as
proof of identity. Rows referring to a person store that profile's `TreeID`;
display name, handle, portrait, and other public profile fields are read from
the profile tree when the view runs, as live dependencies, so a profile edit
updates the views streaming it.

A view or mutation may require a user ([§15.5](#155-user)); the host then
presents its own sign-in before user-dependent reads run. The host rechecks
the session on each request and stream; revocation ends existing streams.

Anonymous and signed-in executions are separate cache and subscription
contexts. A user-dependent view records the identity and access decision as
dependencies, and a result is shared between callers only when its inputs,
authorization, and output are genuinely user-independent.

## 10. Rendering, actions, and live data

The host resolves the requested path to a view, loads one coherent code version, converts the query string to the view's input ([§1](#1-views-and-their-addresses)), and answers as [§4.1.3](#413-implicit-shape-and-dual-evaluation) says for the kind of view. A browser request gets HTML rendered from the view tree, with only validated results and public handle metadata embedded. A client that runs view code gets the plan's rows and draws the view natively.

A JSX view ([§4.1](#41-views)) runs on the client over its `rows` answer, so state changes
on the client rerender without a round trip to the host. The host keeps the rows current
through the same live stream ([§12.1](#121-evaluate-and-stream-views)), and the client
reruns the view when they change.

A mutation is used from a view as an action value ([§15.4](#154-actions-and-forms)), and from
code as a typed call. Optimistic presentation never displaces the subscribed result as the
source of truth.

## 11. Portability

The same source may be served by any compatible local runtime or
server that provides its declared nodes and runtime features. A handle
means the same thing whether expanded children, collection files, or a
placement's SQLite projection supplies its source; schema compatibility,
model fingerprints, and data migration are checked before a new handle
version is used. Cross-server execution never acquires authority merely
through network reachability.

## 12. Overstory operations

Apps use two operations. Views derive current permissioned values without
exposing raw stores; mutations execute reviewed transactional intent. Neither
is accepted-tree synchronization, even when a mutation also advances a data
tree.

### 12.1 Evaluate and stream views

```text
QUERY /.overstory/trees/{SourceTreeID}/views
Content-Type: application/json
Accept: text/event-stream
```

The request names every view a client currently shows from one source
tree. A server without an app runtime, or without hosting enabled for the
source tree, returns `422 unsupported-operation`.

```ts
/**
 * Names a view or a mutation: a name in a file in a tree. For an authored
 * handle, `path` is its module and `name` its export. For a declared view
 * (§4.1), `path` is a collection's `schema.usl` and `name` a `~views` label.
 * `version` is the module's code version (SHA-256 over the paths and bytes of
 * the files its imports reach in the tree, in path order) or the schema
 * file's object hash. The host tells which kind it is from the file at `path`.
 */
type HandleRef = {
  tree: TreeID;
  path: LogicalPath;
  name: string;
  version: Hash;
};

type ViewsRequest = {
  views: Array<{
    id: string;
    handle: HandleRef;
    input: unknown;
    /**
     * What to answer (§4.1). `value`: a data view's JSON. `rows`: a JSX
     * view's plan results, for a client that runs the view itself. `tree`:
     * a JSX view's view tree, run on the host. Defaults to `value` for a data
     * view and `rows` for a JSX view.
     */
    form?: "value" | "rows" | "tree";
    /** Reads a client's run of a `rows` answer reached and didn't find. */
    missed?: ReadPath[];
    knownOutputHash?: Hash;
  }>;
};

/** A read as a path from a root of the plan, such as ["lists", "items", "practice", "tags"]. */
type ReadPath = string[];

/**
 * Annotations on a `value` or `rows` answer, parallel to its JSON.
 * `row` is set on an object built while reading a row (its model and key).
 * `type` is set on a value copied unchanged from a field (that field's
 * schema type, as in schema language §3). `fields` and `items` describe an
 * object's members and an array's elements.
 */
type ResultShape = {
  row?: { model: LogicalPath; key: string };
  type?: string;
  fields?: Record<string, ResultShape>;
  items?: ResultShape[];
};
```

A `missed` list widens the plan for that view and input. The host can't check a path
against the view's code, because a missed read is one its own trace didn't see. What
bounds a widened plan is the caller's authority and the read rules of each model it
reaches ([§4.1](#41-views)): a forged path reads nothing those don't already allow.

Every handle's `tree` must equal the route `SourceTreeID`. The `views` array
is nonempty and its IDs are nonempty and unique within this request. The host
verifies each handle's code version, its input, the user context, effective
access, and the schema fingerprints the view's sources were bound to. The
request and events are independent of whether those nodes are expanded files,
collection files, or SQLite. A
`knownOutputHash` permits omission of unchanged bytes only after fresh
authorization and reevaluation; it is neither
authorization nor evidence of current state. Output hashes are SHA-256 of the
canonical CBOR encoding of the complete public result.

A view's live dependencies are conservative: an ordinary `.children` read
depends on its resolved parent's membership and schema, the sampled child
identities and model hashes, and every field used by narrowing or selection.
Narrower dependencies are an optimization, and missing precision never skips a
reevaluation.

The UTF-8 SSE response has these semantic events:

```ts
type PublicQueryError = {
  code: string;
  message: string;
  retryable: boolean;
};

type ViewEvent =
  | {
      type: "result";
      id: string;
      outputHash: Hash;
      value: unknown;
      /** Field types and row identity for `value` and `rows` answers (§4.1). */
      shape?: ResultShape;
      error?: never;
    }
  | {
      type: "result";
      id: string;
      error: PublicQueryError;
      outputHash?: never;
      value?: never;
    }
  | {
      type: "ready";
      views: Array<{
        id: string;
        outputHash?: Hash;
      }>;
    }
  | {
      type: "reload";
      reason: "source-changed" | "access-changed";
    };
```

The SSE `event` field supplies `type`; JSON `data` supplies the remaining
members. Each `result` is a complete authorized replacement for one query, not
a raw driver event or patch. `ready` is sent only after every query has
established a race-free snapshot-then-follow boundary. Before `ready`, changed
hashes produce complete `result` values and an unchanged retained value may be
confirmed by its hash in `ready`. Identical output hashes produce no payload.
The observation listener is active before sampling. Events racing evaluation
are checked against both the former and newly sampled dependencies; a relevant
event forces another complete evaluation before that result is published. This
is the no-gap guarantee. It does not require a retained query-event replay log.

`QUERY` has the safe and idempotent semantics defined by
[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008.html). Evaluating or
subscribing to a query never performs a mutation. The response is
user/access dependent and long-lived, so it carries `Cache-Control: no-store`;
automatic retry still reauthorizes and reestablishes current state rather than
reusing a cached body.

The response lifetime is the subscription lifetime. There is no durable
execution ID, acknowledgement, SSE replay cursor, or resumable server-side
subscription. Reconnection repeats and reauthorizes the complete `QUERY`. When
the mounted query graph changes, the client opens a complete replacement request
and retains the old response only until the replacement sends `ready`. Source
or access changes send `reload` when possible and close. Listener loss, backing
uncertainty, process restart, or irrecoverable backpressure closes rather than
publishing a result known to be stale; hosts may coalesce intermediate complete
states.

### 12.2 Execute named mutations

Mutation calls carry the reviewed handle identity and version, validated input,
authenticated subject, and caller-stable mutation identity:

```text
POST /.overstory/trees/{SourceTreeID}/mutate
Content-Type: application/json
```

```ts
type MutateRequest = {
  handle: MutationHandleRef;
  mutationID: string;
  input: unknown;
};

type MutationHandleRef = HandleRef;

type MutationResultReceipt<Result = unknown> = {
  mutationID: string;
  requestDigest: Hash;
  /** The accepted update the mutation's writes made, when it wrote. */
  affected?: {
    tree: TreeID;
    update: string;
  };
  result: Result;
};
```

`handle.tree` must equal the route `SourceTreeID`. The host validates the
handle's code version, input, source bindings and authority before data
access. Invocation requires authorized executable presentation, not raw private
source disclosure. Current authority is checked before every new step and receipt
return. Revocation does not undo committed effects. Missing authority cannot reserve
a new effect or leak private handle/resource existence.
Mutation semantic identity is the SHA-256 of the canonical CBOR encoding of
`{ version: "mutate-v1", handle, input, sources }`, where `sources` is the
activated handle's complete, authored-path-sorted set of
`{ authoredPath, tree, path, schemaFingerprint }` bindings. The bindings are resolved when the handle is activated; a caller-selected destination needs concrete resolution and grant coverage. This prevents an
ambiguous retry from executing the same code and input against a newly resolved
store, relation, or schema. Durable lookup is scoped by the source tree, a
trusted caller replay principal, and `mutationID`. The principal is the
authenticated profile TreeID when present, otherwise the presented access-link
digest identity, otherwise an anonymous identity. It is runtime-only authority:
link digests and replay-principal values never enter authored handler context,
results, errors, logs, or transcripts. Reusing that identity
with a different request digest is a conflict; an exact ambiguous retry returns
the original receipt and creates no second effect. This is the same committed-
intent pattern as an accepted tree update: transport representation is excluded
from the semantic digest, the subject scopes replay, and `affected` names the accepted update the mutation's writes made: a client
knows a view result reflects the mutation once that tree's watch has passed
that update. The mutate payload remains distinct from `UpdateRequest`: it
carries reviewed intent, while an update carries tree material.

An action submitted from a browser form may use the view's ordinary canonical
HTTP action surface, while a named Overstory call uses the endpoint above. Both bind through the
compiled handle and preserve this exact request/receipt identity.
The durable receipt and corresponding query result may arrive in either order;
clients correlate them idempotently and treat the query result as authoritative.

### 12.3 Relationship to tree synchronization

`updates`, `watch`, `views` and `mutate` share authentication, semantic digests,
SSE framing, and tree-scoped authorization, but not
transaction or replay domains: `updates` and `mutate` have different conflict
domains, and `watch` has retained replay identity while `views` deliberately
has none. An accepted update requires authority covering its actual effects; a named mutation
requires coverage of its declared author/user capabilities. Consolidation
is shared machinery, not one polymorphic endpoint.

Query streaming is derived-result delivery, not tree history. A mutation of an
Overstory-canonical data tree advances that data tree's ordinary accepted root and
therefore also causes a `tree.update` watch event; it does not change the
app's source-tree root. Neither execution nor
network reachability independently grants accepted-snapshot access, broadens
the readable tree graph, or exposes raw stores, credentials, private handler
source, unrelated rows, or private diagnostics. Cross-server query discovery,
delegated authorization, and server-to-server execution routing remain
unspecified ([deferred 2](README.md#deferred)).

## 13. Agents

A person's own agent run by a client, such as a coding agent working in a
placed folder, edits as its person, through that person's placement, and
appears to others through [presence](1.2-reading-and-watching.md#3-presence)
as an agent of that person. Hosted agents, apps whose body is a prompt with
their own tools, confinement and transcripts, are not yet specified
([Apps 002](../../plans/later/apps-002-overstoryd-hosted-agents.md),
[deferred 4](README.md#deferred)).

## 14. Schema identity

Schema information and explicit relationship declarations are mapped to canonical tree-rooted collection paths so executable source remains portable across placements. Relative collection references resolve against the source tree and path before use. A change to a collection's model layer changes its model fingerprint and invalidates dependent compiled handles. A storage or presentation change alone invalidates none.

## 15. Authoring API

The `overstory/data` and `overstory/ui` packages are a library contract versioned with those packages; the sections above define every semantic guarantee they expose.

Package names are part of the authored portability surface: a compatible runtime provides these two modules with these exports, so the same source runs anywhere the [execution model](#11-portability) allows.

### 15.1 Packages

`overstory/data` is authoring for data and handles: `node(path)` logical node sources, schema-derived children handles with `.all` and `.one`, `view`, facts (`or`, `not`, `rule`), `mutation`, `publicError`, `RowOf`, and `ResultOf`.

`overstory/ui` is the JSX runtime and the UI language's components, among them `Markdown`, `Button` and `Form`. There is no React: no hooks, Suspense, or React Actions.

### 15.2 Views

A view ([§4.1](#41-views)) is a function
from validated input and the user to JSON or a view tree, made with `view`. A file's
default export is its linkable view ([§1](#1-views-and-their-addresses));
named exports are imported:

```tsx
import { node, or, rule, view } from "overstory/data"
import { z } from "zod"

// Components (Shell, PracticeGrid, ListGrid), row types and sorting helpers are omitted.
const List = node("./data/List").children
const Person = node("./data/Person").children
const Practice = node("./data/Practice").children

// Who may see a list is a read rule on the List model, which the host applies to every
// read (apps and views §4.1). Views don't repeat it. `rule` is for an app's own
// reusable facts, such as this one:
const curatedBy = rule<{ l: ListRow; person: PersonRow }>(({ l, person }) => [
  or([l.owner.is(person)], [l.contributors.person.is(person)]),
])

// A data view: JSON, drawn by a client's default renderer when it has no code of its own.
export const list = view(z.object({ id: z.string() }), ({ id }) => {
  const l = List.one(l => [l.id.is(id)])
  if (!l) return null
  return {
    name: l.name,
    about: l.about,
    practices: sorted(l.items, byPosition).map(i => ({
      id: i.practice.id,
      name: i.practice.name,
      tags: i.practice.tags.all(t => [t.list.is(l)]).map(t => ({ name: t.name, color: t.color })),
    })),
  }
})

// A JSX view: the same reads, drawn. Components take rows and read what they show.
export const ProfilePage = view(z.object({ id: z.string() }), ({ id }) => {
  const person = Person.one(p => [p.id.is(id)])
  if (!person) return <Shell title="Profile not found" />
  return (
    <Shell title={person.name}>
      <PracticeGrid practices={sorted(Practice.all(p => [p.authors.has(person)]), byName)} />
      <ListGrid lists={List.all(l => [l.items.practice.authors.has(person)])} />
      <ListGrid lists={List.all(l => [curatedBy({ l, person })])} />
    </Shell>
  )
})
```

Input comes from the query string ([§1](#1-views-and-their-addresses)),
validated by the view's Standard Schema-compatible input schema. Zod is supported
directly, without an Overstory-specific validator vocabulary. A view with no input
omits the schema.

The view tree is plain `{type, props, children, key}` data built by the JSX runtime.
The vocabulary of view types, controls, local state and styling is the UI language
([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)); a client draws it natively
or as HTML.

`Markdown` renders a Markdown source string with Overstory's ordinary link resolution,
safe URL and asset policy, and source semantics. It is the standard way for a view to
present stored Markdown.
It resolves a relative Markdown destination from the directory holding the
source file, as [locators §2.1](1.6-locators.md#21-links-written-in-markdown)
defines. For a destination carrying the reserved `#overstory-key=` alias, it emits
the equivalent server-visible path suffix and preserves the authored
application query. It does not forward the reserved identity alias as an HTML
fragment.

`RowOf` and `ResultOf` expose the types the development compiler infers from declared property and child schemas, so authored source maintains no second result schema.

### 15.3 Mutations

`mutation` accepts an optional Standard Schema-compatible input schema. The mutation's
call input is the schema input type; its handler receives the validated, transformed
output. Validation occurs before data access.

A handler runs in the runner-owned transaction of [§5](#5-mutations). The runtime
owns receipts and deterministic IDs; authors do not implement receipt or outbox
tables.

### 15.4 Actions and forms

Calling a mutation without `await` gives an **action value**, which `Button action=` and
`Form action=` take. `handle.with({…})` adds input, and `.then(result => link)` names
where to go after it succeeds. A client runs the action, supplying a stable mutation
identity, and exposes pending state, then a typed result, durable receipt, or public error.

Form conversion is shallow and deterministic: a name occurring once becomes its string
or file value, a repeated name becomes an array in document order, and an omitted name
is absent. Coercion belongs to the authored schema. Expected failures use
`publicError(code, message, options?)`: a stable code, a safe message,
retryability, and optional field errors. Server exceptions, private values and
stack traces never become action state.

`mutation.for(Model, "create" | "edit" | "delete" | "move")` declares a mutation as that
model's row action, so any list of the model offers it.

### 15.5 User

A view receives the user ([§9](#9-overstory-user-identity)) as `{ user }`, its second
argument. A plan may dereference the nullable-safe symbolic `user.profile`, or use
`user.required.profile` to declare that anonymous execution must fail before data
access.
