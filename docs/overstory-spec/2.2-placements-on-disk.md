# Placements on disk
*Part of the [Overstory spec](README.md), layer 2 (clients): how a placement writes a tree into a folder and reads edits back. Pages, page frontmatter, which entries of a folder are tree content, and how collections are written as files or SQLite. None of this is tree content: two placements of one tree may write it differently and hold the same root.*

## 1. Projection boundary

This format is not the Overstory ontology. It maps ordinary directory entries,
Markdown/frontmatter, reserved store files, and child-placement syntax to the
representation-independent nodes, properties, content, children, and identities
defined by the data model. Another conforming projection may arrange source
differently while preserving the same model and the projection-specific fidelity
guarantees it advertises.

The directory projection preserves exact authored source in addition to modeled
state, so its writes match on [bytes hashes](1.1-data-model.md#4-representation-and-model-equality):
file bytes change the bytes hash even when the model hash is unchanged.

Pages and logical collections are the exceptions. A Markdown page is a
[page object](1.1-data-model.md#51-pages) in the tree: its properties, its
`id` and its exact body bytes. Its frontmatter is this placement's spelling of
those properties ([data model §9](1.1-data-model.md#9-properties-markdown-content-and-identity)), so spelling, quoting and comments stay on the placement
that wrote them, while the body is byte-exact everywhere.

For a logical collection, the rows are logical state in the
tree, and the files a placement writes for them (`_store.csv`, `<Table>.jsonl`,
Markdown row files, `_store.sqlite3`) are that placement's own
[projection](#4-projections), outside this byte-exact
promise. They keep their formatting on the placement that wrote them, and
another placement shows the same rows in its own.

## 2. Pages on disk

A placement reads and writes pages as it does collection files
([§4](#4-projections)):

- **Tolerant read.** Any valid edit to the file, by any program, becomes
  property and body changes against the page last written there.
- **Minimal write.** Writing an accepted page changes only what changed. A
  property change from elsewhere is spliced into the frontmatter already on
  disk, keeping its quoting, comments and key spelling where it can.
- **Canonical form,** for a page written from nothing: `---`, then `id:` if
  present, then the properties in stored order as YAML 1.2 block style, then
  `---` and the body. A page with no `id` and no properties has no frontmatter
  block.
- **Normalizing is not changing.** A file whose frontmatter reads back to the
  page on disk is left as it is, and is no change to the tree.

## 3. Tree membership and ignore files

Not every entry in a placed directory is tree content. An entry that one of the
rules below excludes is not a node, is not part of any snapshot, and is never
published. Writing accepted state into the directory never overwrites or
deletes it. It stays an opaque placement file: it remains on disk and
local tools may open it, but it belongs to that placement, not to the tree.

A collection's projection files ([§4](#4-projections)) are not
tree content either, but they aren't opaque: the placement reads edits to them
as row operations and writes accepted rows into them.

**Mandatory exclusions.** These are never tree content, whatever an ignore file
says: directories named `.git`, `node_modules`, `.overstory`, `Trash`, `.build`, or
`DerivedData` and everything beneath them; write and transaction temporaries
(names containing `.overstory-write-` or `.overstory-txn-`); operating-system metadata
the system rewrites on its own, namely macOS Finder's `.DS_Store` and
AppleDouble `._name` files, at any depth; a cloud provider's
placeholder for an evicted file, such as iCloud's `.name.icloud`, which stands
for its logical file; symbolic links; and the root of a nested tree mounted in
the directory, whose content belongs to that tree. A root accepted before an
exclusion applied may still name such a path; a folder client neither writes
nor removes the local file there, and publishes the root without it.

**Ignore files.** `.overstoryignore` is the portable spelling of an ignore file.
`.gitignore` is read with the same meaning for compatibility. Each applies from
the directory that contains it downward and uses Git's pattern grammar: blank
lines, `#` comments, backslash escapes, unescaped trailing spaces removed, `!`
negation, a trailing `/` for directories only, a leading or inner `/` anchoring
the pattern to the file's directory, and `*`, `?`, bracket expressions, and
`**`. Paths are matched with `/` separators, case-sensitively, one Unicode
character at a time. A rule in a deeper file overrides one in a shallower
file, `.overstoryignore` overrides `.gitignore` beside it, and within a file the
last matching rule decides. As in Git, an entry beneath an excluded directory
cannot be re-included, and ignore files inside an excluded directory are not
read. An ignore file that is not valid UTF-8 contributes no rules. An
implementation reports that locally, naming the file but never its contents,
and continues.

Ignore files are themselves ordinary tree content. They are published like any
other file, and no rule excludes them except by excluding a directory that
contains them. Only these files decide membership: `.git/info/exclude`,
`core.excludesFile`, a global Git ignore file, and Git's index are never
consulted, because they are private to one machine and would make the same
directory yield different trees on different devices.

**Tracked entries.** Rules keep new local content out of a tree; they do not
take out content already in it. A path in the tree the directory last held is
*tracked*: it stays tree content even when a rule matches it, so its local
edits are published and accepted changes to it are written. It leaves the tree
only through an explicit deletion, local or accepted. After that, a local file
at that path that a rule matches is untracked and stays in the directory,
unpublished. A directory placed for the first time has nothing tracked, so its
rules apply before its first snapshot. Editing an ignore file therefore never
deletes anything from a tree, and writing accepted state never deletes
untracked content that the directory's rules, before or after the write,
exclude.

## 4. Projections

A placement chooses how to project each collection: as files of a format, as
a SQLite database ([§5](#5-sqlite)), or not at all. The choice and the
placement's own [storage mapping](1.5-schema-language.md#7-attributes) are
placement-private options ([§7](#7-local-placements)),
never tree content. On first sight of a collection it has no choice for, a
placement records what it finds on disk, so an existing folder keeps its
files. Creating a projection from nothing writes canonical form ([§4.1](#41-file-projections)).

Every projection reads and writes the same way:

- **Tolerant read.** Any valid edit to the projection, made by any program,
  becomes row operations against the state last applied to it. A row the
  schema can't read is reported for that row, and the rest of the collection
  still syncs.
- **Minimal write.** Applying accepted state writes only changed rows: a file
  projection splices changed rows into the file it already has, keeping its
  column order, quoting, line endings, unchanged rows and anything else
  that isn't data, and a database updates only changed rows in one
  transaction. A write never overwrites an edit the placement hasn't read yet.
- **Typed values at the boundary.** A projection converts between its
  spellings and [collections §2](1.4-collections.md#2-rows-and-values)'s values. Normalizing is not changing: a stored value
  that reads back equal to the logical value is left as stored.

Partial files and rolled-back attempts never become observable committed
states. Projection bytes, query plans and SQLite pages are private placement
state.

### 4.1 File projections

A file projection holds a collection's rows in one of these forms, beside its
`schema.usl`:

- `_store.csv`, `_store.json` or `_store.jsonl`, when the file layout has one
  table;
- one `<Table>.csv`, `<Table>.json` or `<Table>.jsonl` per table of the
  [file layout](1.5-schema-language.md#10-layout), all in one format; or
- one Markdown file per row of a single-table collection: the body field
  ([collections §2](1.4-collections.md#2-rows-and-values)) as the body, the title field as its first H1, and the other fields as
  front matter. Such a file is a projected record, not a page, so
  [data model](1.1-data-model.md) byte-exactness doesn't cover it,
  and Story presents the folder as a collection.

`_store.csv` uses its header for column names. `_store.json` is one top-level
JSON array whose elements are row objects. `_store.jsonl` has one JSON object
per nonblank line. Each row has its file-layout columns, `created` and
`modified` included. Canonical form, for a projection created from nothing,
writes rows in stable-key order and columns in layout order, as RFC 8259 JSON
without whitespace, or CSV per [§4.2](#42-csv-cell-conversion).

Mixing projection forms in one folder produces a diagnostic and stops the
placement from reading the projection, without making the files inaccessible
or changing the tree.

### 4.2 CSV cell conversion

A CSV cell is text, so a CSV projection converts each cell to a value using
its column's type. JSON values are used as parsed and converted to [collections §2](1.4-collections.md#2-rows-and-values)'s
types (an `Int` column's `2.0` reads as `2`; `2.5` makes the row unreadable).

Header names must be distinct; a repeated header name makes the file
unreadable. A header name that is not a declared column is the placement's
own, kept on write and never read as data. A declared cell converts as
follows:

1. A missing or empty cell is absence when the column is optional or an array,
   otherwise the empty string for a text column; otherwise it is invalid.
2. A nonempty text cell (`Text`, `Markdown`, `Date`, references) is its exact
   text, so a key such as `001` remains the string `"001"`.
3. A nonempty `Int` or `Number` cell must match the JSON number grammar
   exactly, without surrounding whitespace, and converts to that number.
4. A nonempty `Bool` cell must be exactly `true` or `false`.
5. A nonempty array cell must be a JSON array.

Writing uses the file's own columns in their order. Numbers use their
shortest round-trip JSON number text, arrays their JSON text, and absence an
empty cell. A value that would not convert back to itself, such as the empty
string in an optional text column, can't be projected to CSV, and the
placement reports the collection as not projectable in that format.

## 5. SQLite

A SQLite projection holds a collection's rows in a `_store.sqlite3` database
in the folder, which implements the schema's
[database layout](1.5-schema-language.md#10-layout) as that placement's storage
resolves it. A placement that finds such a database beside a `schema.usl` on
first sight records it as its projection; one that adopts an existing
database whose names differ records them in its own storage mapping. A
database that doesn't implement the layout, or that the placement hasn't
chosen as a projection, is an ordinary file: a `.sqlite3` file never makes a
folder a collection by being there.

The database stays usable by ordinary SQLite tools. The placement observes
committed changes, including those other processes make, and turns them into
row operations ([§4](#4-projections)); a wakeup alone is never proof of a committed row
change, and when affected rows can't be recovered precisely it rereads the
tables. Positions of `ordered` connections are the database's own, and a
change of position order reads back as a move. A placement applies accepted
row operations to the database in one transaction per accepted update, and a
placement that has missed history rebuilds the database from the host's rows.
The database's pages and WAL are never tree content and are never assigned a
bytes hash.

A host may keep its own SQLite projection of a collection, to answer queries
and run mutations ([executable documents](4.1-executable-documents.md)). It is
derived from accepted state and can be dropped and rebuilt from it; it never
changes what a root means. A mutation computed on it submits its effects as an
ordinary update of row operations. Changing a projection at the same logical
path does not change portable handles.

## 6. Backing migration

Changing how a placement projects a logical collection, from Markdown rows to
CSV or from CSV to SQLite, changes nothing in the tree: the collection's
address, rows, logical hash and portable operations stay as they are, and
other placements are unaffected. Moving rows between a logical collection and
an external store, or between external stores, preserves the logical
collection address, stable row identities, logical child names, and portable
operations only when the schema, primary-key values, child-name rule, and
every field of each row are preserved. The transition is not atomic across
independent backing authorities unless the implementation actually provides
that guarantee.

## 7. Local placements

Placement is intentionally separate from account membership, device
registration, and portable Overstory content. Each implementation may choose its
own local representation, but it must keep operating-system paths and
placement-private options outside synchronized configuration and Overstory content.
How a placement projects each logical collection, and its own storage mapping
for it, are such options ([placements on disk §4](2.2-placements-on-disk.md#4-projections)).
Removing a placement stops that local materialization without deleting local
files, remote identity, ACLs, history, canonical boundaries, or conflicts.

See [reference local placements](../implementing-sync-services/local-placements.md)
for the local file layout and the distinction between a placed folder and a
working tree borrowing that folder's object store.
